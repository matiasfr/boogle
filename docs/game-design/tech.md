# 9. Tech and tooling

Brief; the rules for contributors are in [AGENTS.md](../../AGENTS.md) (imported by [CLAUDE.md](../../CLAUDE.md)) and the
folder map in [src/README.md](../../src/README.md).

- **Stack.** three.js 0.187 (`WebGPURenderer`, WebGPU only; shaders in TSL, see
  [src/render/README.md](../../src/render/README.md)), Rapier 0.21.0 (physics, WASM, loaded behind the splash; equal exact SIMD/plain pins), WebSocket to our server (`ws` 8 on Node 26), TypeScript (strict), bundled with Vite ([package.json](../../package.json));
  the build splits three into a vendor chunk; Rapier is its own chunk and WASM file ([vite.config.ts](../../vite.config.ts)).
  The server ([server/README.md](../../server/README.md)) is Node with Express and `ws`, and runs hosted
  rooms with the game's own `src/world/` and `src/sim/` code (section 8).
- **Layout.** `src/` is grouped by domain: `features/` (auto-loaded plug-ins), `world/` and `world/rules/` (lockstep),
  `sim/` (pure logic), `net/` and `netplay/`, `island/` and `pois/`, `adapters/` (the game side of lockstep state),
  `physics/`, `player/`, `render/`, `boogler/`, `guest/` and `decomp/` (the dino's guest), `boot/` (the loading
  screen), `debug/`.
- **Plug-ins.** Feature entries register entities for world/screen objects and use `onStart(fn)` for one-time setup. Only allow-listed services and prototypes use `onFrame(fn, { phase, order })` ([src/loop.ts](../../src/loop.ts),
  which lists the core hooks' orders; features use −10 and up). `main.ts` wires modules and renders. Heavy or
  rarely used parts load with a dynamic `import()` ("Lazy parts" in `loop.ts`): today the caves, the Boogler's
  conversations and the debug tools; never sync ops, state, rules or anything seen in the first seconds. Shared
  registries: controls (`registerAction`), interactables (`registerInteractable`) and particles (`emit(...)` in
  [src/render/particles.ts](../../src/render/particles.ts)).
- **Draw safety.** Shared instance factories bound visual counts to their buffers and mark rejected counts with batch identity. GPU errors retain console logging and bounded diagnostic marks. Isolated uncaptured errors are non-fatal; device loss, a thrown frame or 60 consecutive GPU-checked failing draws offer Reload without resetting the room; see [graphics recovery](graphics.md). See the [capacity audit](../research/freeze-draw-audit.md) for coverage and limits.
- **Instance uploads.** Local blob-shadow and critter pools retain their fixed capacity, bounds and draw counts.
  After initial allocation, refills upload only the current live matrix prefix. Each refill replaces pending ranges
  from culled or skipped draws; empty fills transfer no matrix bytes, including when an earlier update is pending.
  Particle uploads use their separate owner.
- **Checks.** `npm run check`: lint (determinism rules on lockstep files, import boundaries, `registerOp`/
  `registerState`/`onTick` only in `world/rules/`), `tsc` typecheck, unit tests (`node:test`, pure logic only), the
  registry check (`npm run registry`: wire shapes against `main`, for mixed builds) and build.
  `npm run check:full` adds server tests and the headless WebSocket room tests (`dev/peer-test/ws-run.ts`); local triggers are `src/net*`, `src/world/sync.ts`, `src/world/game-world.ts` or `server/`. Key tests:
  [test/world-replay.test.ts](../../test/world-replay.test.ts) (seeded edits for every op, host killed midway, late
  joiner, identical hashes) and [test/world-snapshots.test.ts](../../test/world-snapshots.test.ts).
- **Frozen shot lists.** `node dev/look/shots.ts dev/look/beats/dev-looks.ts` (or broker client `shots`) warms a
  camera/setting matrix once per route/MSAA/size group, holds one frame and saves direct canvas PNGs with exact
  settings, camera, repeat-pixel checks and timings. It reuses the local session or trusted look broker and
  sheet compositor; ordinary players import nothing new. Native-pixel boards print their still-only limit:
  no evidence of motion, GPU cost, load stalls or feel. Details: [frozen-shot-lists](../research/frozen-shot-lists.md).
- **Production harness.** Only `BOOGLE_HARNESS=1 npm run build` emits the module entries and source-ID import map
  generated by `dev/look/import-map.ts`; the page installs it only with `?debugcam`. A plain `npm run build` emits
  no harness entries, and its debug camera installs no map. This preserves the ordinary game's chunk graph.
  `node .look/see-client.ts look --production --curves` and `playthrough --production --query 'proto=place&shot=play'`
  request this opt-in build automatically. Cold-start explicitly keeps the plain build, including when brokered.
  Development needs no map because Vite serves source modules. The scanner includes quoted IDs in eval strings and
  variables across `dev/`; computed module families must be expanded there. Maps preserve module identity, not copies.
  Pages advertise source-module capability in HTML so tools fail before loading the game when it is absent.
  On a plain build or the live site, `look --url` still supports ordinary stills/video/heatmaps; `--curves`, checkpoint
  restore (`--at`), `--eval`, `--action`, `--until` and warp require the harness build or Vite. Playthrough, perf,
  hitches, sessions, audio/video scripts and source-import scenarios likewise reject plain builds with instructions.
  Window-handle-only scenarios (smoke, reconnect-edit, atlas, home-app, look-lab, roster, splash) remain supported;
  the nightly live smoke test uses that path. Cold-start, boot-time and sw-check also retain plain-build support.
  `hitches --allocs` requires development source URLs even on a harness build; omit `--allocs` or use Vite.
  The report's generic “Never happened (or isn't marked)” catalogue is separate from the bot's failing `NEVER:`
  expectations. “Found a crystal” can be collected but unmarked: the pickup saves `personal.crystals` without emitting
  the `crystal`/`finds` mark. Compare initial and final checkpoints before treating that line as a missed action.
- **Scenarios.** `npm run scenario -- <name>` and `npm run look` (stills, motion sheets, heatmaps). Scenarios in
  [dev/scenarios/](../../dev/scenarios/): atlas, boogler-tag, caves, controls-guide, dino, falls,
  guest-play, interact, lighthouse, one-hand, particles, pause, reconnect-edit, shared-kinds, smoke, splash,
  world-inputs. PR CI runs single-player
  scenarios only (`world-inputs`, must pass; two software-rendered tabs are too slow there); seven others (reconnect-edit,
  shared-kinds, one-hand, interact, caves, lighthouse, atlas) run nightly on the owner Mac via `dev/daily` and never block; the
  rest run only by hand. `smoke` needs a GPU: `npm run check:gpu` runs it in `npm run ship` on a
  Mac, and `smoke.yml` runs it against the live site after every deploy and nightly. Every run is WebGPU (SwiftShader on Linux and CI, Metal on a Mac). `npm run island-map` renders the composed island.
- **Perf.** `npm run perf`: draw calls, shadow calls, triangles, shader stages, main-thread CPU per frame section and ms per lockstep tick, with rows tagged by handler. `?prof=1` shows the frame sections live (any build).
- **Atlas.** An internal map of how the code fits together, served at `/atlas/` beside the game (its own page and
  chunks; d3 never reaches the game bundle). Facts are read from `src/` with the TypeScript compiler API on every build
  (`npm run atlas` prints them, [dev/atlas/](../../dev/atlas/)); the explanations live in
  [docs/atlas/](../atlas/) and `atlas.yml` keeps them current daily. Not part of the game.
- **Video.** `npm run clip`, `reel`, `video:changes`, `video:publish` ([dev/video/](../../dev/video/)).
- **Prototype inventory.** `npm run registry -- --json` lists each card's selector, loaders, core seams and incoming
  dependencies (including types). Answered cards with no other experiment importing them are owner-review notes only;
  nothing is archived automatically. The protos page's retired onehand and arrive cards link to their merged game
  features on the classic island; ride links to the wagon, with the destination named instead of a stale Play button.
- **Shipping.** `npm run ship` and self-merging PRs; the steps are in [docs/agents/shipping.md](../agents/shipping.md#shipping), required by AGENTS.md. `smoke.yml` runs the
  nightly live two-tab test; `deploy-server.yml` deploys `server/` when a token exists, on changes to `server/` and to
  what its image carries (`src/world/`, `src/sim/`, `src/net/ids.ts`, `src/net/ws-wire.ts`), since the server runs the
  same rules as the tabs.
