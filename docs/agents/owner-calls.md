## How we work and ship

- <a id="worktrees"></a>**Clean up worktrees diligently** (owner, 13 November UTC, with 55 worktrees left after 93 were removed that hour: "clean up remaining 55 worktrees. we should be diligent about cleaning up worktrees"). Orchestrator's reading: a worktree is removed as soon as its branch lands or its review is read, not at a daily pass: after every ship, remove that branch's worktree and its review worktrees; at each heartbeat, remove anything clean whose commits are all on main; anything unmerged that no running job owns is archive-tagged (`archive/worktree/<branch>`, local) and removed without waiting 48 hours; uncommitted work is preserved in an `archive/worktree/<branch>-wip` tag before removal, never discarded. Kept: the main checkout, `boogle-trusted`, the worktrees of running jobs, and the daily-job checkouts (never touched). This tightens the 7, 9 and 10 November worktree rules in the orchestrate-boogle skill.

- <a id="live-dev"></a>**Development is live** (owner, 13 November UTC, on whether the greybox route should be open in the shared live room: "Yes, I think it should. In general, we should consider this like a live service game where we have a working game and then we're working on something in the background. We're fully in the midst of development and so we should make any changes on the live game so that when we playtest we're seeing everything live and everything that we've progressed on"; then, correcting himself: "we shouldn't consider this like a liver service game*"). Corrected meaning: this is not a live-service game with a finished game in front and work hidden in the background; the game is in full development, so changes go on the live game and a playtest sees everything built so far. Orchestrator's reading: work in progress ships to the live game, greybox and half-made areas included; no flags or private rooms to hide unfinished areas from players unless he asks. It narrows the [10 November blockout entry](../decisions-rail.md#d-2026-11-10-block-out-the-whole-map-then) that kept the walkable layer behind a flag so players can't reach unfinished areas, and extends the 9 November playtest jump-ins note in "One live game" below. It does not lift the binding safety rules (no `WORLD_NS` bump mid-session; reviews before sim, net and server merges). Decision: [the greybox route is open in the shared room](../decisions-rail.md#d-2026-11-13-greybox-route-open-in-the-shared-room).

- <a id="github-outage"></a>**If the GitHub outage holds, migrate checks to local; don't stop shipping** (owner, 11 November: "If the GitHub outage holds, then just migrate checks to local. Don't prohibit us from shipping."). Orchestrator's reading: during a GitHub Actions outage the orchestrator runs every CI job's commands locally on the merged batch (lint, typecheck, build, registry, level-check, `assets --check`, the four unit shards with `--ci`, the server tests, `test:net`), then merges by pull request; the server image boot is skipped without Docker, and the report says so. Used once, on 11 November (batch A, #1598).

- <a id="remove-trees"></a>**The orchestrator may force-remove worktrees to clean up** (owner, 10 November: "you as orchestrator can force remove work trees to clean up"). Orchestrator's reading: once a worktree's commits are verified on main (`git cherry origin/main <branch>` shows every one applied) or its tip is tagged `archive/worktree/<branch>`, the orchestrator removes it and deletes the branch with `git branch -D` without asking. Still kept and listed for the owner: worktrees with uncommitted work nobody has read, ones a live agent holds, the daily-job checkouts and `~/Developer/THAT FRANCO CODE`.

- <a id="fast-ships"></a>**Fast ships: one green run merges; docs skip the build; one proof look** (owner, 10 November: "I want to increase iteration speed, are there any checks that make sense to skip? for PRs?", then to five proposals: "1-5 implement all, yes!"). (1) A docs-only change (`dev/ci/change-class.ts`: prose and docs images nothing builds or tests; anything unknown is code) runs only the docs checks (registry budgets and routes, agent frontmatter), in CI and in the local ship gate. (2) Automerge merges on the first green run when the PR merges cleanly, even if main moved; only a PR whose code files main also changed since its CI gets main merged in and CI rerun. CI on main after every merge is the combination check: red main opens a `red-main` issue, Claude opens a fix PR and `npm run heartbeat` leads with RED MAIN. Conflicts still go back to the branch. (3) A ship branch's pull_request CI runs do nothing. (4) The client gate runs as four parallel jobs. (5) One proof look per player-visible change ([verification](verification.md)). Deliberately kept: lint, typecheck, unit tests, registry, level, assets and build for every code change; server and net tests (and the server image boot check) for code changes and before every server deploy (orchestrator's reading, 11 November: for code changes in their import closure, since a test cannot be affected by a file outside it, and the image boot for the image's paths; `dev/ci/change-class.ts --jobs`; on main the same three are scoped by everything that changed since main's last green run, with every job on a red or unreadable verdict and once a day: owner, 18 November, "Go ahead with scope server idea"); the independent review (its trigger is now "Build more, test less", (c)); the long playthrough nightly. [Pipeline](ship-pipeline.md).

- <a id="no-playtest-hold"></a>**Nothing waits for a playtest** (owner, 9 November: "In general I do not want anything held up for playtest."; "We want to build out as much as possible of the vision and then playtest everything we have whenever I can and make adjustments."). Keep building out the vision: building, merging and starting the next item continue while a playtest is pending. The owner plays whatever is live, whenever they can, and the notes feed adjustments back in. One safety note: don't ship a `WORLD_NS` bump (it resets saves) while the owner is mid-session, if the playdata shows a live session. Replaces "Stop at the owner's playtest" (3 November) and its exceptions. _13 November: the "don't ship a `WORLD_NS` bump" safety note is retired; see [Save resets never block development or architecture](#save-resets-never-block-development-or-architecture)._

- <a id="iterate"></a>**Iterate fast** (owner, 8 November, approving four speed changes). Run independent work in parallel and rebase later, rather than waiting on an unmerged branch, when the overlap is a few files. Codex workers run `test:net` and `perf` themselves through the look broker when their change touches sync, server or performance, so the orchestrator does not redo them by hand. Batch small, finished changes into one ship. Prove each change with short, targeted checks (a spawn-at-the-moment look, an `--eval` setup, unit or server tests); the full `playthrough --long` runs once, as the final pass before a playtest. Brief Codex in pieces of two or three reviewable steps that can each ship, not one job of ten steps.

- <a id="try-early"></a>**Try things early** (owner, 5 November). This early in development, don't wait for the owner's permission to try reversible things: run experiments, prototypes and previz on branches and show the results. Ask first only for a change of direction or unapproved scope and for anything irreversible or outward-facing.

- <a id="no-old-builds"></a>**No old builds in development** (owner, 5 November). Until public playtests, assume every client is up to date when we play; an out-of-date client may hit bugs, and that is accepted. Don't spend work preserving old builds or old saves: no compatibility code, version fences, capability gates, save migrations or mixed-build tests and proofs. Where such code already exists, refactor, optimize or cut it. When a reshape would break the durable world, bump `WORLD_NS` (one line) instead of migrating. Reset the world whenever a change needs it, without asking, unless the owner has said they're in a playtest (owner, 6 November). The server still validates every message, which is room safety, not compatibility. Returning players redownloading unchanged lazy assets after a deploy is also acceptable in development; do not add cache promotion back ([loading contract](../plans/loading.md#a-service-worker-built)). _13 November: see [Save resets never block development or architecture](#save-resets-never-block-development-or-architecture)._

- <a id="latest-tools"></a>**Stay on the latest versions.** Default to upgrading frameworks, tools and runtimes for their features and performance, as long as nothing breaks. A change in feel or download size is something to measure and report, not a reason to stay behind; hold back only for a real break, and say what would unblock it. Prefer a complete upgrade over keeping an old version alongside; a partial step is a stop on the way, with the rest of the path named (owner, 3 November).

- <a id="full-links"></a>**Give full clickable links** (owner, 3 November 2026). When pointing the owner at a page or option, give the full clickable URL, never a bare flag such as `&q=mobile`: he clicks from a phone or iPad and will not type URLs. Link only what is deployed; if the change is not merged yet, say so.

- <a id="fast-coverage"></a>**Fast iteration over test coverage** (1 November). Agents run many tasks in parallel, see their own results and ship by themselves; tests only where lockstep needs them.

- <a id="prototypes"></a>**Prototypes are temporary, but don't clear them out for tidiness.** Don't over-index on their decisions: no design debates about a prototype's internals, and no reshaping core code around one. A prototype still doesn't change fundamental code outside its own scope without saying so. While it's being tested, or other work depends on it, it stays on `main` behind its flag. Once answered with nothing depending on it, it's archived, not thrown away: tag the last commit that has it `archive/<name>`, remove it from `main`, and set `archived` on its card in `protos/protos.ts`. When graduating, the prototype version goes. Clean up what a prototype leaves in core code (a `protoOn` check, a seam, a setting only it uses), and remove code a decision has replaced so nobody takes it for the real thing. A tool for testing real code (`?proto=lay`) isn't a finished prototype.

## Architecture and maintenance

- <a id="security"></a>**Don't over-engineer against attackers** (owner, 14 November UTC, after four review rounds hardened the room-replacement endpoint's rate limits and a follow-up was asked to model address-flooding attacks on the other limiters: "This is a casual game, let's not over engineer for fear of hackers or attackers"). Orchestrator's reading: security work is sized for a casual co-op game. Keep the basics: an operator key that is required, long and never logged; server-side validation so a malformed or forged message cannot crash a room, corrupt a save or wipe one; simple rate limits. Do not spend review rounds or build machinery on determined-attacker scenarios (distributed floods, address minting, lockout races, timing side channels); a reviewer's finding of that kind is logged P3 and not fixed unless it is also something an ordinary player or a simple script could hit by accident. Review briefs stop asking for those scenarios. It agrees with the 6 November note that exploits do not matter, and it does not relax the room-safety rules (a client must not be able to wipe or roll back a room).

- <a id="engine-first"></a>**Engine foundations first** (owner, 13 November UTC: "Keep me posted on the bit ECS spike as that would be the number one priority change as well as the other engine changes so that we can continue building on top of that without having to worry about migrating in the future, like having to do a big refactor because we'll already be building on the right foundations"). Orchestrator's reading: the bitECS decision and the engine unification work (the nine lockstep states onto components, one scheduler, schema-driven saves and replication, the player and seat onto the model) are the number one priority, ahead of new gameplay systems, so new work is built once on the chosen foundation. No ECS library is adopted yet: the spike (branch `codex/bitecs-store-spike`) and the second study (`docs/research/engine-long-term.md`) report first and he decides. Until then, work already built ships (the fourth car, train spacing, Ring Island's crossing), view-only greybox layout continues, and new sim or server systems that would have to be migrated are not started. It sits beside "Playtest before bespoke functionality": both hold, and neither starts new bespoke mechanics. _13 November (owner, UTC, on what he wants from it): "Yeah, what I'm interested is basically having all our models adhere to a system, you know, whether it's ECS or another library that's more like a proper game engine. That way, if there's any models that are implementing that are lesser in quality, they'll still have to adhere to the systems that we put forth."_ Orchestrator's reading: the first criterion for the engine foundation is enforceability: one way to add game state, behaviour and views, which the tooling rejects when broken (lint, schema gates, declared system access checked at run time, scaffolds, tests that cover any new component automatically), so weaker models cannot build outside it. The in-house ECS, bitECS or another library is judged on that first, then on speed and portability. _13 November (owner, UTC, on the options so far; "Bexy" is his dictated spelling of Becsy):_ (a) "I think it sounds appealing to not own the core, and I guess that makes a good case for Bexy. Are there any other alternatives? And if we go with Bexy, does that really put us in a good place to transition to Unity, Unreal, or Godot eventually?" (b) "What I want to avoid is having to micromanage oversight of straying from an established, enforced system and a good engine that follows principles. I don't want to have to invent that from scratch." Orchestrator's reading: he prefers an established, externally documented and enforced system over rails the project invents and maintains itself. That weighs against "build the in-house ECS up to the contract" (the two spikes' recommendation) and for adopting an established library or engine core. He leans toward Becsy but has not decided; no decision is recorded. Research on alternatives and engine portability is in progress (`docs/research/ecs-alternatives.md`, Codex, not yet on main); the spike reports are on branches `origin/codex/becsy-model-spike` and `origin/codex/bitecs-store-spike`. _13 November (owner, UTC, evening, after [ecs-alternatives-live](../research/ecs-alternatives-live.md) ranked Bevy ECS in Rust first and checked Becsy second): "Remind me, adhering to Becsy puts us in a good place in case we need to switch engines in the future right? Becsy seems good compared to having to pull a rust engine."_ Orchestrator's reading: a Rust core is off the table; checked Becsy in TypeScript is his choice of foundation. The orchestrator told him it reads this as the decision and will have the migration planned (plan only, nothing built) unless he says otherwise; if he confirms, record it in the decision log. _13 November (owner, UTC, later the same evening): "Okay, that all sounds good. I think let's consider the Bexy step later, but for now continue with the prefab stuff, etc."_ So: no ECS library is adopted and no Becsy migration is planned now; he will come back to it. The work that continues is the prefab data plan, the server-owned players plan and the rest of the queue. New sim and server work keeps to the in-house ECS facade and the lint rules already on main. Caveats given to him: one maintainer; the access and cycle checks exist only in the checked build, so the checked build is what ships; no serializer, so saves and replication stay ours; for non-ECS engines what carries over is prefab data, rules separate from rendering and server-owned commands, not the library.

- <a id="agents-own-code"></a>**The codebase is the agents' to own** (owner, 11 November, to the orchestrator during the ECS migration: "As you implement architecture remember: this codebase is yours: what it's for and how it's built are your call, and you'll keep building on it."). Orchestrator's reading: on architecture and code structure, decide and build rather than queue a question for him; choose what you would want to maintain, since the same agents build on it next; a planner states its choice and its reason, and lists an owner question only for game direction, unapproved scope or an irreversible or outward-facing step. He said what it is for the same day: "Specifically it should encourage good architecture calls, and code deduplication". So: when a step meets a weak boundary or a second copy of the same logic, fix it in that step or log it as a ranked leftover, rather than work around it or add a third copy; a reviewer treats new duplication and a dodged architecture call as findings; a brief may not forbid the cleanup its own change needs. What the game is (design, copy, direction) stays his, as "Deferring to direction" below says; the engine calls above still guide the choice.

- <a id="tested-engines"></a>**Conform to tested engine architecture** (owner, 6 November: "this is now a serious project"). Prefer the patterns of Unity, Unreal, Godot and published netcode over our own, and justify departures ([6 November calls](../decisions.md#process)).

- <a id="tunables"></a>**Anything playtests could tune is tunable** (owner, 5 November). Give such values one typed, easy programmatic interface for agents, unless it adds large performance or architectural overhead. Shared game-logic values stay identical across a room. Design: [tunables](../research/tunables.md) (in progress).

- <a id="simplify"></a>**Simplify in batches** (owner, 5 November). With many agents merging, run a cleanup pass for reuse, simplification, efficiency and waste (the `/simplify` skill) over recently merged code periodically: in batches, not after every change. The orchestrator runs one after every few code merges or once a working day, whichever comes first, on its own branch, and merges it like any other change. Since 9 November this runs daily as part 1 of the [tidy skill](../../.claude/skills/tidy/SKILL.md) (owner: a "one stop clean up shop to keep things running well": periodic simplify, auditing implicit state machines, docs and memory). _12 November (owner: "I'm also curious if we've been doing slash simplify on our changes that we've made. I feel like we might want to make that part of a routine and overall run slash simplify on the code base changes of the last few days."):_ the last pass was 9 November, `src/render` only (`ca3212d0`, #1248), and nothing since. A pass is owed every working day, and the orchestrator's first heartbeat of a session checks the state file's last-pass commit.

- <a id="research-first"></a>**Research before deep facets.** A facet with real depth (level design, vehicle handling, rendering, construction, pipelines) starts with research into how games solve it: web sources, GDC talks, postmortems, in `docs/research/<topic>.md` with sources and numbered recommendations. Builders cite it.

- <a id="engine-patterns"></a>**Compare to standard engines.** Justify an architecture call by what Unity, Unreal and Godot actually do (their docs), and say where Boogle differs; don't defend a pattern because the code already uses it.

- <a id="deduplicate"></a>**Fold copies into one helper.** When the same small thing has been written several times (like the white-noise buffer, now `src/render/noise.ts`), simplify it into one shared helper when you notice it, as long as it's cheap and doesn't change behaviour. After each batch of tracks, not on a timer, Codex runs a simplify pass over the batch: no behaviour change, checked against a playthrough.

- <a id="research"></a>**Research is fair game.** Learning how existing games solve a problem isn't copying any one of them. No copyright caveats or avoidance guidance in research docs, briefs or repo files.

## Tests and proofs

- <a id="seed-goldens"></a>**Pinned golden fixtures may be regenerated without a `WORLD_NS` bump when only dev seed data changes** (owner, 11 November: "yes"). The seed builders' own op sequences under `src/sim/railway-seed*.ts` may change and `test/fixtures/railway-golden.json` be regenerated (`GOLDEN=1 node --test --test-concurrency=1 'test/railway-golden-*.test.ts'`) with no bump; never for a rule, tick, wire or save-shape change, which still needs a bump. The regeneration changes only the stages whose seeds changed, and an independent reviewer confirms that by a keyed comparison. The rule also sits at the top of [`test/helpers/railway-golden.ts`](../../test/helpers/railway-golden.ts).

- <a id="checkpoints"></a>**Build more, test less; test at checkpoints, swift and targeted** (owner, 11 November: "My goal is that we should be developing and implementing and spending a lot less time testing. That should happen more rarely at bigger checkpoints. And even then, it should be pretty swift and targeted."; the same day, on CI: "evaluate if there's any other sort of CI or tests that we can cut down on or be more conservative with because we're iterating so quickly, and just handle those in later batches"; and "Yes, do 1 through 4" to: ship the unit-suite split first, cancel superseded CI runs on main, batch reviewed branches into one ship, enforce Node 26). Orchestrator's reading, until the [CI diet plan](../plans/ci-diet.md) replaces it with exact gates: (1) a build step proves itself with typecheck, lint and the tests of the files it touched (`node dev/ship-check.ts`), not the full check, bots, looks or `test:net`; a brief asks for nothing more. (2) Proof beyond that (a look, a bot segment, `test:net`, a scenario, the full suite) is run once at a checkpoint, for what the checkpoint changed: the end of a milestone or plan (M12 done, Ring Island build 1 playable), a `WORLD_NS` bump, a change to what loads at startup, or his ask. The orchestrator names the checkpoint and its few targeted proofs when it plans the milestone. (3) Steps between checkpoints still ship as they are built ("Nothing waits for a playtest"); several reviewed branches go in one ship. (4) No new tests beyond the [test diet](tests.md); a conversion or review that would add a slow test shares an existing fixture or adds none. - <a id="place-ports"></a>**Port from Place only what still fits** (owner, 9 November, cutting the gold finds: "We shouldn't just blindly copy everything from place. I think we want most of it, but we should interrogate if it fits into the design still."). Before a Place piece is ported, a designer check asks whether it still earns its place in the live game's design (DESIGN.md, the decision log, what overlaps it already); keep, change or cut, and log the verdict. A plan saying "port" is not that check.

- <a id="spatial-town"></a>**A well-designed town, not a view from spawn** (owner, 9 November, after the Home hall was reworked twice to show the forge from spawn: "im not sure why we're evaluating the view from spawn as the right metric. not everything has to be visible, it just has to be a well designed town spatially"). Judge a place by how it works as a space: how its parts relate, how you move through it, whether it is coherent and to scale. What is visible from one fixed spot, spawn included, is one lens among several and never a pass or fail test; things may be discovered by walking. Don't rework a layout only to raise how much of something shows from spawn.

- <a id="html-first"></a>**Visualize in 2D HTML first** (owner, 6 November). For layouts, upgrade trees, economies, world maps and similar design questions, agents first build a visual HTML page (published as an artifact), iterate on it with the owner, and only then build it in the game: it's much faster to iterate on. Use Codex previz freely for upgrades and new content. Present research and recommendations as visual pages where that helps the owner parse them.

- <a id="physical-work"></a>**Machines show their work physically** (owner, 5 November). Track laying, resources filling up, scaffolding and construction should look physical, even if unrealistic: the gantry picks a rail and lays it, a magazine empties as rails go down, a stack grows as logs arrive. Anything the game counts gets a visible physical form that changes, not just a counter. Build machines from rigid parts with pivots, driven by real game state, and keep the motion readable over realistic. For a machine, plan the motion first with a storyboard of the action's beats and a parts sheet of every moving part, its pivot and its range. Use beauty previz only for the static shell, so a render never fuses parts or freezes a pose. Judge the motion from real-time capture, not stills.

- <a id="gameplay-shapes"></a>**Gameplay shapes the environment** (owner, 5 November). Before dressing an area, decide what it is for: somewhere players should go, a view, a boundary or a route. Make the forms and materials say it: walkable invitations read clearly, and barriers read as "not this way" without invisible walls. Previz is a reference, not a target: be smart and tasteful rather than matching the pictures.

## Performance and devices

- <a id="no-limits-ahead-of-a-measured-problem"></a>**No limits ahead of a measured problem** (owner, 14 November 2026, asked whether to raise the prefab record ceiling from 200 to 320: "yeah, we can raise the record ceiling. I don't know why we have these weird limitations for these things. We should only lock them down when we encounter performance issues"). Orchestrator's reading: budgets and ceilings on content (catalogue records and bytes, counts of props, placements, draw or triangle budgets written as test failures) are not set in advance. A limit is added only where a performance problem has been measured, sized from that measurement and citing it. Until then tests REPORT the numbers, so growth is visible in output and reports, and fail only on real defects: duplicate validation, unbounded growth by accident such as a record duplicated per placement, or a stale artifact. This sits beside "Place for the look, not the cost; terrain may change" below; it supersedes the prefab 200-record / 350,000-byte ceilings and the consolidation report's proposed 320-record replacement.

- <a id="frame-time-60"></a>**Frame time is the measure; the target is a stable 60 fps on every platform** (owner, 11 November: "frame time should be an important measure. we want to target a stable 60fps across platforms if we can"). Perf work reports frame time (median and worst frames) before and after, on the Mac, on Windows and from a device run where one exists; triangle and draw counts explain a result but are not the result. The orchestrator's reading: this sets the target for the performance pass and for reports; it does not undo the call above, so a number still never blocks or shrinks a feature. **Low priority for now** (owner, later on 11 November: "frame time pass should be low priority right? the game runs fine for now and there's a lot to develop. we can also test frame time relatively quick with abridged tests"): measure with a short reading (three poses, about 20 s each) when a change warrants it; queue no perf jobs unless something visibly runs badly. The first reading (HOTBOX, RTX 3080, 2560x1440, main `bace9b951`) held the display rate at the village green, Far Head and the Ring Island halt; Far Head has the least headroom (12 ms CPU, 14.6 ms GPU).

- <a id="on-demand"></a>**One nightly load; perf on demand; atlas and patch video off** (owner, 10 November: "Let's disable the patch video automation for now since it uses a lot of usage and we don't need it right now. We can disable Atlas for now as well and perf and scenarios should maybe just be one load. I don't think perf needs to run all the time. Maybe just in specific circumstances"). Supersedes the daily cadence of "Measure performance daily" below; its method (fixed bench, history, a reasoned mitigation per regression) stands. Orchestrator's reading: launchd runs only `scenarios` and `long` (`scheduled` in dev/daily/jobs.ts). The orchestrator runs `npm run daily -- perf` on a quiet machine after a merge that could cost frames (rendering, materials, world size, draw calls), before a `WORLD_NS` release, when a session or the owner reports slowness, or on request. Atlas and patch video run only when the owner asks.

- <a id="performance-guides-not-gates"></a>**Performance guides, it doesn't gate, until he calls the pass** (owner, 10 November: "By the way, at this stage of development, it's good to be efficient, but we shouldn't let any just strict number of triangles or assets or frame rate deter implementing features. We will always converge for performance later in the development process, once we have our gameplay running as intended. im just calling it out since in the past some of my decisions have been interpreted too strictly around performance"). At this stage performance numbers (triangle, draw-call and asset counts, frame rate, budgets) guide work but never block or shrink a feature. Build the gameplay as intended, be sensibly efficient (instance what is placed by the hundred, share materials, skip hidden faces), measure and report the cost, and leave convergence on performance to a later pass he will call. A regression found in passing is still reported, and fixed when cheap. How to apply: a brief sets no hard cap that cuts a feature's scope (a count or frame time is a target to report against); a reviewer does not send a feature back for exceeding a budget alone; a plan that drops or defers gameplay "for performance" needs his word first. This does not relax correctness: lockstep determinism, crashes, stalls a player feels as broken and the "not tested on a device" line stay as they are. Narrows "The Mac and mobile are the targets", "Geometry budgets follow prominence" and "Measure performance daily": their numbers are guides until the pass. **Asset sizes warn (owner, 10 November),** answering a list of size limits enforced in code (an asset over 4 MB or a texture over 2048 px failed the asset build; first load over 25 MB and total over 100 MB were flagged): "asset over 4mb shouldnt necessarily strictly fail. same with manifest flags. texture seems reasonable for a mobile playable game", and then, of the texture cap, "texture should also be just a warning". So no asset size or texture size limit fails a build now; all three warn: an asset over 4 MB (or its sidecar's `budgetKB`), a texture over 2048 px, and first load or total over their totals. `npm run assets -- --check` and the build print each warning with the name, size and limit and end with one summary line counting the assets over a target, and still emit the asset as authored. Stale or missing outputs and a non-KTX2 texture over 256 px still fail `--check`.

- <a id="geometry"></a>**Geometry budgets follow prominence** (owner, 6 November). No flat size cap for props. Give each asset bytes and triangles according to how prominent it is: a hero piece the player stands beside or watches for minutes gets far more than scattered scenery, and anything placed by the hundred is instanced and lean. The test is whether the geometry is efficient for what it is: no triangles the silhouette or close-up doesn't need, no hidden faces, shared materials, and LODs where it is seen from afar. Big geometry is fine once loading can stream it, loading and unloading by area and distance, so the real limit is what is resident at once on the Mac and on mobile, not the size of the whole catalogue. The numbers in the [asset pipeline](../plans/asset-pipeline.md) are defaults to revise, not caps. _(Narrowed 10 November: triangle and asset counts guide and never cut a feature; see [Performance guides, it doesn't gate](#performance-guides-not-gates).)_

- <a id="perf-method"></a>**Measure performance daily** (owner, 6 November). Performance is measured actively, at least once a day, not only when a phone feels slow: a fixed benchmark on the Mac with history, so a regression is caught the day it lands. Each regression gets its reasoning (what change, why it costs), a mitigation, and where it repeats, a systemic optimization rather than a one-off patch. Mobile scales down from the Mac results. _(Narrowed 10 November: the benchmark measures and reports; a number over budget is a finding for the later pass, not a reason to block or shrink a feature, and a regression is still reported and fixed when cheap. See [Performance guides, it doesn't gate](#performance-guides-not-gates).)_

- <a id="mac-mobile"></a>**The Mac and mobile are the targets.** An M1 Max is the average; judge looks and budgets on the Mac the agents run on, and let mobile scale down, though it still has to run there. The owner tests on several devices, so don't check every device each time. In a report, one short line is enough: "not tested on a device" (owner, 2 and 3 November). **A device run replaces that line** (owner, 10 November, asked whether a report may cite a device run instead: "Yes"): when `npm run device -- pull` has produced a report (`.look/device/<id>/report.md`) of a build that contains your change, paste its first line ("Tested on a device: ...", which carries the run code, device and build) and say what it covers. It covers only what the suite measures: load, and frame times and counts in its scenes (spawn, town, forge, bay, pier, head). A change outside those scenes, or to feel, input, audio or two-player behaviour, still says "not tested on a device"; so does a change with no run of its build. Use the newest run for the area when one exists; never cite a run you have not read. [Plan](../plans/remote-device-tests.md). _(Narrowed 10 November: the budgets judged here guide and do not gate a feature; see [Performance guides, it doesn't gate](#performance-guides-not-gates).)_

## How the owner works

Standing preferences from the Boogle 2.0 design thread (1–2 November), moved here from the decision log on 8 November. Where a dated standing call above differs, the later call wins; those are marked.

- <a id="right-over-less-work"></a>**The right solution over less work** (owner, 16 November 2026, offered two ways to fit the riders' coach at Home with the smaller one recommended partly for being "a fraction of the work"): "If it's the right solution, let's not shy away from the work". Orchestrator's reading: when options are put to him, judge and recommend them on which is right for the game; give the size of each as a fact, never as the reason to prefer one. It does not say the larger option is the right one.

- <a id="player-count"></a>**Tune for 1–3 players** (owner, 6 November: "really tuned to 1 to 2 to 3, maybe 4 people, unlikely more than that"). Design and tune for one to three; four must still work; don't design for more.

- <a id="feel-first"></a>**Feel first.** "Game feel is tantamount." Every interactive thing gets a feel pass before it gets rewards.

- <a id="ambition"></a>**Think ambitiously.** Early mocks were "too simplistic". The owner wants clear technological stratification between eras, a bigger island, and a city.

- <a id="likes"></a>**Likes:** vehicles, exploration, construction you can watch, goofiness, Palworld's take on materials.

- <a id="grinds"></a>**Wary of:** material grinds.

- <a id="narrative"></a>**Collaborators may write the narrative.** Don't lock story details in alone. Draft options for them to react to.

- <a id="pick-pages"></a>**Decides through HTML pages with pick buttons.** The concept page ends with a round of questions and a copyable summary. Keep its localStorage key `boogle-2-v5`: changing it wipes the owner's picks. Playtest feedback works the same way: tap answers on a page Claude can read, as in the [Round 4 Replay](https://claude.ai/artifact/TAb4PhNz2E9g1DiZD5bHoF) (private to the owner).

- <a id="mechanics-first"></a>**Mechanics before narrative.** Find the fun in the core loop and its feel first (1 November). Story, characters and gags come later and are easy to fill in. Don't commit to them before the loop works.
