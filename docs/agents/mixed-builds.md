## Mixed builds
Tabs reload onto new deploys (`src/features/updates.ts`), but a visible tab waits until hidden, so rooms mix builds for a while. Wire changes are additive (new ops, states, presence keys, message types; old tabs ignore them). Never change an existing one's shape or meaning without a version: a state's `version` + `migrate`, or a new name.

**Dev phase (until public playtests), owner call "No old builds in development":** assume every client is current; an old tab may hit bugs, and that is accepted. Write no compatibility code, version fences, capability gates, save or localStorage migrations, or mixed-build tests, and cut such code where you find it. To remove or reshape ops, states or catalog entries, bump `WORLD_NS` in `src/world/namespace.ts` in the same commit with a dated history line, so the durable world starts fresh instead of being migrated; `npm run registry` skips its mixed-build comparison after a bump. The server still validates every message and must not crash on malformed input (room safety). The rest of this page applies after public playtests start.
