## Rules learned

Active uncodified operational rules (rules already in skills or code live there; historical rules 1–84 are archived verbatim in [the log](orchestrator-log.md#28-november-state-file-pruned-rules-1-84-archived)).

1. **Shared rule constants are mixed-build changes:** a constant the server checks (reach point, position) ships web minutes before server — note it in the ship or land server first.
2. **Never pipe `ship-queue` to `| tail`:** it hides the exit code. Log to a file, grep narrowly, and read each open ship PR (`UNSTABLE` = failed check, `DIRTY` = conflict) before ending a turn.
3. **Runtime & tool paths:** use Node 26 (`v26.13.0`); run focused tests with `UNIT_ONLY="<file> <file>" node dev/test-unit.ts` (space-separated, not commas or bare args); on HOTBOX set `BLENDER="/c/Program Files/Blender Foundation/Blender 5.3/blender"` for asset work.
4. **Worktrees & branches:** never `git stash` (`refs/stash` is shared across worktrees); check `git log origin/main..HEAD` before shipping a delegate branch; check `ps -ef | grep ship-queue` before moving/removing a clean worktree; check `git diff --name-only origin/main...<branch>` before filling a slot beside a running job (fix rounds widen past the row).
5. **Checks `ship-check.ts` skips:** briefs touching `src/place/land.ts` (or `dev/level/grounding-props.ts` bindings) ask for `npm run level-check`; briefs touching `server/src`, `src/sim/railway-seed*.ts`, or seed goldens ask for the full `server/` suite (plus `npm run test:net` for seeds).
6. **Boot probe for new lines/trains/halts:** adding to `RAIL_LINES`, `RAIL_TRAINS`, or halts requires `vite build` + `vite preview` + `dev/live-boot.ts --offline` PASS (on HOTBOX launch with `channel: 'chromium'` for WebGPU).
7. **CI timeouts & slow runners:** CI runs `server/` tests with `RAIL_AUDIT=1`. On a 15-minute cancelled `server` job, compare per-test timings with main before starting a fix round (~4x slower across the board = rerun failed jobs once). Unit tests that time out under load get `{ timeout }` at the source (marked `read` by `review-stamp`).
8. **Look harness:** solo looks warp ~12x while server is real-time (wait on server ticks); two-player warp needs `--warp-speed 2`; reload checks need `--real`; on HOTBOX Chromium's frame interval floors at ~18.2 ms even blank (judge perf on CPU/GPU ms); never edit files while a bot run is in flight; commit at most ~16 curated 1200 px stills beside the plan/report (never under `.look/`).
9. **Codex child guardrails:** Codex briefs state nobody can approve prompts — no `Start-Process`, `taskkill`, or `Remove-Item -Force`/`rm -rf` outside `.look/` (the look harness starting its own servers is allowed). Every run/wake checks `t3_thread_read` for `pendingRequestCount > 0` or 15 min idle, and re-reads running threads once more before closing.
10. **Wakes & follow-ups:** a delegate's report wakes the thread that started it (when sending a fix into another session's thread, schedule a ~20 min one-off follow-up). Every follow-up prompt ends: *"If a delegate's report wakes this session, act on that job as a wake does; start no new backlog job."* When a later hourly run has started (`t3_thread_read`), an earlier run's wake handles only its job and leaves bookkeeping/slots to the newer run.
11. **Sim/server verification traps:** every new op needs a real `r:edit` host test (not just `apply()`); new ops/marks join `GENERIC_OPS`/`ACTIVITY_MARKS` in `dev/loop/graph.ts`; prompt/card/grant changes update bots (`dev/look/bots/railway.ts`, `coop-unlock.ts`) and seeds (`railway-seed-route.ts`); input-taking overlays check `inputState.held`, not just `momentBusy()`.
12. **Doc budgets:** `owner-calls.md#index` caps at 6,000 chars (nearly full); task-route must-read budgets cap at 14,000 chars (`tests.md`, `sync.md` are near the cap — do not grow them).
13. **Backlog & claim hygiene:** moving a row's rank deletes the old row in the same commit; an owner answer that unblocks a row updates the row in the same ship; check the topic's Current rules before briefing; delete stale "Jobs in flight" rows when a branch merges.
14. **Property tests & probes:** keep default property-test runs under 25% of CI's budget on HOTBOX (CI runs ~3x slower); check bounds across 24–48 seeds before claiming a limit holds.
15. **Playtests & artifacts:** an orchestrator tab on `boogle.club` logs as a play session; artifact stores return read-only objects (copy before mutating); search `docs/brainstorms` and `docs/plans/town-layout.md` for the owner's terms before saying something is not planned.

## How merging works

`npm run ship-queue -- <worktree> --wait [--reviewed "<stamp> <who, what they found>" | --orchestrator-read "<what changed>"]`, in the background, one branch after another ([orchestrate-boogle skill](../../.claude/skills/orchestrate-boogle/SKILL.md), "Merge"). The gate prints the stamp or read flag it needs and finds Node 26 itself. Keep merging while the owner plays: live deploy handles deploys and `WORLD_NS` bumps with players on ([live-deploy](../plans/live-deploy.md)); hold only when the owner asks.

An independent review (`--reviewed`) is required only for what `npm run review-stamp -- <worktree>` marks `review` (desync/save-loss paths: `server/src/`, `src/net/`, `src/world/` wire/sync/replicate/namespace/rules/server-ops/game-world, golden fixtures, and review-path test assertion changes; [faster reviews](../decisions-process.md#d-2026-11-28-faster-reviews)). Work marked `read` (docs, `{ timeout }`-only or skip/import/move test edits, and standalone `src/sim`/`src/ecs`/`src/world` refactors or queries with unchanged goldens and assertions) ships on the orchestrator's read with `--orchestrator-read`.

On the Mac `../boogle-trusted/node_modules` symlinks to the main checkout's node_modules, and an `npm ci` there empties it; on HOTBOX it is its own install. Reinstall with `npm ci` in the main checkout if `node dev/playtest/cli.ts` can't find playwright.

The Codex sandbox cannot launch a browser: the orchestrator runs `npm run test:net` in the job worktree itself; do not treat a sandbox launch failure as a network regression.
