# Room-owned time after T1

_5 November 2026. Research and implementation proposal, not an approved gameplay decision. Base: `10dc567b81367d792e8a0bb59668e5d2101e3a66`. Read-only comparison with `codex/production-core-slice-2` at `cb3429992aadffbb559588db3988bf78a7986bbc` and `codex/color-defaults` at `08a2056aae6e3dcb823f0e302069566cf9d5b32a`. Live primary-source research and focused code inspection; no implementation or runtime experiment. **[V]** inspected source/decision; **[H]** earlier recorded evidence, not rerun; **[D]** recommendation; **[E]** planning estimate. Night is out of scope._

**Give the room one durable, bounded day → evening → day sequence, driven by accepted construction facts, and let each renderer present its current endpoint.** Build the authority seam after T1; connect it to Station 3 only when production slice 3 owns that completion. Prefer returning to daylight when line 2's first construction becomes fully funded and starts, subject to the owner's unanswered brief. A small lamp on the sign is the leading readability fix at gain **0.12**. No calendar, automatic cycle, attendance check, timer-based daylight return or time-gated activity is needed.

This serves [DESIGN.md](../../DESIGN.md)'s **Designed for drop-in, drop-out**, **Leave something for the next visitor**, **Show, don't tell** and **Clear authority**. Disposition: **prerequisite first**. This report does not approve the first-evening milestone or camera change, establish that T1 is accepted, or authorize work beyond the owner's current gates.

## Smallest state and writer [D]

Proposed names below are implementation targets, not existing APIs. Register one versioned state, **`roomTime`**, containing just:

| Field    | Domain                   | Meaning                                                                                                                                                                                                                                                     |
| -------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `step`   | integer `0`, `1`, `2`    | `0`: initial day; `1`: first evening; `2`: returned day. Logical phase is `step === 1 ? evening : day`. This monotone sequence distinguishes the two day states and makes an old completion unable to retrigger evening. It is not a third lighting preset. |
| `atTick` | nonnegative safe integer | Authority apply tick of the most recent step; initial `{step:0, atTick:0}`. Supplies fade age and transition identity together with room identity and `step`. Never a wall timestamp or “time since this tab joined.”                                       |

No separately saved `phase`, `from`, transition progress, duration, `seen`, attendance, lamp boolean, sky settings or reward fields. The preceding look follows from the ordered sequence. Keep the existing authored fade durations as Local constants; a later need for multiple transition recipes warrants an explicit versioned extension, not a catalogue now. Validate exact integer domains, reject `NaN`/negative zero, and cross-check `atTick <= snapshot.tick` at the snapshot boundary.

**Writer:** the server's production-room coordinator detects accepted milestone predicates after the owning rules' ticks and requests a single host-only **`time.advance`** op. Its payload is the desired step; apply stamps `atTick` from its supplied authority tick. Clients cannot choose a phase, send a time request through presence, or turn a local preview into a milestone. All replicas apply the accepted edit deterministically through the existing sync pipeline.

Keep at most one pending advancement in the coordinator. Validation and apply both check the current step and accepted facts: reject forged/unjustified targets, treat duplicate or superseded stamps as harmless no-ops, and let the next after-tick reconciliation schedule the latest valid target. Return accepted-change information; apply performs no rendering, sound or inventory work. This tiny op is preferable to a browser milestone callback: it gives the transition tick the same publish-after-durable guarantee as T1. Merely changing phase in a render callback or unjournaled server timer would leave a crash window.

Suggested owners: pure descriptor/validation in a small `src/sim/room-time.ts`; registration and read API in `src/world/rules/room-time.ts`; append in the playable railway registry; host reconciliation beside `createRailwayWorldHost`; a mount-owned adapter alongside `src/adapters/railway.ts`. Follow [sync](../agents/sync.md), [room safety](../agents/room-safety.md), [lockstep](../agents/lockstep.md) and the inspected nested AGENTS. No new transport or frame loop. Reuse the branch adapter's single-router/disposable-listener pattern so remounts do not multiply callbacks.

## Save, crash recovery and quiet restoration [D]

The new state joins the **same** snapshot/hash and bounded recovery envelope as construction; there is no separate room-time file or browser save. `time.advance` uses the existing durable stamping barrier. If disk write fails, do not publish the new time or present a successful transition. Preserve the last good save and expose the existing recovery failure behavior.

At startup: validate checkpoint → replay durable tail in stored order → apply the existing bounded funded-work catch-up → reconcile time from resulting accepted facts → durably stamp and apply any time advancement behind the startup barrier → durably checkpoint → serve the ready snapshot. `whenDurable` alone does not mean a future-tick edit has applied: drain its due tick before initial room reveal. During a running empty room ordinary ticks may finish funded construction. During eviction/server downtime only already-funded work may complete. Do not count offline hours toward a time-of-day cycle, auto-fund Q1 or commission an unfunded forge. Repeated startup with the same resume marker must produce no second advancement.

| Interruption                                                   | Required result                                                                                                                                                            |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Crash after construction completion but before scheduling time | Recovery reconstructs the accepted progress; startup reconciliation durably advances time before serving a ready room. No client has been promised the missing time stamp. |
| Crash after time publication, before periodic checkpoint       | Durable tail restores the exact accepted step and `atTick`; no second trigger or reward.                                                                                   |
| Crash while replacing checkpoint or upgrading save             | Last complete envelope remains recoverable; never serve a fresh day world over failed saved state.                                                                         |
| Reload, late join, resync or return from background            | Read the latest verified descriptor; initialize its target endpoint directly, including when the room is mid-fade. No repeated fade, whistle, camera or personal reward.   |
| Disconnect while playing                                       | Hold the last accepted look; no locally earned progress-driven time. On reconnect reconcile from verified room state quietly.                                              |
| New room                                                       | Day, step 0. An absent field in a known older format is a migration case; a malformed current field is corruption, not permission to reset.                                |

The late-join choice follows the brief literally: the newcomer enters evening immediately, not at the start of the old fade. Incumbents may still be behind their veil. Shared **logical phase** agrees at a common verified tick; subsecond presentation and network arrival are not promised frame-identical. Presentation history is not durable state.

### Recovery upgrade is a prerequisite, not a default initializer

[`restoreRecovery`](../../src/world/sync.ts#L718) checks exact key counts and versions **before** loading registered state. Its whole-checkpoint hash and envelope checksum also cover the old representation. Therefore adding `roomTime`, or bumping a state's version and supplying only `migrate`, fails this path today. Do not weaken these guards or fill defaults before verifying old bytes.

Recommend a bounded **v1 → v2 recovery-envelope upgrade** at the existing recovery owner, preserving `t1v02` room identity and balances. Validate the known v1 registry, checksum and old hash using its old rules, replay its tail with old semantics, then convert the resulting complete state, append initial `roomTime`, and atomically write a newly hashed/checksummed v2 checkpoint before readiness. Preserve sequence numbers, roster/account identities, claim-related data, material counts and the consumed offline marker. Catch-up then runs once under the upgraded contract. A startup crash at every boundary must leave either the old valid envelope or the new valid envelope, never half of each. Retain recoverable original bytes while the upgrade is being validated.

Preserve offline accounting across that upgrade too. Compute the outstanding bounded absence from the original saved timestamp/tick and replayed resume marker before replacing the envelope. Durably carry the normal `rail.resume` descriptor or equivalent unconsumed baseline through the replacement until catch-up applies. Simply timestamping an upgraded checkpoint “now” can discard funded offline progress; retaining an old timestamp without accounting for tail replay can consume the interval twice. Include both failures in upgrade/crash tests.

For today's T1-only saves, initialization is unambiguously step 0: there is no line-1 milestone to backfill. If integration lands after later production facts, derive the matching step quietly and use the migration checkpoint tick as `atTick`; label it an initialization anchor, not an invented historical completion time. Do not replay a celebration. Unknown newer versions, unknown registries or bad checksums stop loading; no generic best-effort field stripping. Old server binaries must refuse v2 after upgrade, not overwrite it during rollback. This is one explicit production save upgrade, not a general migration framework.

The [approved production plan](../plans/production-core.md#approved-scope-record) already requires preserving accepted production progress after its initial clean break. A further disposable namespace reset is therefore **not** the default shortcut. If the owner explicitly chooses one, change the actual playable railway namespace/router and dated history as well as any applicable `WORLD_NS` contract; do not import prototype localStorage or delete old saves.

## Late assets and mixed builds [D]

Network compatibility and disk compatibility are different proofs. The normal [`sync.ts` hash comparison](../../src/world/sync.ts#L489) can compare common state keys, while recovery requires the upgrade above. Append the new state/op; do not alter the meaning of existing railway edits. Preserve [mixed-build rules](../agents/mixed-builds.md).

| Combination                                   | Expected behavior and limit                                                                                                                                                                                                                                                 |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New client + new server                       | Same descriptor at the same verified tick; ready skies initialize directly, later accepted changes fade.                                                                                                                                                                    |
| New client + old server                       | No advertised/registered room-time state: remain day and do not synthesize an evening from prototype progress. The server never accepts a client time command.                                                                                                              |
| Old client + new server                       | Old client ignores the additive unknown state/op and retains its day presentation; existing interactions/material rules must remain valid. | New client, prepared assets delayed or failed | Keep the latest descriptor pending; bind only the newest target when ready. If “everyone, including indefinitely open old tabs” is mandatory at rollout, add explicit minimum-build admission/reload handling in the owning room interface; additive state alone cannot provide that. Future time-dependent gameplay is a separate gate and cannot rely on cosmetic fallback. No such gameplay is part of this plan.

## Connecting the prepared renderer and the sign lamp [D]

Keep [`setEveningLook`](../../src/render/water/evening-transition.ts) as the presentation entry, but extend its contract deliberately in implementation:

1. **Preparation and initial restore.** Enable the two prepared endpoints for the supported production room independently of the URL preview. Read room state and prepare behind existing loading; immediately before reveal, select the newest verified target directly. Provide a snap mode on the existing seam/controller instead of simulating a fade during startup. Await sky bake, fill readback, filtered maps and their first-use readiness. No runtime bake when the milestone fires.
2. **Live transitions.** Observe a newly accepted `time.advance` through the adapter; compute age from the synchronized tick (`100 ms` per tick) plus Local render interpolation. Pass age/identity to the seam so delayed delivery does not start a full old fade. Retain the authored 0.45/0.65 s cover/reveal and a rendered opaque exchange; seek or settle expired events. Do not mutate the authoritative anchor to satisfy a slow frame. The extension is required: today's API cannot do this.
3. **Interruption and re-entrancy.** Maintain one latest desired target, not a FIFO of fades. A busy/unavailable false return is not acknowledgement. When return-to-day overtakes evening, cancel/retarget under cover or settle directly on reconciliation; recheck identity at asset-ready and swap boundaries. Clear veil/listeners on disposal. No repeated polling writes, callbacks from a disposed sea or replayed completion sound.
4. **Coherent selection.** The existing private `select` already exchanges raw sky sampling, filtered environment, direction and fill. Use that same selection boundary for the sign lamp's visible dusk state and the Local evening-look query. Keep sky, fog, water/underwater/snow, key and hemisphere coherent; retain the fixed-exposure pipeline, one sea lifecycle, one output and input throughout. Do not drive lamps from `skyNow.day`, which remains 1 in the preview.

The current veil leaves input live but covers the screen. Test a distant friend jumping, gliding or riding when another finishes the crossing; cosmetic does not mean the view interruption is harmless. The owner's camera decision remains separate. If the prepared fade makes traversal unpleasant, stop for that bounded presentation decision; do not add attendance voting or pause the world.

### The 0.12 lit-sign regression is a required integration case

The base checkout still has compensated unlit boards and documentation for gain 0.16. The inspected [color-defaults boards](https://github.com/matiasfr/boogle/blob/08a2056aae6e3dcb823f0e302069566cf9d5b32a/src/proto/place/signs.ts) use rough `MeshStandardNodeMaterial` with no inverse-gain/emissive floor; its [exposure settings](https://github.com/matiasfr/boogle/blob/08a2056aae6e3dcb823f0e302069566cf9d5b32a/src/render/exposure.ts) set 0.12, and its water notes apply key 1.12/fill 3.2 to both endpoints. The brief reports much darker evening signs. Earlier [evening verification](../game-design/water.md#evening-verification-5-november) at 0.16 with the old boards does not clear this new combination. I did not independently reproduce its darkness here.

Recommend **one small warm sign lamp**, physically above/in front of the board, enabled by the selected evening endpoint. Preserve painted ink, rough paper, fixed gain 0.12 and underwater offset; do not brighten the whole evening or revert the sign to uniformly unlit. Begin with a short-range unshadowed source through [`addLightSource`](../../src/render/lights.ts), reusing the existing two-light pool. Position and beam coverage matter more than arbitrary high intensity. Choose actual intensity/range from matched readable views; this report supplies no measured values.

That pool scores sources by intensity and camera distance and keeps only two. A forge or nearby lamp can evict the sign lamp; the Graphics option can disable the whole pool. An emissive bulb alone does not light the board. Prove readability at the interaction/approach distance with two competing sources and with lights disabled. First try placement and local fill; if the board remains essential and unreadable, propose a narrowly scoped board-lighting fallback or justified priority rule to the graphics owner. Do not claim a third persistent/shadowed light is free, silently expand the pool, or alter every sign's material. `addLightSource` currently has no remove handle: an owned sign must disable its source on teardown and avoid duplicate registration, or receive a small unregister contract in the lamp task.

Inspect day, evening, return and late-join evening at Station 3, the sign close-up, shore, town, indoor boundary and waterline; check rewards and particles too. Record exposure, active pool sources and visible board text. Keep signs independently readable even though different cameras can select different local lamps. Smaller 512/256 sky comparisons belong to the existing sky-quality work; do not silently change the accepted 1024 baseline. [Earlier cube-memory arithmetic](water-times-of-day.md#allocation-arithmetic-not-measured-browser-residency-le) is a planning model, not new residency evidence.

## Implementation order and smallest proof [D/E]

1. **After T1's required technical acceptance:** bounded descriptor/op, host reconciliation, playable registry and the recovery upgrade. Prove with isolated fixtures, leaving real rooms in day. No dependency on new art or T3 implementation for this authority proof.
2. **When production facts and the brief's choices are ready:** map slice-3 completion and the selected slice-4 return fact; integrate ready/snap/seek behavior at the existing evening seam and the sign lamp. Keep the day/evening comparison separate from shared gameplay truth.
3. **Before activation:** run the matrix below, inspect evidence, then the owner's gut question: “Walking home, did it feel like you'd finished something, or like the game had ended?” Stop for that verdict. Do not add night or repeat the pattern across the campaign.

Planning allowance: roughly **2–4 focused days for authority/recovery and its proofs**, then **1–3 for renderer/lamp integration and evidence**, excluding upstream milestone promotion, device access and owner iteration. These are estimates, not measurements. The recovery-version seam makes this materially larger than just wiring a callback.
