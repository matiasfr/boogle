# Make every Boogle control describe itself once

*2026-10-29. How to clean up the controls guide and add a pause view: a codebase audit at 266cf32, pause and controls-guide patterns from other games, action registries in engines and on the web, and visual presentation. Nothing was run in a browser. Since then, main has given every control a pad slot and added `wrapAction` (7d736ce), so treat the slot counts and the feel.js monkey-patch below as history.*

Boogle's controls guide is broken less by its look than by its plumbing: a single control is described in up to seven independent places (a key handler, a hand-written help row, a `registerAction` label, a touch button, its CSS position, a glyph table entry and the README), so the guide has already drifted, and there is no pause view at all. The fix is to grow the existing registry in [src/player/controls.ts](../../src/player/controls.ts) into the one description of a control (label, group, order, display keys, optional context) and *derive* every surface from it: the keyboard guide, the gamepad card, prompt glyphs and a test that fails when a control is missing. On top of that, add a pause view that is a **local overlay over a world that never stops**, opened by pointer-lock loss on desktop, Menu on the pad and a top-corner button on touch, built as a `<dialog>` that reuses the input-capture pattern The Boogler's talk box already proved. Visually it should speak the game's existing "paper sticker" dialect with the `.g-*` glyphs everywhere, instead of the translucent always-on 18-row panel in the bottom-left corner. Rebinding and settings stay out, but the schema keeps keys as data keyed by action id, so rebinding later means changing who dispatches keys, not rewriting the guide. The work splits into three shippable phases plus a deferred fourth, each a plug-in feature or a small shared module, with no new dependencies.

## One control lives in seven places, and the guide already drifted

The audit (taken at commit 266cf32) found that "the controls guide" is three unrelated things. Desktop players get a static `#help` panel of 10 `<kbd>` rows in [index.html](../../index.html), shown by default whenever `body.playing` is set and toggled with H. Five features then append 8 more rows by hand, two of them via `innerHTML` strings and three via `createElement` loops, for **18 rows in feature-filename order**, which is why "H Hide these controls" sits mid-list and E, the main interact key, appears after V and T ([src/main.ts](../../src/main.ts), [src/loop.ts](../../src/loop.ts)). Gamepad players get a different `.pad-card` generated from `listActions()`, shown for 6 s on first pad use and toggled by Menu ([src/features/gamepad.js](../../src/features/gamepad.js)). **Touch players get nothing**; the help panel is excluded with `:not(.touch)` and the pad card is pad-only ([src/style.css](../../src/style.css)).

Only the pad card is derived from data, because `registerAction(id, { pad, label, down, up, held })` knows a pad slot and a label but no keyboard key, touch button, group or glyph. Every other list is hand-kept, and they disagree. The static rows still say Click is "Use what you hold (empty hands: same as E)" although commit b22fa8b changed what E and click do. Dig and pile are described twice (index.html's shovel rows and [src/features/shovel.js](../../src/features/shovel.js)'s Q/Z rows). The E row is added by [src/features/hotbar.js](../../src/features/hotbar.js) even though [src/player/input.ts](../../src/player/input.ts) owns the key. Dive (Q while swimming), mouse-wheel zoom, Esc and drag-look are missing entirely, and [README.md](../../README.md) still says "Click grab" and omits E, T, G, V and 1-8. The keyboard handlers are just as scattered: T, G, V, Q and 1-8 each add their own window `keydown` listener with a different typing guard. Honk and ping check the name input, hotbar checks the tag name and `me.entered`, bump checks focus but not `me.entered`, and the dive listener in [src/features/feel.js](../../src/features/feel.js) checks neither.

The uncommitted working tree has already fixed part of this, and the report should not scold edits that are in flight. The diff in [src/features/bump.js](../../src/features/bump.js), [src/features/feel.js](../../src/features/feel.js) and [src/player/input.ts](../../src/player/input.ts) gives bump a pad slot (RT) and so closes the audit's one violation of AGENTS.md's "every control is playable on a Backbone-style gamepad" rule. It drops the separate pad `dig` action (dig is X with the shovel in hand), moves flatten to D-pad up and collapses zoom into one R3 action that steps close / middle / far. That leaves **two free slots (`down`, `right`)** instead of one, though `right` is still borrowed by the update toast ([src/features/updates.js](../../src/features/updates.js)). Two problems survive the diff. Bump still appends a hand-written V row, and feel.js still monkey-patches a registered action's `down`/`up` so that it dives while swimming, now on `pile` instead of `dig`. That monkey-patch matters beyond tidiness: with 14 of 16 slots taken, context-sensitive slots are the only way new controls will fit, and today the guide cannot see them (the slot keeps saying "Pile sand"). The recommendations below therefore do not depend on the exact slot map.

## Grow `registerAction` into the single description of a control

Every mature input system splits an action's identity and display metadata from its per-device bindings, then generates prompts by asking what the action is bound to on the active device. Unity's `GetBindingDisplayString` resolves the text from the binding rather than from the UI ([Unity manual](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/manual/ActionBindings.html)), Unreal's mappable-key settings carry a save `Name`, a `DisplayName` and a `DisplayCategory` ([Unreal API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/EnhancedInput/UPlayerMappableKeySettings)), and Steam Input resolves glyphs from an action's bound origins and warns that hardcoded button translation "ignores the user's remapping" ([Steamworks ISteamInput](https://partner.steamgames.com/doc/api/ISteamInput)). On the web, KAPLAY declares `buttons: { jump: { keyboard: [...], gamepad: 'south' } }` once and lets UI read `getButton('jump')` ([KAPLAY input guide](https://kaplayjs.com/docs/guides/input/)). Boogle's registry already has the identity half; it needs the display half, not a replacement.

The recommended extension adds **display metadata only** and leaves dispatch where it is:

```js
registerAction('honk', {
  pad: 'y',
  label: 'Honk',                 // short verb, sentence case, used by prompts and the guide
  detail: 'three at once make a chord', // optional second line in the full guide
  keys: ['KeyT'],                // KeyboardEvent.code values (or 'Mouse0', 'Mouse2', 'Wheel'), for display
  touch: 'Honk',                 // label of the on-screen button, or omitted if none
  group: 'friends',              // move | camera | hands | ball | sand | friends | menu
  order: 10,                     // stable sort inside the group
  down, up, held,
});
```

Controls that claim no pad slot still need rows: the sticks (fixed Move/Look), mouse look, hotbar digits 1-8 (pad equivalent LB/RB), the wheel. A sibling `describeControl(id, { label, keys, padText, group, order })` in the same module puts those into the same list, so the guide has exactly one source. Groups should lead with the game's identity: Move, Camera, **Ball** (grab, throw, bump, bring back, which follows DESIGN.md principle 2, "the ball stays the star"), Hands, Sand, Friends, Menu. The feel.js monkey-patch becomes a first-class `wrapAction(id, { when, label, down, up })` that layers a contextual meaning onto a slot, so the guide can render "LT: Pile sand, while swimming: Dive" and the pad card can show only the meaning that applies right now. Steam's "action set plus layers" model is the right mental picture: a base set with swimming or holding layered on top ([Steamworks ISteamInput](https://partner.steamgames.com/doc/api/ISteamInput)). The full priority-stacked contexts of Unreal's mapping contexts ([Unreal docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/enhanced-input-in-unreal-engine)) are unnecessary here, because Boogle already exposes the state as `me.swimming`, `body.shovel` and `body.holding-thing`.

With that data in place, three things become functions of the registry instead of hand-kept tables. A shared renderer in a new `src/player/guide.ts` builds grouped rows (glyph, then verb) for a given input kind; the gamepad card, the pause view's Controls page and the first-run card all call it, so they cannot drift. `glyph()` in [src/player/glyphs.ts](../../src/player/glyphs.ts) learns to take an action id and resolve its key or pad slot from the registry, retiring the five-entry `GLYPHS` table that today mirrors `pad: 'b'` for interact by hand. And [src/features/updates.js](../../src/features/updates.js) stops copying `PAD_LABEL[pad]` into its button text at registration, which is exactly the pattern that goes stale on device switch. Prompts should also keep glyph and verb as separate nodes rather than one concatenated sentence, so a later `t(label)` translation pass touches one function.

The registry also makes the guide testable, which the hard-coded rows never were. Extend [test/controls.test.mjs](../../test/controls.test.mjs), which today covers only slot clashes, to assert that every registered action has a non-empty label and a known group, that no key code is claimed twice outside a `wrapAction` layer, and that every action with `keys` or `touch` also has a pad slot or a declared pad equivalent. That last check turns AGENTS.md's gamepad rule into a failing test instead of a sweep someone has to remember. No cited project lints its action registry this way; it is a recommendation that fits the repo's "test what would silently break" rule.

### What stays out, and why the schema does not block it

Rebinding is out of scope, but the line that keeps the door open is simple. `keys` and `pad` are data keyed by a stable action id, and **every UI reads them at render time and never caches a formatted label**. Unreal saves remaps by the action's `Name` and KAPLAY's `setButton` merges a per-device override ([Unreal API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/EnhancedInput/UPlayerMappableKeySettings), [KAPLAY input guide](https://kaplayjs.com/docs/guides/input/)). Boogle's later version is a saved override map applied before dispatch. The only structural change rebinding then requires is moving key *dispatch* into the registry: one `keydown` listener in controls.js looks up `keys`, runs one typing guard, and calls `down`. That also fixes the five divergent guards, so it is worth doing before rebinding, but it touches every feature with a key and is not needed for the guide or pause view. Two other things wait too. Layout-aware labels via `navigator.keyboard.getLayoutMap()` would show "Z" for `KeyW` on AZERTY, but the API is experimental, not Baseline and secure-context only ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Keyboard/getLayoutMap)). Because bindings are `code` values, it can slot in later without a schema change. The `touch` field is display-only for now as well. Touch buttons stay hand-placed across five feature CSS files, and the audit flags them as collision-prone on small phones. Generating the touch layout from the registry is deferred, because one button per action does not scale past a handful, and a real fix needs a thumb-zone layout with a cap rather than more generated buttons.

## Pause is a local overlay over a world that never stops

Shared synchronous worlds cannot pause, because one player stopping would interrupt everyone else acting in the same space ([Journal of Games Criticism](https://gamescriticism.org/wp-content/uploads/2023/07/schmalzer-4-1.pdf)). Minecraft Java freezes only in singleplayer and swaps "Save and Quit" for **Disconnect** in multiplayer ([Minecraft Wiki](https://minecraft.wiki/w/Pause_menu)), and Valheim on a dedicated server never pauses ([Thunderstore PauseMyServer](https://thunderstore.io/c/valheim/p/DeathMonger/PauseMyServer/)). Boogle is stricter still: physics, presence and the lockstep tick run unconditionally every frame ([src/main.ts](../../src/main.ts)), Owner, Host and Lockstep state all keep moving, and DESIGN.md principle 8 assumes people drop in and out at random. Boogle's pause view is therefore a **Local** piece of state in DESIGN.md's sync table. It diverts only this player's input to a menu and leaves the island rendering and simulating behind it. In a cozy world with no danger, the only open question is social signalling. A small `away` flag through `addPresenceField`, drawn as a sleepy pose or "zzz" over the avatar, would tell friends why someone stands still. No source documents a mainstream game doing this, so treat it as an optional idea, not established practice.

### The talk box already solved input capture; extract it

The Boogler's talk box is the one real modal in the game, and its mechanics are the template ([src/boogler/dialogue.js](../../src/boogler/dialogue.js)). On open it calls `input.keys.clear()`, hands the pad to itself with `setPadModal`, exits pointer lock, and installs a **capture-phase** window `keydown` listener that calls `stopPropagation()`. That last step is what silences every feature's own bubble-phase key listener without touching any of them. A `<dialog>` alone would not do this, because `showModal()` makes the page inert for focus and pointer events while key events still bubble to `window`. Extracting those few lines into a shared `openModal({ onKey, onPad })` helper (for example `src/player/modal.ts`) lets the talk box and the pause view share them, and **decouples the pause view from the key-dispatch refactor above**: the overlay works with today's scattered handlers. The helper must also be the single owner of "a modal is open", so the pause view refuses to open while the talk box is up, and the reverse. The Fortnite Creative bug where friend-request pop-ups blocked the pause menu from opening shows what happens when overlays fight ([Unreal Engine forum](https://forums.unrealengine.com/t/friend-request-pop-ups-prevent-opening-the-pause-menu-and-can-block-in-game-controls-when-spammed/2724374)).

Use `<dialog>` with `showModal()` for the view itself. It gives the top layer, inert background, initial focus via `autofocus`, an implicit `aria-modal="true"` and a `cancel` event for free ([MDN dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog)), and it replaces any hand-written focus trap. One ordering constraint comes from the codebase. [src/features/gamepad.js](../../src/features/gamepad.js) steals focus back to the canvas on iPadOS, because pad A otherwise "presses" a focused button, and it skips that steal only while a pad modal runs. **The overlay must call `setPadModal` before `showModal()`**, or the dialog's focused Resume button will lose focus on the next poll.

### Each device opens it its own way, and desktop must follow pointer lock

On desktop the natural key is Esc, but the browser owns it: Esc releases pointer lock, `pointerlockchange` fires on the document, and relocking requires a fresh engagement gesture ([MDN Pointer Lock API](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_Lock_API)). Chrome also refuses relock for a short cooldown after Esc, with no documented duration ([three.js forum](https://discourse.threejs.org/t/three-pointerlockcontrols-unable-to-use-pointer-lock-api/18321)). The robust pattern, the one three.js's own pointer-lock example uses, is to **treat every loss of lock while playing as "open pause"**, and to make Resume the click that calls `requestPointerLock()` ([three.js example](https://github.com/mrdoob/three.js/blob/dev/examples/misc_controls_pointerlock.html)). If `pointerlockerror` fires during the cooldown, keep the view open and say "click again to resume" rather than retrying automatically, since auto-relock attempts fail and reading mouse input while unlocked causes runaway camera spin ([Bugnet](https://bugnet.io/blog/how-to-fix-pointer-lock-errors-and-the-mouse-escaping-in-browser-fps-games)). Lock is also lost on alt-tab, so this one hook covers focus loss as well. The talk box releases lock on purpose, so the helper sets an "intentional unlock" flag that the pause trigger respects.

This changes one existing behavior, and the change should be deliberate. Today Esc drops the player into an "unlocked but still playable" state with a "Look around" hint and mouse-drag look ([src/player/hud.ts](../../src/player/hud.ts), [src/player/input.ts](../../src/player/input.ts)). Under this design that state survives only where pointer lock failed or is unsupported (`inputState.lockFailed`). Everywhere else, Esc means pause. A second Esc inside the open view should do nothing (call `preventDefault` on the dialog's `cancel` event), because it cannot relock and closing to a half-unlocked state confuses more than it helps. H, today's "hide controls" key, opens the same view on its Controls page. That also gives keyboard players a way in that does not depend on Esc, which XAG 112 calls out for players who cannot reach that key ([XAG 112](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/112)).

On the pad, Apple's controller guidance assigns Menu to "opens game settings or pauses gameplay", A to confirm and B to back ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/game-controls)). Menu already means "show controls" in Boogle, so the `pad-help` action becomes `pause`, with no slot cost. Navigation is a hand-rolled pad modal: D-pad or stick up/down moves real focus with a repeat delay, A clicks, B goes back a page or resumes, and focus wraps in the linear list as XAG 112 asks. Spatial-navigation libraries exist ([Coherent](https://frontend-tools.coherent-labs.com/interaction-manager/features/spatial-navigation)), but a single column of four buttons does not justify a dependency under AGENTS.md. Style a `[data-focus]` attribute as well as `:focus-visible`, since it is unverified whether programmatic `focus()` triggers `:focus-visible` in every browser. On touch, put a pause button in a top corner, as Apple recommends for secondary controls ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/game-controls)), padded with `env(safe-area-inset-*)` ([MDN env()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env)) and well above WCAG's 24×24 CSS px minimum target ([W3C SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)).

### Four items: Resume first, Leave last

Minecraft, Roblox and Don't Starve Together all put Resume first and the exit last, with social items in between ([Minecraft Wiki](https://minecraft.wiki/w/Pause_menu), [Roblox DevForum](https://devforum.roblox.com/t/edit-escape-menu/77986/12), [DST pause screen](https://vietnd69.github.io/dst-api-webdocs/docs/game-scripts/screens/pausescreen)). Boogle's view should hold exactly four items. **Resume** is focused by default. **Controls** opens the derived guide. **Room** shows the room name, who is here and a "Copy invite link" button, which needs no text entry. **Leave** is last. "Leave" is the right word, not "Quit": the room survives the host's departure. [src/net/peer-room.ts](../../src/net/peer-room.ts) documents host migration (peers race for the host id after a loss), and commit 5414673 saves the world on every peer, not just the host. A light confirm (press again) is enough; the menu does not need a warning that the room will end. The header should carry the room name, and a reserved but hidden Settings slot marks where look sensitivity, invert Y and volume will go, the first options XAG 107 expects ([XAG 107](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/107)).

### Retire the always-on panel; teach once, then on demand

GAG asks that players be able to recall controls during play ([GAG](https://gameaccessibilityguidelines.com/indicate-allow-reminder-of-controls-during-gameplay/)). Layered disclosure meets that better than an 18-row panel parked over the island. The layers are contextual prompts at the moment of need (already built in [src/features/prompt.js](../../src/features/prompt.js)), a **first-run card** with the same derived rows for the active device, and the full reference in pause. The three.js pointer-lock example merges onboarding and reference into one "click to play" screen ([three.js example](https://github.com/mrdoob/three.js/blob/dev/examples/misc_controls_pointerlock.html)). Boogle's version shows the Move, Camera, Ball and Hands groups the first time a player enters, dismisses on first movement, and remembers that in `localStorage` (the current panel's hidden state is never persisted, so it reappears every load). A one-line pill ("Esc / H: menu and controls", or "Menu" on pad) can stay in a corner as the persistent reminder. Breath of the Wild lists special controls only after the game reveals them ([Zelda Wiki](https://zeldawiki.wiki/wiki/Special_Controls)), and a later `when`-based "discovered" filter could do the same. It is not needed now.

## One sticker-and-glyph visual system, sized for the couch

The HUD already speaks two dialects. "Glass" is used by the roster pills and the help panel: `--glass` at 0.58 alpha with blur. "Paper sticker" is used by the lobby card and prompt chips: white paper, 3px ink border, a hard ink drop shadow, Lilita One ([src/style.css](../../src/style.css), [src/features/prompt.css](../../src/features/prompt.css)). Keycaps come in two unrelated styles too: the global translucent `kbd` at 11px used by the help panel and pad card, and the paper `.g-key` used by prompts ([src/player/glyphs.css](../../src/player/glyphs.css)). The pad card even writes "LB" and "D-pad ←" as plain text instead of the coloured `.g-pad` circles. The pause view and guide should use **glass for the full-screen dim and opaque paper cards for everything with text**. XAG 102 measures contrast against "the lowest contrasting area of the background", and a moving 3D scene full of sunlit sand and sky makes any text on a 58% dim a gamble. Text on opaque paper, by contrast, holds its 4.5:1 minimum regardless of what is behind it ([XAG 102](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/102)). Sea of Thieves solves the same problem with a dark plate behind menu text on a patterned background (same source).

Glyphs should be the `.g-*` set everywhere, and the global translucent `kbd` rule should go. CSS keycaps are real text: they scale with font size, take the theme tokens and are read by screen readers, which satisfies XAG's "no text in images" rule ([XAG 102](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/102)). LT already has a rounded tab, but the pad set still needs the shapes CSS draws poorly: bumpers, RT, D-pad halves, stick clicks, View and Menu. For those, inline a handful of SVG paths from Kenney's CC0 Input Prompts ([kenney.nl](https://kenney.nl/assets/input-prompts)), recoloured with ink and paper, rather than shipping a PNG sprite sheet in a second visual style. Keep Xbox letters and colours as the default. The standard mapping is Xbox-shaped, Steam Deck accepts Xbox names ([Steamworks Deck compat](https://partner.steamgames.com/doc/steamdeck/compat)), brand detection from `Gamepad.id` is "not strictly specified" and varies by browser ([MDN Gamepad.id](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad/id)), and the Backbone's reported id is unknown until someone logs it on a device. PlayStation shapes carry a trademark question no CC0 pack resolves ([OpenGameArt](https://opengameart.org/content/free-keyboard-and-controllers-prompts-pack)), so adding them is a human decision. On touch, the guide should show the on-screen buttons as they appear, not controller letters, which Apple explicitly advises against as touch artwork ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/game-controls)).

Size matters more than it looks, because a pad player may be on a couch. XAG 101 sets minimum text body height at **26px at 1080p for console and 18px for PC**, requires glyph text to meet the same minimum and scale to 200%, and allows scrolling in one direction only ([XAG 101](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/101)). The current `.g-key` (13px in a 24px box) and `.g-pad` (14px in a 25px circle) fall short inside a full-screen guide. Size the guide's text with something like `clamp(18px, 2.4vh, 40px)`, which lands near 26px on a 1080p screen, and size glyphs in `em` so they grow with the row; then measure the rendered result rather than trusting the number. Lay the Controls page out as grouped cards, two or three columns on wide screens and one column with vertical scroll on phones. Each row is glyph then verb in sentence case, with small Keyboard / Gamepad / Touch tabs that default to the active device. Following XAG, the guide shows only the active device unless the player asks. No source compared card lists against a controller diagram, but a diagram does not reflow to a phone and separates each label from its glyph, so the list wins here.

Motion and cost should stay modest. NN/g puts a modal's entrance at 200–300 ms with ease-out and its exit slightly shorter ([NN/g](https://www.nngroup.com/articles/animation-duration/)). Under `prefers-reduced-motion`, MDN's pattern swaps movement for an opacity fade rather than removing feedback ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion)); the game already does this for the lobby button and the prompt pop. The dialog's `::backdrop` cannot fade out on close, so draw the dim as an element inside the dialog. Skip `backdrop-filter` blur by default: WebKit's engineers note it "forces the engine to perform more rendering passes" ([WebKit](https://webkit.org/?p=3632)), and Firefox's bug reports on backdrop blur near WebGL point in both directions, so it is not a safe default. A flat darker dim over a live scene is cheaper and reads as "the world is still going", which is the message.

## A phased implementation outline

Each phase ships on its own through `npm run ship`, leaves the game better than before, and keeps hotspot edits to deletions and one-liners. Nothing in the layout claims below has been checked in a browser; the audit's overlap concerns (the help panel against the hotbar on short windows, touch buttons against the stick zone on narrow phones) are inferences from CSS values. Every phase therefore ends with a scenario in `dev/scenarios/`, modelled on [dev/scenarios/interact.mjs](../../dev/scenarios/interact.mjs), which already checks glyphs per input kind.

| 1 | Registry metadata, derived guide renderer, `glyph(actionId)`, registry test; old rows deleted | `src/player/controls.ts`, new `src/player/guide.ts`, `src/player/glyphs.ts/.css`, `src/features/gamepad.js`, the five row-appending features, `index.html`, `src/style.css` | 7 Telegraph everything; Small and readable | Extended `test/controls.test.mjs`; scenario asserts every `listActions()` id renders for kbm and pad |
| 2 | Pause overlay, shared modal helper, first-run card, touch pause button; always-on panel removed | new `src/player/modal.ts`, new `src/features/pause.js/.css`, `src/boogler/dialogue.js`, `src/features/gamepad.js` | 8 Drop-in, drop-out; Local sync kind | New `dev/scenarios/pause.mjs`: open/close per device, keys suppressed, talk box and pause exclusive |

### Phase 1 makes the guide correct before making it pretty

Add `detail`, `keys`, `touch`, `group` and `order` to `registerAction`, add `describeControl` for padless rows, and register metadata for every existing control, including Move, Look, wheel zoom, dive and hotbar 1-8. Write `src/player/guide.ts` as a pure DOM renderer, `renderGuide(container, { kind, filter })`, that groups, sorts and emits paper rows with `.g-*` glyphs. Point the gamepad card at it, and keep H toggling a **generated** panel in the same bottom-left spot for now, so this phase changes correctness without changing behavior. Then delete the 10 static rows from [index.html](../../index.html), the `.help` and global `kbd` rules from [src/style.css](../../src/style.css), and the hand-appended rows in bump, honk, hotbar, ping and shovel. That is more than AGENTS.md's "a line or two" in hotspot files, but it removes hotspot content rather than adding to it, and it should be said so in the commit body. Fix the stale README controls line to point at the in-game guide and list only the core verbs. The registry test lands here, and the scenario fails if any registered action is missing from the rendered guide on either kind.

### Phase 2 adds the pause view on top of the existing modal pattern

Extract `openModal` from the talk box first, as a no-behavior-change commit, so the talk box proves the helper. Then add `src/features/pause.js` with its own CSS and DOM created in JS, per the plug-in rule. It needs the `pointerlockchange` trigger with the intentional-unlock flag, `pointerlockerror` handling, H and Menu opening it (Menu replaces `pad-help` in the same slot), a top-corner touch button registered with `registerAction` like every other control, the four items, the Controls page rendered by `renderGuide`, hand-rolled pad focus with wrap, and a `cancel` handler that ignores Esc. The first-run card, which reuses the renderer and a `localStorage` flag, replaces the default-on panel, and Phase 1's interim H panel goes away. The optional `away` presence field fits here if wanted; it is an Owner field via `addPresenceField` and should be its own commit. Tick a PLAN.md line in the same commit.

### Phase 3 makes the guide follow the player

Replace the sticky body-class detection with a last-used-device signal. Today `body.touch` is fixed at load and `body.gamepad` clears only on touch or disconnect, so a keyboard player with a pad plugged in can keep seeing pad glyphs. The signal sets keyboard on `keydown` or a mouse `pointerdown`, touch on a touch `pointerdown`, and pad only on a button edge or a stick past a deadzone of roughly 0.3 to 0.5, so stick drift cannot flip prompts while the player types ([MDN pointerType](https://developer.mozilla.org/en-US/docs/Web/API/PointerEvent/pointerType), [MDN Gamepad API](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad_API/Using_the_Gamepad_API)). It emits one event on change, which prompts and the open guide listen to. Keep `body.touch` meaning "show the touch UI" and let glyphs follow the new signal, so a touchscreen laptop does not lose its keyboard prompts. Replace the feel.js monkey-patch with `wrapAction('pile', { when: swimDive, label: 'Dive', ... })`, and let the pad card show only the meanings that apply in the current context. Point the update toast at `glyph('update-reload')`.

### Phase 4 waits until rebinding or settings are wanted

Move key dispatch into the registry: one listener, one typing guard, and features declare `keys` instead of adding listeners. Then add a saved override map keyed by action id, layout-aware labels where `getLayoutMap` exists, and a Settings page in the reserved slot with sensitivity, invert Y and volume. None of Phases 1 to 3 has to change for this, which is the test that the earlier phases did not block it.

## Conclusion

The pause view is the visible deliverable, but the registry is the durable one. Once a control's label, group and keys live in one record, drift becomes a failing test instead of a playtest discovery, and the next contributor adds a control by filling in a few fields rather than editing up to seven places. That matters more in Boogle than in most games, because several friends and their agents ship features at the same time. Pad slots are the binding constraint, not screen space: with 14 of 16 slots taken, `wrapAction` contexts are what keep AGENTS.md's gamepad rule satisfiable as features keep arriving, and they should be treated as infrastructure rather than polish.

The one real design trade is on desktop. Making pointer-lock loss mean "pause" retires today's half-playable unlocked state in exchange for a predictable Esc, a recoverable relock and an obvious place for the controls. That is the right trade for a drop-in game where newcomers need to find the controls without being told where to look. It is also the change most worth watching in the first playtest notes after Phase 2, since no playtest has yet recorded how players actually use Esc, H or the pad's Menu button.
