# WebGPU particles with more than one silhouette

_Research report, 5 November 2026. Live primary-source research, published-package inspection and local source audit for prettier, more capable and efficient Boogle particles. Trigger: the floating-axe summon sparkle on `codex/axe-sparkle` inherits the shared pool's soft round dots. Research only; no game code, dependencies, rendering defaults or owner decisions changed._

**Recommendation [R].** Keep the GPU pool and its `emit()` interface. First give the existing axe burst a crisp four-point glint, controlled rotation and a short size/opacity envelope, without increasing its particle count. Next distinguish solid chips, dissipating dust and water droplets. Improve admission, uploads and visibility budgets before introducing alive-list compaction, sorting or indirect draws. A library would supply authoring vocabulary, but replacing this small working GPU simulation is not the smallest route to a better sparkle.

**Owner call (5 November 2026).** No particle library is adopted. Treat NewKrok three-particles (MIT), three.quarks and three-nebula as references: borrow ideas (lifetime curves baked to lookup samples, force fields, collision planes, soft depth fade, mesh and trail renderers, editor vocabulary) into Boogle's own pool. Any code borrowed from an MIT source keeps its license notice. Step 1, the axe glint, is approved and building on `codex/axe-sparkle`.

**Evidence key.** **[V]** = inspected repository/package code or fetched primary text; **[P]** = primary source located, but only description/abstract/search text checked; **[D]** = calculation from stated inputs; **[R]** = recommendation, estimate or interpretation. Maintainer test claims are attributed, not Boogle tests. No commercial game was played or frame-counted, no library was rendered, and no game GPU timing was measured. Not tested on a device. Exact proposed shapes, timings and budgets are [R].

Format follows `docs/research/tool-swing-animation.md`, read with `git show codex/tool-swing-animation:docs/research/tool-swing-animation.md` at `e74d862a12473bab424bf4369dbe47e13b725e69` (absent from this checkout), and [living-world-shaders](living-world-shaders.md). Serves **7. Telegraph everything**, **11. Show, don't tell**, and **Small and readable**. The [owner calls](../agents/owner-calls.md) require research, comparisons with standard engines, tunable presentation and asset-stage motion review. This report does not approve a new tool-appearance direction.

## 2. Libraries: current compatibility, not old reputations

Status checked live on 5 November. A recent `three` peer range does not establish shader compatibility with WebGPURenderer.

### three.quarks: useful vocabulary; released renderer remains incompatible

**[V]** npm latest **0.17.1**, published **21 May 2026 UTC**. Inspected master `de7c207f791c8b2260c43334a282976221688b1b`, its changelog and published package. `SpriteBatch`/`TrailBatch` construct `ShaderMaterial`; mesh materials patch shaders. Published exports have only the root entry, no `./webgpu`. The [changelog](https://github.com/Alchemist0823/three.quarks/blob/de7c207f791c8b2260c43334a282976221688b1b/CHANGELOG.md) mentions WebGPU shader support in 0.17.0, but this does **not** establish compatibility of these batches. [Package](https://www.npmjs.com/package/three.quarks/v/0.17.1), [SpriteBatch source](https://github.com/Alchemist0823/three.quarks/blob/de7c207f791c8b2260c43334a282976221688b1b/packages/three.quarks/src/SpriteBatch.ts).

**[V, attributed]** [Issue #114](https://github.com/Alchemist0823/three.quarks/issues/114) distinguishes experimental `quarks.nodes` from three's renderer. [PR #115](https://github.com/Alchemist0823/three.quarks/pull/115) proposes `NodeBatchedRenderer`, TSL materials, billboard/mesh/trail modes and soft particles. GitHub API: **open, `merged_at:null`**, updated 20 October. Its author reports parity/performance checks on r184/r186; these were not reproduced here and do not certify Boogle's r187 HDR pipeline. Do not describe the PR as released support.

**[V/R]** The [project](https://github.com/Alchemist0823/three.quarks) offers curves, colour/size/rotation behaviors, flipbooks, stretched billboards, trails, mesh particles and a [visual editor with JSON export](https://quarks.art/create). Editor workflow located, not exercised. Releases and the open port show activity, but no merge date/support SLA was verified. `BatchedRenderer.update(delta)` advances CPU systems and updates batches; compatible material/texture/render settings batch together, not universally into one draw. Adoption means owning a port/fork or waiting, translating emitters/exposure, precompiling variants and replacing rather than duplicating simulation ownership. **High integration risk** for this brief.

### three-nebula: released TSL rendering, CPU simulation

**[V]** npm latest **13.3.0**, published **19 September 2026 UTC**. Inspected master `1264b628eaace16365f6ccd07df174f5544b2a86` (30 September), release history and published exports. [12.1.0](https://github.com/creativelifeform/three-nebula/releases/tag/v12.1.0) added `three-nebula/webgpu`; [13.0.0](https://github.com/creativelifeform/three-nebula/releases/tag/v13.0.0) added seeded simulation/fixed-step `tick(realDeltaSeconds)` and fixed unrecycled renderer slots. [13.3.0](https://github.com/creativelifeform/three-nebula/releases/tag/v13.3.0) adds vortex/curl-noise behavior and emission zones. This is recent maintenance evidence; descriptions of a legacy-only abandoned library are stale.

**[V]** The [WebGPU adapter](https://github.com/creativelifeform/three-nebula/blob/1264b628eaace16365f6ccd07df174f5544b2a86/src/webgpu/GPURenderer/index.ts) uses `SpriteNodeMaterial`, TSL attributes, an atlas and one instanced mesh; additive blending is the default. Particle events write position/colour/alpha/scale/rotation/texture ID into CPU attributes and mark all six dirty. Dead slots return to a free list and get zero scale; draw count is a high-water mark. [System.ts](https://github.com/creativelifeform/three-nebula/blob/1264b628eaace16365f6ccd07df174f5544b2a86/src/core/System.ts) advances CPU emitters. **“GPURenderer” does not mean compute simulation.** Its [RibbonRenderer](https://github.com/creativelifeform/three-nebula/blob/1264b628eaace16365f6ccd07df174f5544b2a86/src/renderer/RibbonRenderer.ts) rebuilds geometry from particle history and uses a basic mesh material; don't assume sprite batching makes ribbons equally cheap.

**[V/R]** The [official site](https://three-nebula.org/) describes desktop Nebula and says its browser editor is forthcoming; current installation/schema parity/usability were not tested. JSON authoring and behavior composition could help a future effect-heavy workflow. Integration adds a CPU effect tick to existing `onFrame`, never another `requestAnimationFrame`; its container joins our scene. Audit blend families, atlas colour space, exposure, precompilation, Local/reduced-motion semantics and cleanup. There is no intrinsic need for a second HDR pipeline, but substantial work to match ours. **Medium/high migration risk**; no local r187 rendering test. A candidate if authoring complexity becomes the bottleneck, alongside NewKrok below; neither justifies replacing four births now.

### NewKrok three-particles: released compute, with integration conditions

_Owner-requested addendum, checked live on 5 November. Earlier library findings above were not re-audited during this addendum._

**[V] Published artifact and maintenance.** Registry latest is [`@newkrok/three-particles@3.0.0`](https://www.npmjs.com/package/@newkrok/three-particles/v/3.0.0), published **25 April 2026, 22:15 UTC**; [GitHub's latest release](https://github.com/NewKrok/three-particles/releases/tag/v3.0.0) agrees. Registry `gitHead`, release tag and freshly cloned master identify **`f54737cabfec5668ac654c712aff0593162ca4ef`**. Downloaded the published tarball, checked its SHA-512 against registry integrity, and inspected `dist/index.js`, `dist/webgpu.js`, declarations and the pinned source. Unlike quarks' open port, this package actually exports `./webgpu`. The repository shows no later master commit at inspection; April releases and substantive implementation/tests are evidence of work, not a current support guarantee. The [changelog](https://github.com/NewKrok/three-particles/blob/f54737cabfec5668ac654c712aff0593162ca4ef/CHANGELOG.md) still labels the world-space/colour changes “Unreleased”; inspected v3.0.0 distribution contains them, so that heading is not the release boundary.

**[V] This is real GPU simulation in source, not just GPU drawing.** [`enableWebGPU()`](https://github.com/NewKrok/three-particles/blob/f54737cabfec5668ac654c712aff0593162ca4ef/src/webgpu.ts) registers TSL materials and compute helpers. The active factory calls [`createModifierComputeUpdate`](https://github.com/NewKrok/three-particles/blob/f54737cabfec5668ac654c712aff0593162ca4ef/src/js/effects/three-particles/webgpu/compute-modifiers.ts): eight storage buffers, fixed-slot birth data, guarded active-particle integration, gravity, lifetime/death, colour/size/opacity/rotation curves, velocity/noise, force fields and collision planes. Curves are baked to 256 samples on CPU. `compute(computeKernel(), maxParticles)` returns the node; the caller must dispatch it after `system.update(...)` and before the scene draw. Geometry reads GPU-written buffers. This proves the implemented computation path, **not successful execution on Boogle's GPU**.

**[V] CPU work remains significant.** [`three-particles.ts`](https://github.com/NewKrok/three-particles/blob/f54737cabfec5668ac654c712aff0593162ca4ef/src/js/effects/three-particles/three-particles.ts) schedules bursts/rate/distance births, packs init data, updates uniforms/configuration and scans creation slots for lifetime expiry/free-list management. With death sub-emitters it also runs an approximate CPU shadow simulation for spawn positions; this is not GPU readback and need not match every GPU modifier. Child sub-emitters explicitly use `SimulationBackend.CPU`; trails always use CPU simulation and CPU-rebuilt ribbon attributes. Instanced/mesh GPU systems each allocate their own buffers, material, geometry and compute node; `instanceCount=maxParticles`. Thus **N visible GPU systems nominally mean N compute dispatches and N particle draws**, plus child/trail draws and any depth pass, not cross-emitter batching. Counts are source-derived, not captured. Use one existing game update hook; don't copy the editor's frame loop or create one pool per Boogle `emit` call.

**[V/R] Materials fit the architecture, not the look automatically.** The pinned [billboard material](https://github.com/NewKrok/three-particles/blob/f54737cabfec5668ac654c712aff0593162ca4ef/src/js/effects/three-particles/webgpu/tsl-instanced-billboard-material.ts) uses `MeshBasicNodeMaterial`, custom `vertexNode` and `colorNode`, configurable blend/depth state, `fog:false` and `toneMapped:false`. Its [mesh material](https://github.com/NewKrok/three-particles/blob/f54737cabfec5668ac654c712aff0593162ca4ef/src/js/effects/three-particles/webgpu/tsl-mesh-particle-material.ts) adds a fixed camera-facing half-Lambert-style term, **not Boogle scene lights/PBR**. Prefer INSTANCED for cards and adapt mesh shading deliberately. The default POINTS path creates `THREE.Points`; even the editor substitutes INSTANCED for WebGPU. It is not an acceptable Boogle path.

v3 [colour helpers](https://github.com/NewKrok/three-particles/blob/f54737cabfec5668ac654c712aff0593162ca4ef/src/js/effects/three-particles/color-utils.ts) decode authored sRGB inputs to linear. Boogle `emit()` already receives linear `Color` components and separately scales HDR intensity; translating those values directly into NewKrok `startColor` would decode them again. Explicitly bridge authoring colour, linear HDR gain and coverage. Keep our one scene/HDR/Neutral output; `toneMapped:false` does not bypass the final fixed gain/Neutral transform. Precompile each material through [precompile.ts](../../src/render/precompile.ts), and await `renderer.compileComputeAsync` for every system's node before dispatch, as [particles.ts](../../src/render/particles.ts) does. Structural effect variants need their own readiness/warm-up handling; the package does not supply Boogle's readiness gate.

Its [soft-depth helper](https://github.com/NewKrok/three-particles/blob/f54737cabfec5668ac654c712aff0593162ca4ef/src/js/effects/three-particles/webgpu/tsl-shared.ts) expects an externally supplied depth texture. The [editor world](https://github.com/NewKrok/three-particles-editor/blob/b6b03b757559236b47eafaf8465176564011a5b6/src/js/three-particles-editor/world.ts) hides particles and renders another scene depth pass, then draws normally with no tone mapping. Do not transplant that output/pixel-ratio setup into Boogle; integrate depth under our render owner and verify MSAA, scene-resolution UVs and device depth conventions. Editor appearance is not HDR/Neutral parity.

The practical distinction is **shape + temporal contrast + material identity**. The following are Boogle recipes, not reconstructions of commercial shaders.

### Shapes, lifetime and motion

- **Glint:** a concave four-point star/tapered cross, compact centre, unequal arm lengths, one short expansion/contraction. Two tapered lobes are a good start; plain intersecting rectangles read as a plus sign. Rings suit pulses, but a camera-facing ring does not lie on water. Keep masks inside their card; antialias their edges.
- **SDFs:** centered UV `p=2*uv-1`; annulus distance `abs(length(p)-radius)-thickness`. Union two box distance fields for a cross; taper arms or use a star distance function for a glint. For negative-inside `d`, coverage can be `1-smoothstep(-w,w,d)` with `w=max(fwidth(d),epsilon)`. These are unevaluated recipes. Compute derivatives before nonuniform branches/discard, per the TSL contract. Fade or widen subpixel arms to avoid shimmer.
- **Lifetime:** normalized age `u=1-lifeLeft/fullLife`; a few named envelopes suffice: glint attack/peak/decay, dust quick growth/slow dissipation, chip nearly constant size/short retirement. Preserve legacy `grow/shrink/fade` defaults. Use analytic curves or a shared lookup, not per-emitter shader compilation.
- **Colour/alpha:** separate colour progression, HDR intensity and coverage. Ivory-to-warm-gold glint; low-contrast dust that loses density. Interpolate linear values. Twinkle is a bounded pulse with a birth phase, not synchronized flashing; the 0.1–0.16 s axe cue needs one beat.
- **Rotation/stretch:** choose birth angle/spin once, derive angle from age. Transform velocity into camera space for screen-plane alignment, clamp aspect and handle near-zero projected velocity. Keep camera-motion stretch off initially so turning the view does not whip droplets around. Unity's renderer documentation supplies the precedent, not the constants.
- **Wood chips:** compare a flat wedge card with a small instanced opaque bevelled wedge. Orientation, spin, gravity, short life; no Rapier bodies, initially no shadows. Shared lit node material helps chips belong to the wood. Keep the cosmetic simulation service; use a distinct mesh draw batch.
- **Dust:** a few lobed silhouettes, fast expansion, slow fade and optional alpha erosion. Atlas or procedural mask; subtle upper/lower colour variation can suggest volume without a light per particle. Preserve the contact point's visibility. Landmark smoke needs different envelopes/budgets from foot dust.
- **Splash:** fast narrow drops become compact beads near the apex; foam stays soft. Preserve floor death and existing surface ripples. A short splash-crown flipbook can complement fewer drops later, not cover the water with a bright card.
- **Trails/ribbons:** bounded sampled history for glider tips/rockets or a deliberate axe swoosh, with minimum sample distance, age-dependent width/alpha and reset on teleports. Repeated/zero-length points must not create NaNs/bright bands. This adds history, geometry and ordering work; summon sparkle does not need it.

**[R] Three biggest visual changes:** (1) crisp glint plus one envelope, (2) rotating non-circular chips, (3) dust silhouette/dissolve. Spin/aspect support benefits all three; flipbooks/ribbons follow only when a named effect needs them.

### Atlas and flipbook tradeoffs

**[R]** SDFs avoid assets and stay crisp for simple stars/crosses/rings, at fragment-ALU cost. A shared atlas supplies painted dust/splash shapes in one texture/material batch. Animate frame index by age; interpolation needs two samples. Add gutters/mip-safe padding to prevent tile bleeding. Colour textures use sRGB, masks are data; don't multiply straight alpha twice. Uncompressed **512×512 RGBA8 is 1 MiB, approximately 1.33 MiB with all mips [D]**, independent of download compression. First glint needs no atlas.

### Normal versus additive under HDR + Neutral

**[V]** [readable-unlit.ts](../../src/render/readable-unlit.ts) already folds reciprocal fixed exposure into reward RGB; dust/smoke/foam default to intensity one. [Khronos Neutral](https://github.com/KhronosGroup/ToneMapping/blob/main/PBR_Neutral/pbrNeutral.glsl) compresses/desaturates bright highlights. Brighter additive overlaps can converge toward white; more intensity does not improve silhouette.

**[R]** Normal alpha gives dust/foam body on bright backgrounds but needs ordering. Additive suits small hot cores/glints and is largely order independent amongst additive layers, but weak on bright sky and wrong for brown chips. Keep depth testing and disable transparent depth writes. Start the star with current normal alpha; compare a separately batched additive accent only if needed. Blend state is per draw: a per-instance enum cannot independently select hardware blend equations. Mixed normal/additive batches still have ordering considerations.

Evaluate before the same fixed gain, Neutral and sRGB output. Never compensate twice, in both `readableIntensity()` and the material. `toneMapped:false` does not bypass the final scene post transform. No second canvas/renderer. Bloom can spread light but cannot replace a good shape; global bloom/exposure changes exceed the sparkle fix.

### Soft particles / depth fade

**[V]** [GPU Gems 3, chapter 23](https://developer.nvidia.com/gpugems/gpugems3/part-iv-image-effects/chapter-23-high-speed-screen-particles) explains depth-based intersection fading and low-resolution particle rendering's fill-rate tradeoff. Its old hardware timings are not Boogle measurements. Installed r187's `softParticles()` provides the depth-gap operation.

**[R]** Apply to dust/large smoke cutting through geometry, not every tiny star. Use a valid opaque-depth snapshot, correct viewport resolution/UVs and camera depth convention. `viewportDepthTexture` copies depth; it is not a free sample of a still-written attachment. Don't read this frame's scene-pass result from the same scene's particle material and create a cyclic dependency. Verify MSAA depth copy/resolve, adaptive scene resolution and Safari before enabling. Preserve stored MSAA. The helper's perspective conversion needs review for orthographic cameras. Transparent water's depth policy can still leave seams; depth fade is neither collision nor a water-surface query.

## 5. Efficiency: source facts versus measurements

### Calculated baseline, not timings

| Item                | Amount [D]                                                                                          | Boundary                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| State/draw arrays   | `720×7×16 = 80,640 B` = 78.75 KiB                                                                   | Excludes renderer allocations, uniforms, bindings/alignment.                                                   |
| Spawn queue         | `256×6×16 = 24,576 B` = 24 KiB                                                                      | Uploaded only on birth frames.                                                                                 |
| Combined payload    | 105,216 B = 102.75 KiB                                                                              | Not total GPU residency; CPU queue mirror and 5,760 B deadline array are additional.                           |
| Birth-frame upload  | Full 24 KiB even for four births; four records need 384 B                                           | Backend/source behavior, not bandwidth timing. Continuous 60 birth-frames/s: 1.40625 MiB/s; 120: 2.8125 MiB/s. |
| Update dispatch     | r187 default 64-thread groups: `ceil(720/64)=12`, 768 invocations; generated count guard rejects 48 | Dead slots exit early. No elapsed milliseconds inferred.                                                       |
| Spawn dispatch      | Four groups / 256 invocations on birth frames; `spawnCount` exits unused indices                    | Less arithmetic does not remove dispatch overhead.                                                             |
| Draw while nonempty | One draw, 720 quad instances, nominal 1,440 triangles                                               | Zero-size slots save covered fragments, not instance/vertex submission.                                        |

**[V]** Installed `WebGPUAttributeUtils.updateAttribute` uploads the entire attribute when `updateRanges` is empty; the queue sets only `needsUpdate`. A later implementation can use one contiguous `addUpdateRange(0, queued*24)` in scalar components and inspect the resulting upload. Current `q.set([…])` creates five temporary JS arrays per birth; direct scalar packing removes those allocations if profiles justify it. GPU simulation still leaves CPU emitter scans and birth construction.

### Behavior to protect before optimizing

- **Round-robin means insertion order, not earliest death or least important effect.** With variable lifetimes, it can overwrite a live slot while another is dead. Bursts can erase landmark smoke; decorative spray competes with action cues. No priority/drop/replacement counters expose this. `particleCounts()` estimates CPU deadlines; floor kills, overwrites and clock differences mean it is not a GPU alive count. **[V]**
- **Pool-wide culling is disabled.** This avoids incorrect default Sprite bounds for a world-wide batch. Birth-distance/importance quotas can save work without GPU readback. Don't remove offscreen particles about to enter view, or distant landmark smoke indiscriminately. **[V/R]**
- **Fill can dominate at 720.** Quad area, overlap and shader work matter; thin star arms still reject surrounding fragments. Low alpha is not cheap. Apple's [GPU architecture talk](https://developer.apple.com/videos/play/wwdc2020/10602/) explains opaque/feedback/translucent work and hidden-surface removal. Opaque chips can trade vertices for less blended coverage, but this is not a measured Boogle win. **[V/R]**
- **No instance sorting.** Three sorts objects, not the 720 instances inside this Sprite. Sort only a normal-alpha batch with observed artifacts; CPU sorting needs a CPU position model or readback, GPU sorting adds indices/passes/storage. Additive doesn't repair smoke ordering. **[V/R]**
- **Compaction has a break-even point.** Alive-list scans/atomics/synchronization can cost more than the dead-slot work saved here. Keep state slots stable; compact draw indices. Reset/cap counters, generate indirect arguments after compaction, then draw. Atomic append does not depth-sort, and racing birth/update/free ownership can corrupt the pool. **[R]**

**[R] Better order:** count drops/replacements → prioritize admission → upload queue prefix → reduce unnecessary births/large-card coverage → split genuinely different blend/geometry families → measure → consider alive lists/indirect draws/sorting. Don't create a new 720-slot pool and two compute passes per emitter. Use one service with bounded subpools or render lists. Current update has seven storage bindings; one separate buffer per new field can exceed the baseline eight. Pack appearance records/structs and count each generated stage's bindings.

### Mobile / iPhone and a measurement protocol

**[V]** [WebKit's Safari 26 release article](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/) establishes WebGPU availability, not a particular iPhone's frame budget. [WebGPU core limits](https://www.w3.org/TR/webgpu/#limits) include eight storage buffers per shader stage and 256 compute invocations per workgroup. Inspect actual adapter/device features/limits; don't assume optional timestamp queries, f16, subgroups or desktop memory ceilings. These 64-thread kernels/small arrays are modest in that dimension. Thermal load, screen pixels, MSAA, water and sustained overdraw remain unknown.

**[R]** On the Mac first, compare fixed camera/viewport/DPR/scene resolution/MSAA and identified builds at idle, four glints, sustained chopping, shoreline spray, large steam/confetti bursts and overlaps. Record requested/admitted/dropped/replaced births, estimated occupancy, draws/dispatches, upload bytes, CPU emitter/update cost, completed-frame cadence and first-use hitches. `performance.now()` around compute measures submission, not GPU execution; use GPU timestamps only when supported/validated. Separate cold compilation from warmed steady state. Quiet timing requires the shared machine's GPU to be available; don't terminate other workers.

Test sparse and saturated cases and a camera inside smoke. Low quality should reduce decoration/lifetimes/large-card coverage and omit soft-depth extras before weakening action cues. [quality.ts](../../src/render/quality.ts) remains resolution/cadence owner. On iPhone/iPad record hardware/OS/browser, sustained duration, effective pixel dimensions and errors. No universal “720 is safe” or FPS prediction follows here. Low-resolution smoke is a later fill-rate option with depth/upscale artifacts; retain crisp stars/chips at full resolution.
