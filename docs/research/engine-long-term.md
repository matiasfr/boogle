# Boogle's engine in a year: an independent second opinion

> **Verdict:** Build one component-based gameplay model, with explicit authority and lifetime, one scheduling framework and versioned data contracts. Move the classic states, player and seats onto it; retire the parallel gameplay object model. Keep renderer and physics objects as owned runtime resources. Preserve deterministic rules, but finish replacing client lockstep transport with server replication and prediction.
> **Top recommendations:** 1. Unify gameplay state. 2. Unify scheduling, not clock rates. 3. Make commands and accepted events data. 4. Derive persistence, replication and inspection from versioned schemas. 5. Give entities, plug-ins and assets explicit lifetimes. 6. Keep a replaceable storage backend; prove portability with a second implementation.
> **Status:** open. Independent research requested by the owner; deliberately reopens architecture decisions. Neither an approved implementation plan nor a change to existing contracts.

_2026-11-13 UTC. Code census and reads at `5b6c49a09ee637f92f29f8a3356af0312ec24646`; live primary-source research on the same date. The first study, [engine-portability](engine-portability.md), is dated 2026-11-12 internally and was present on `origin/main` during this review. Its blob matched this checkout. Schedule and sunk cost do not determine the recommendations below. [DESIGN](../../DESIGN.md)'s “Understandable at a glance” is the principal goal: adding a shared toy, vehicle or place should use the same inspectable rules for ownership, replay and cleanup._

## Target architecture: one-page contract

**1. One gameplay data model, several authority domains.** An entity is a stable game ID plus typed data components; systems own behavior. Schemas declare field types/units, references, defaults, version, authority, persistence, replication audience and prediction policy. Singletons use the same contracts. Server worlds, confirmed client worlds, prediction overlays and local worlds share definitions, not mutable storage. No second canonical `GameEntity.state`, `me` or mesh `userData` gameplay state. A presentation object can remain an ergonomic renderer adapter. [E's schema](../../src/ecs/schema.ts), [player state](../../src/player/state.ts) and [entity](../../src/entity/entity.ts) are the seams.

| State | Where it lives in the target; who may change it |
| --- | --- |
| Current classic lockstep and railway economy | Deterministic integer components in the room world. Server accepts ordered commands; clients predict a declared subset. Keep lockstep execution during storage migration, then retire its network protocol separately. Retain replay hashes permanently. |
| Other server-owned gameplay | Room components for seat occupancy, shared physical props, NPC decisions and sessions; explicit transient/persistent flags. Shared physics has a floating-point execution group, outside the integer replay closure. Quantized observations enter deterministic rules as recorded commands. |
| Player | Identity, motor/input, pose, inventory references and seat attachment are components. Owner computes ordinary movement locally and publishes validated pose; server owns scarce/shared outcomes and seats. Local prediction and remote interpolation are separate components. |
| Local view | Transient pose smoothing, camera intent, animation intent, selection and effect state in a local world. Meshes, Rapier handles, mixers, DOM and audio nodes in disposable sidecars keyed by entity ID. Never saved or hashed as gameplay. |
| Per-account | Separate versioned profile records keyed by account ID; materialize the relevant projection on join. Room progress stays room-scoped. Private conversation memory/settings can remain local records; credentials remain outside ECS. Cross-room rewards, if added, need idempotent account transactions, not room snapshots. |
| Immutable content / services | Versioned content catalog, prefab definitions and asset IDs; transport, storage I/O, authentication, renderer and audio services injected as capabilities. They are not entities merely to obtain uniformity. |

**2. One scheduler implementation and registration contract.** Replace the independent ordering machinery in [loop](../../src/loop.ts), [walker](../../src/entity/walker.ts) and [E](../../src/ecs/world.ts) with named groups: admission → command application → deterministic rules → commit; fixed pre-physics → physics → post-physics; frame interpolation → views → render. Declare reads/writes of components, resources and event queues, explicit before/after edges, structural-change barriers and teardown order. Reject cycles and unordered conflicting accesses; canonical names break only harmless ties. Preserve existing command/tick boundaries first. Browser RAF and server clocks drive different groups; neither rendering nor Rapier is forced onto the economy tick. [Unity's groups](https://docs.unity3d.com/Packages/com.unity.entities@1.3/manual/systems-update-order.html) and [Bevy's schedules](https://docs.rs/bevy_ecs/latest/bevy_ecs/schedule/index.html) support this distinction. Start serial; access declarations are correctness and tooling, not a promise of safe parallelism.

**3. Commands and events are typed data with different semantics.** Network commands carry actor/session/request identity and an admitted order. A dispatcher runs receipt check → handler → settlement → receipt/event commit. Preserve first-success fallback and per-command structural visibility in [railway-systems](../../src/sim/railway-systems.ts). Outcomes describe what actually happened; presentation consumes committed events with deduplication, prediction tags and independent reader cursors. Rule-to-rule events drain at declared barriers; they are not arbitrary recursive callbacks. Transient queues need not be entities or durable history. Replay contains admitted inputs and external observations; presentation effects never replay as gameplay. Replace the mixed roles of [sync callbacks](../../src/world/sync.ts) and [effect callbacks](../../src/adapters/railway-effects.ts).

**4. Schemas generate mechanisms; game rules supply meaning.** Generate codecs, validation scaffolding, canonical hashes, replica field selection, diffs and entity inspection from schemas. Authors still provide conservation/reference invariants, audience/interest policy and semantic migrations. Stable schema names/field IDs and game IDs outlive registration order and backend handles. Save format, content version and wire protocol are separate versions. A migration loads an old envelope into staging, replays its old-rule tail, converts and validates, then atomically publishes with a retained backup. Unsupported/corrupt data fails closed. Never silently create a fresh world over it. Extend [store](../../server/src/store.ts) and [recovery](../../src/world/sync.ts); replace namespace wipes as the normal upgrade mechanism. [Unreal's versioned asset serialization](https://dev.epicgames.com/documentation/en-us/unreal-engine/versioning-of-assets-and-packages-in-unreal-engine) illustrates explicit compatibility handling, not automatic semantic conversion.

**5. Components describe; runtime adapters realize.** Body/collider descriptions create Rapier resources; pre-step systems send intent and post-step systems publish observations. Views read immutable confirmed/predicted state and never feed mesh transforms back into rules. Plug-ins declare dependencies, schemas, systems and assets; a scope owns registrations, requests, entities and resource leases, and can cancel/dispose them in reverse dependency order. Prefabs compile typed authoring into portable data: stable keys, component initializers, relationships, asset references and collider recipes. Keep TSL materials, mesh generation and special presentation code in renderer modules. This extends [asset-loader](../../src/render/asset-loader.ts)'s existing disposal rather than replacing functioning ownership.

**6. Own the game contracts, keep storage replaceable.** My year-end choice is an expanded, tightly scoped E behind these contracts, not a second object ECS alongside it and not a full-engine rewrite. Adopt established scheduling/lifecycle semantics, not a blanket ban on libraries. Run a real bitECS backend comparison after the contracts exist; replace E if it deletes machinery while passing the same behavior, snapshot and prediction tests. A Rust/C++ port reuses schemas, schedules and trace fixtures, not TypeScript source. Library choice is secondary to whether state and effects can be reconstructed without the renderer.

Specific hazards visible in the implementation:

- E's `get` exposes a live object with a readonly TypeScript type; audited access is optional. Queued structural changes are discarded on a thrown system, but prior value writes are not rolled back. Use scoped mutation access and invalidate a failed authoritative transaction; do not call current `world.run` transactional.
- `world.changes(c)` drains marks. An inspector, replicator and save writer cannot independently consume that stream. Introduce revisioned journals/read cursors or one commit fan-out; bounded retention must fall back to a snapshot for lagging readers.
- `railway-replicate` currently despawns an entity when a replicated component disappears. This suits today's fixed sets; generic add/remove needs distinct component removal and entity destruction, reference remapping, validated staged publication and immutable snapshots. A server hash includes private components; compare replicas only over the declared projection.
- Roster ordinals address stacks and site credit. Piles have allocation/tie-breaking rules; sources depend on site completion and age; opening resets through `onApplied`. Preserve these facts explicitly. Moving arrays into a single opaque “ClassicState” component would preserve the split in disguise.

The runtime census orders the railway tick as `lineTick → line2Tick → legTick → cartTick → yardTick → trainTick → tradeTick → worksTick → steelTick → jobClock`. Preserve that graph before regrouping it. Existing `jobClock` reads `JobRun/QJobRun` and writes `Job/QJob`; the target adds equally explicit declarations for resources and non-railway systems. For example, proposed Motor reads InputIntent/SeatAttachment and writes MotorState/BodyIntent; Physics reads BodyIntent and writes PhysicalPose; View reads PhysicalPose and writes SceneRuntime. Physics and View cannot write economy components.

Normalize the callable systems into **scheduled rules**, **command handlers** and **lifecycle handlers**, all with the same access/scope metadata. Command handlers can remain `(context, command) → outcome` functions behind an ordered queue dispatcher; session, departure, resume and supply become typed lifecycle inputs with replay policy. Do not turn receipt lookup into a periodic tick or batch actions by opcode: that would change fallback, resource competition and receipt order. Pure calculations remain ordinary functions.

Cross-cutting proof rule: **new schema hashes need not equal old raw hashes**. During conversion, encode the new world through the old schema/hash projection and require hash-for-hash equality; also compare full canonical values and outcomes to avoid relying on hash collision resistance. Pin new-schema goldens separately. Keep the existing [railway golden helpers](../../test/helpers/railway-golden.ts), [schema fixture gate](../../test/railway-schema.test.ts), [census](../../test/railway-census.test.ts), [world replay](../../test/world-replay.test.ts) and recovery tests. Change the schema gate from “bump namespace” to “version plus proven converter”; never regenerate goldens merely to make a refactor pass.

A future language port also needs explicit safe-integer ranges, overflow behavior, float-bit encoding, string encoding, optional-value representation and canonical iteration in its schema/trace specification. Matching a component's name and fields is insufficient. Game IDs and reference remapping belong to that specification; generational backend handles do not.

## The options the first study dismissed

**Library adoption is a maintenance decision, not only a tick-time contest.** My choice of E is conditional on it remaining a small replaceable mechanism: sorted keyed data, canonical codecs and prediction snapshots are Boogle's actual workload. No library removes the need for authority, saves or domain validation. Conversely, expanding E into an archetype optimizer, worker scheduler or general relationship engine would justify adopting those facilities rather than reimplementing them. The comparison in stage I is required evidence, not a claim that E is fastest.

| Candidate | Actual fit and decision |
| --- | --- |
| [bitECS](https://github.com/NateTheGreatt/bitECS) | Data-oriented storage with flexible component backing; strongest candidate for replacing E's storage. Keep stable game IDs separate from native IDs and sort semantically significant iteration. A row facade can hide a rewrite but can also preserve allocation overhead and duplicate tracking; compare the actual command/prediction workload, not an unrelated entity loop. |
| [Miniplex](https://github.com/hmans/miniplex) | Plain object entities and queries, explicitly no built-in scheduler. Easy conceptual fit for current rows, but it leaves access enforcement, canonical serialization, snapshots and scheduling to us. Reject as the year-end default: it does not remove the difficult mechanisms identified here. |
| [Becsy](https://lastolivegames.github.io/becsy/guide/architecture/systems) | Strong access entitlements and scheduling dependencies align with the target. A credible whole execution-model replacement, not a transparent store swap. It wins if adopting its scoped access/query lifecycle deletes our corresponding machinery; reject a permanent Becsy view world plus E gameplay world. No performance claim without a Boogle port. |
| [Bevy](https://docs.rs/bevy_ecs/latest/bevy_ecs/world/struct.World.html#method.run_system_with) / [Flecs](https://www.flecs.dev/flecs/Systems.html) | Bevy supports registered systems with typed input and output; Flecs manual `ecs_run` accepts a parameter, with results supplied through explicit data. The callable systems are not a fundamental portability barrier. A future port maps components/resources, ordered groups, command buffers and stable IDs; runtime handle and numeric/string encoding differences still require work. |

**Scene/prefab data: yes, for gameplay composition.** A workshop chair's visual asset, collider, seat and lifetime should derive from the same authored record. Keep typed TypeScript authoring, compile a versioned data artifact with deterministic stable keys, and validate references at build/load. Do not serialize closures or a live three.js scene as the game model. Parent-owned dependencies and independent scene units are established in [Godot's scene organization](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html). The reason is consistent headless construction and unloading, not a speculative visual editor.

**ECS events: yes, explicitly buffered.** State deltas cannot represent repeated equal-value events, request outcomes or effect causality. Use typed queues with retention/cursors and replay policy, rather than attaching ephemeral event entities everywhere. [Flecs observers](https://www.flecs.dev/flecs/ObserversManual.html) provide ordered notifications, but notification hooks alone do not define Boogle's acceptance, prediction or rollback semantics. Do not turn every component write into gameplay callbacks; that hides the schedule again.

**Player/components: yes; lockstep Rapier: no by default.** [Rapier's JavaScript determinism contract](https://rapier.rs/docs/user_guides/javascript/determinism/) explicitly permits cross-platform determinism given the same version, initialization and operation ordering; trigonometric initialization outside Rapier can break it. The reason to keep physics outside the integer core is Boogle's input/authority boundary and reconstruction burden, not “physics cannot be deterministic.” Keep owner movement for responsive traversal and server authority for shared outcomes; a competitive anti-cheat requirement or tightly coupled player-body simulation would justify server movement with reconciliation. Componentizing the motor makes that later choice possible without rewriting views.

Shipped-game evidence supports **composition as a complexity tool**, not a universal ECS speed claim: [Timothy Ford's Overwatch GDC session](https://gdcvault.com/play/1024001/-Overwatch-Gameplay-Architecture-and) describes using ECS and determinism for varied networked gameplay; [Mick West's Tony Hawk account](https://cowboyprogramming.com/2007/01/05/evolve-your-heirachy/) describes incremental migration to composed objects. The GDC abstract was read, not the full talk; neither source establishes that Boogle needs their exact engine.

## Where the first study was right, and where I disagree

- **Right:** the railway facade, deterministic integer rules, schema-derived serialization and renderer separation are valuable assets. Porting storage cannot port the substantial renderer-specific view layer. Keyed reads and stable IDs matter more here than fashionable archetypes. No measured performance result from this review supports a library speedup.
- **Wrong objective:** “nothing urgent” and “after the playtest” answer present prioritization. They do not answer which architecture compounds over a year. Consistent construction, mutation, inspection, persistence and disposal are benefits even when today's tick is fast.
- **Wrong coupling:** componentizing classic storage does not require changing authority or wiping saves. Split those migrations and use old-path replay as the oracle. [Replication R3/R4](../plans/replication.md) should consume the common model, not be its prerequisite.
- **Wrong inference about schedulers:** separate fixed/frame groups are normal; independent ordering/lifetime mechanisms are not necessary. Preserve rates and merge the framework. Likewise, input-and-result systems already have external engine equivalents; the real work is making admission, fallback and effects explicit.
- **Too dismissive of player, events and prefabs:** seat grants, mixed callbacks and workshop cleanup already expose the integration seams. Their long-term value is reducing special cases across future mechanics, not lowering current entity counts. Keep disposable view objects, but remove their competing gameplay ownership.
- **Save policy must change:** namespace wipes and cleanup are acceptable development policies, not a sustainable progression game's engine contract. Retain explicit reset as an owner operation; distinguish it from migration. Existing deleted saves cannot be recovered by designing converters now.

## First action and the smallest convincing slice

Start **A + the tune portion of B**, not a wholesale library swap. Preserve the old `createTune` implementation in a test reference, put values/revision in components, adapt existing consumers without changing authority, and derive its inspector and save codec. Run `tune.set` and `tune.commit` through a typed command/receipt boundary, with read-only adapters for their existing site constraints; leave `fill/reset` on the legacy bridge until the dependent stores move. Load an old checkpoint with a pending tune tail, recover under old rules, migrate, reload, and continue the same trace with matching old-projected hashes and receipts. Also show a stale revision rejected, an unload/remount without a duplicate registration, and a dry-run migration diff.

This slice proves data → command → save → inspection across real server and client seams. It does **not** prove dynamic references, whole-engine scheduling or motor feel: the next proof is roster/stacks plus a pile transfer with stable identity, followed by a server-owned seat and its disposable view. Failure to preserve semantics or remove duplicate live state is a reason to revise the contract. Calendar pressure and an outstanding playtest are not reasons to preserve the split architecture. Human play validates that later motor/seat migration still feels right; it is not a gate on this research or headless work.
