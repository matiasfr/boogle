# Graphics settings: preserve the look, scale the work

> **Verdict:** Three presets and six controls; registry and cost switches built, pages not.
> **Top recommendations:** 1. Make Auto a policy, with three explicit presets and a Custom indicator. 2. Expose six controls, not the water laboratory. 3. Use one small registry with owned adapters.
> **Status:** partly adopted. See [plan graphics-switches](../plans/graphics-switches.md).

## Recommendation [D]

1. **Make Auto a policy, with three explicit presets and a Custom indicator.** Add a page through [pause-pages.ts](../../src/player/pause-pages.ts). Quality keeps the active route's full appearance and resolution; Performance keeps its art, uses adaptive resolution and the reduced cosmetic settings below; Battery Saver adds a 30 fps render cap. Auto initially preserves existing desktop/touch behavior, including the new-water mobile ceiling; it must not silently select Performance from a guessed GPU name. Start at the last stable scale, ignore loading/hidden-tab samples and let measured sustained frame pressure adjust resolution. A later automatic effects downgrade requires measured benefit and an owner comparison. Quality/Performance target 60 rendered fps; offer Display for higher refresh. These are proposed caps, not current behavior.

2. **Expose six controls, not the water laboratory.** Presets set the first five; camera comfort remains independent. Show the scene behind the page for live comparison, with Reset and a clear pending-reload state. Exact reduced values below are starting proposals, not measured optima.

   | Control         | Choices and intended effect                                                                                                                                                                                                   |
   | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | Resolution      | Auto / 100 / 80 / 60% of capped device DPR. Softer picture, fewer scene pixels; one controller, not two multiplied sliders.                                                                                                   |
   | Frame limit     | 30 / 60 / Display. Battery Saver = 30; gate rendering, never simulation, networking or input processing. Display follows delivered callbacks, not a promise of 120 fps.                                                       |
   | Shadows         | Standard / Reduced. Keep grounding shadows; initially test half the current map edge. Do not offer competitive visibility-changing shadow removal.                                                                            |
   | Water detail    | Full / Reduced. Initially test caustics updates at 30 Hz while retaining the previous texture. Keep surface geometry, FFT, queries, refraction and underwater boundary intact. Hide when this route has no applicable effect. |
   | Ambient effects | Full / Reduced. Reduce cosmetic spray and underwater snow; later decorative grass only where present. Preserve impact, interaction and navigation cues. Requires emission/draw adapters, not just strength sliders.           |
   | Camera motion   | Normal / Reduced / Off for shake and decorative camera motion. Seed from reduced-motion preference; never let a quality preset reset comfort.                                                                                 |

3. **Use one small registry with owned adapters.** A proposed renderer-independent `src/graphics-settings.ts` describes `id`, bounded choices/default, `audience`, `scope: Local`, availability/reason, persistence, cost category and `applyMode: live | rebuild | reload`. Owners register `read`, `apply`, optional `prepare`, and disposal; presets are maps of those IDs. Return **requested/effective/pending** values in a serializable snapshot. Keep renderer resources in their existing owners and the registry free of debug imports. Order: route defaults → Auto/preset → player overrides → explicit Dev/session overrides. Save validated player choices under `boogle.graphics.v1`, separately from Dev keys; Dev Off removes its overrides and restores player choices. Catch unavailable storage. Adapt [adaptive-res](../../src/features/adaptive-res.ts), [water quality](../../src/render/water/quality.ts) and bounded [water bindings](../../src/render/water/live.ts), without treating every water binding as player-safe.

4. **Make Dev measure actual work removed.** Add Graphics to the existing [Dev tool descriptors](../../src/debug/dev-menu.ts), with feature on/off, restore baseline and a copied settings/route/camera snapshot. Cover shadows/MSAA, caustics producer, spray, snow, shafts/lens, bloom/meter, lights, foliage and lab effects. Distinguish “zero visual strength” from “skip dispatch/draw/pass”; keep geometry/wave/query-off experiments in isolated fixtures. Use [Performance](../../src/debug/dev/performance.ts) for matched, warmed on/off captures: frame intervals and CPU/GPU separately, missing timestamps marked unavailable. Player readout: current internal resolution, optional fps and plain cost labels (“pixels”, “shadow rendering”, “extra passes”), not an invented VRAM bar or percentage saving. Measured deltas belong in Dev with device, scene and sampling conditions.

5. **Integrate the dock and colour work without duplicating owners.** The inspected, uncommitted `codex/dev-dock` plan, `docs/plans/persistent-dev-dock.md`, proposes `registerDockPanel({id,label,load})`, lazy mounts and persisted placement; it is not an established API in this checkout. Mount the same Graphics adapter there; closing a panel must not reset appearance. Keep [water-tuning.ts](../../src/debug/water-tuning.ts) as detailed authoring, sharing underlying IDs where appropriate. The inspected `codex/color-grading-research` report at `61bbf3be` proposes one HDR/AgX output chain and dev comparisons; coordinate there and with [tone-comparison](tone-comparison.md). Exposure, grading, bloom tuning, sky time and tone-map selection stay Dev-only. Neither research track authorizes a new default look or a second post owner.

6. **Build and validate in this order:** registry + unified resolution/cap ownership → real Dev cost switches and safe preparation → six-control Pause page/presets → matched M1 Max appearance/cold-switch checks and representative mobile soak. Verify two peers retain identical gameplay with different presets, including swimming; verify storage/reset and returning from a hidden tab. Stop at the owner's playtest. Update [graphics as built](../game-design/graphics.md) when implemented. Do not build startup stress benchmarks, GPU-name databases, DLSS/FSR/frame generation, a renderer selector, texture packs, player draw-distance/population controls or a permutation for every checkbox. Accessibility contrast/cue colours need targeted readable UI and redundant shapes, coordinated with colour work; a global “colour blindness” filter is not a substitute ([Steamworks guidance, V](https://partner.steamgames.com/doc/accessibility_features?language=english)).

**Existing numbers, with limits.** [Visual target](../proposals/visual-target.md) measured whole-scene queue-drained batches on a shared M1 Max GPU at 2420×1668: baseline 1.0–1.3 ms; grass 1.46/1.56, GTAO 4.77/2.08, SSGI 6.84/7.93, bloom 1.43/1.68 ms (two views). These are **old total scene times, not marginal costs**, predating new water, frozen sky and AgX. Its iPad multiplier is an estimate; its initial summed-timer “50 ms bloom” result was discarded because passes overlap. Do not add GPU render and compute spans or reuse those totals as new-water budgets.

[Water-load-stall](water-load-stall.md) reports roughly 0.88–0.94 s CPU shore solving, 0.10–0.17 s packing, 0.30 s frozen-sky setup and 77 ms spray preparation: startup attribution, not steady-state GPU cost. [Water-metal-cold](water-metal-cold.md) found 4.5–4.8 s reveal freezes; warming real pipelines behind a 16 s deadline reduced the longest reveal gap to 318–400 ms in two coarse runs, with `trueCold:false` and `measurable:false`. This supports preparing selected graphs through [precompile.ts](../../src/render/precompile.ts), not claiming all switches are hitch-free. Stage structural changes behind explicit Apply/reload; keep the previous working settings if preparation fails. Never precompile the Cartesian product of options.

## Web limits that shape the implementation [V → D]

- **Capabilities are not a tier.** [WebGPU](https://gpuweb.github.io/gpuweb/) permits empty/generalized adapter information; names and limits do not reliably identify performance. `timestamp-query` is optional and may be quantized; texture sample counts are **1 or 4**, not 2/8. [detect-gpu](https://github.com/pmndrs/detect-gpu) maps WebGL renderer strings to benchmark tables: useful precedent, not a measurement of this WebGPU scene or current heat. Do not add it to decide Boogle's default.
- **Observe cadence, not advertised refresh.** [rAF](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame) can follow 120 Hz displays and is normally suspended in hidden tabs. Browser/OS policy and power conditions can reduce delivery; WebKit's [frame-rate explainer](https://webkit.github.io/explainers/animation-frame-rate/) is a proposal, not a shipped 120 Hz guarantee. Existing adaptive logic can also mistake a stable GPU-bound 30 fps for a browser cap: test this explicitly. A 30 fps limiter must tell the resolution controller its chosen target and retain uncapped callback timing; otherwise it can misdiagnose its own cap. Do not tie Owner physics/query cadence to skipped render frames.
- **Heat and memory have no universal web budget.** Safari/iOS sustained load can throttle or lose the page/device. Apple's [WebGPU WWDC guidance](https://developer.apple.com/videos/play/wwdc2025/236/) discusses bandwidth, compact data and memory pressure, not a safe per-tab VRAM number. Battery Saver is user intent, not temperature detection. Limit transient targets and dispose unused optional resources; measure sustained play, not only the first five seconds. Hiding a bloom draw while retaining its textures does not recover its memory.
- **Scale pixels before adding an upscaler.** The [three.js responsive-rendering guide](https://threejs.org/manual/pages/responsive.html) explains high-DPI pixel cost. At 60% linear scale there are 36% as many scene pixels, **not a guaranteed 64% frame-time saving**: FFT, CPU, fixed-size maps and output passes remain. Boogle already has adaptive DPR; unify it with the scene ceiling before considering spatial/temporal reconstruction, which adds passes, history and potential ghosting.
- **Keep downloads and persistence boring.** Lazy-load Dev and optional effect modules; don't download/build optional assets merely to switch them off. A scalar/uniform change can be live, target resizing needs allocation, and a new TSL graph/MSAA pipeline needs preparation or reload. Preserve saved choices across reload via versioned, validated [localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage); handle exceptions/private-session loss. It is origin-local, not account/cloud state. Never serialize graphics choices into room operations, saves, Lockstep or presence. Even a Local control must not alter collision, visibility of necessary cues, world population, water forces or gameplay timing.
