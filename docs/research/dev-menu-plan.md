# A Dev menu for fast live playtests

> **Verdict:** One opt-in Dev page in the pause menu, water tuning first.
> **Top recommendations:** 1. Mount Water as the first tool. 2. Make “Go to” a named, reversible test action. 3. Add a Local camera tool with one-click return.
> **Status:** adopted. See [plan dev-menu](../plans/dev-menu.md).

_2026-11-03. Research and recommendation, not implementation approval. Code audited at `9b828d68`; live web sources below. **[V]** means source text/code read, **[S]** means secondary account or indexed abstract only, **[D]** means a Boogle recommendation. No game or device test performed._

**Build one opt-in Dev page inside the existing pause menu, with eight tools below.** Water tuning is its first plug-in, delivered by the separate water track. Prioritize getting to a mechanic, seeing its state, and copying enough context for an agent to reproduce it. Keep cheats in disposable tests. This serves **Toys before chores**, **Clear authority**, and **Small and readable**.

The target is today's [round-4 place](../game-design/place.md): walking path → axe → pack → depot → trains, plus double jump, hook and glide. The [current decision log](../decisions.md#the-shape-of-the-game) replaces global eras with materials and upgrades; a debug stage list must follow that ladder. Debug destinations are testing aids, not approval for the deferred player fast-travel system.

**Where Boogle differs [V/D].** A browser has no attached editor on a phone, reloads can pick up another friend's deploy, and agents need JSON as well as buttons. [DESIGN.md](../../DESIGN.md#pick-how-each-feature-shares-state) distinguishes **Local**, **Owner**, **Host** and **Lockstep**; Rapier is not deterministic Lockstep. Moreover, today's place progression is a temporary co-op snapshot system: [coop.ts](../../src/proto/place/coop.ts) elects the **oldest visible co-op tab**, not necessarily the room lead; [job.ts](../../src/proto/place/job.ts) saves shared/personal slices in room-specific localStorage. Do not confuse that with server-saved Lockstep. The menu must identify both authorities and the build, and report unsupported tools explicitly.

## Hard rules before implementation

- **Live access:** for the current friends-only phase, anyone deliberately opening `?dev=1` may use Local/read-only tools, including owner, friends and agents. It enables a visible Dev entry in Pause for that tab; a bookmark works on phone/iPad. Do not claim this identifies the owner. No name, localStorage value, URL secret or client PIN authorizes shared mutation. The current [process call](../decisions.md#process) keeps one live site; this proposal adds no deployment gate.
- **Shared actions:** normal validated ops may affect shared state only within their existing permission and acceptance rules. Never assign `boogle.sync.world`, hash state or another peer's body. `submitEdit` means queued; report success and spend inventory only on acceptance. Arbitrary grants, skips, resets and movement cheats are disabled in normal rooms. Existing [`tune` validation](../../src/world/rules/tune.ts) accepts `ctx.env.protoRoom`; **`proto-` is not private**, particularly now that `proto-place-coop` is the default. Do not reuse that prefix as the new menu's authorization check.
- **Disposable means isolated:** v1 fixture launch chooses a fresh random room, explicit `proto=place&coop=0`, scoped save keys and a persistent TEST badge; it never imports all of the user's storage or clears all place saves. This is accidental-collision isolation, not access control. No shared cheats on the live server until server-enforced test-room capability/membership exists. Prototype-local stage setup may use its existing handlers only there; any Lockstep fixture edit still uses validated ops on every participant. A private room does not make divergent local Lockstep writes safe.
- **Owner/Host:** teleport only the tester, detach seat/carry safely, clear velocity, validate finite in-bounds landing and retain a return spot; restrict this to the disposable test run initially. A camera bookmark does not move the player. Shared-object reset goes through ownership epochs; Boogler changes go through the actual Host. Place's temporary co-op authority is a separate adapter, never assumed to be the server or the room lead.
- **Pause means input capture:** reuse [`modal.ts`](../../src/player/modal.ts); server world and other players continue. No live `dt` multiplier, `world.tick` assignment or harness `__warp` exposed to shared rooms. Capture a still if the owner wants to examine a frozen image.
- **Owner gate and registry:** this is research only; implementation follows [shipping's plan approval rule](../agents/shipping.md). [Registry debt](../agents/registries.md) growth needs the owner's exact key/list, cap and reason in `APPROVED_DEBT`; agents cannot approve it. Current rules do **not** provide a runtime “owner account” gate or a blanket server-change veto. Reuse Pause's registered action and pad navigation; any new shortcut obeys `registerAction`/`onKey` + guide rules, `wrapAction`, and leaves the required pad slot free. No new suppression/cycle debt to make Dev fit.
- **Off costs nothing extra at runtime:** one small eager gate, no Dev chunk/CSS/DOM, sampler, timer, frame hook, GPU readback or network message when disabled. Lazy-load the shell, then each tool on opening; close/dispose removes its subscriptions and restores overrides. Existing `prof`/boot instrumentation is existing baseline, not a new zero-cost claim. Keep ops/state/rules eager; use entities for visible overlays, no second renderer/loop. Follow [plugins](../agents/plugins.md), [boundaries](../agents/lint-boundaries.md) and [rendering](../agents/rendering.md). Legacy tools without teardown need reload-based enable/disable until adapted.
- **Mixed builds and saves:** carry `BUILD`, `WORLD_NS`, fixture/schema version and effective flags. Disable unsupported commands with a reason. New wire operations are additive/versioned; incompatible development changes require the documented namespace break, never an ad hoc menu protocol. Validate snapshots before clone/restore; never overwrite a live room from a client dump ([mixed builds](../agents/mixed-builds.md), [room safety](../agents/room-safety.md)).

## Recommended first version: eight numbered decisions [D]

1. **Mount Water as the first tool.** A tiny `src/features/dev-menu.ts` gate dynamically loads a shell under `src/debug/`; water owns its panel, defaults and teardown. Only appearance tuning is live-room-safe. Reuse the active [water runtime](../../src/render/water-render.ts); negotiate the panel's interface with its separate track rather than importing prototype settings into production.
2. **Make “Go to” a named, reversible test action.** Derive destinations from [place layout](../../src/place/layout.ts), current frame and [water views](../../src/proto/water/views.ts), with separate player-safe and camera-only poses. It starts/uses the disposable run, never silently advances the ladder. Include Return; normal Get unstuck remains available outside Dev.
3. **Add a Local camera tool with one-click return.** Extend the [fixed-camera hook](../../src/debug/debug-cam.ts) with bounded free movement and explicit restoration of pose/FOV/input. Keep player movement/interactions captured; camera controls work with touch drag, up/down buttons and pad sticks. Do not call it noclip.
4. **Show inspect data and focused overlays.** Use [`inspect()`](../../src/entity/inspect.ts), plus explicit adapters for place and water; begin with nearby colliders/decks and water coverage/query validity, not the entire scene graph. Sampling runs only while shown. Keep GPU field readback off unless explicitly requested.
5. **Combine performance and startup evidence.** Wrap the existing [profiler](../../src/debug/prof-overlay.ts) and [startup recorder](../../src/debug/startup-record.ts); expose Measure, Copy, and Reload with capture. Preserve unsupported GPU values and warm/cold uncertainty; a reload is not a Metal-cache reset.
6. **Make Room health a read-only page.** Adapt [`netdebug`](../../src/debug/netdebug.ts), showing server connection, room lead, place authority, builds, pending/rejected commands and last hash result. Do not label place snapshot agreement “Lockstep verified.”
7. **Give owner and agent the same test report.** Copy build/namespace, effective route flags, tool settings, player/camera pose, fixture ID, inspection summary and recent bounded command results; offer a screenshot download and optional existing input recording alongside it. Provide selectable-text/download fallback. A setup link contains only allow-listed settings/destination/fixture version and asks before launching a fixture; it never executes code, embeds credentials or silently resets a joined room.
