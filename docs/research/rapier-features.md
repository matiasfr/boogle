# Rapier JS 0.19.3 → 0.21.0: what Boogle can use

_Research report, 3 November 2026. Live primary-source research, published npm declaration comparisons for plain and SIMD builds, and Boogle source inspection at `0e4376b161dccd91f1069a38d2a409b1241e08ef`. Recommendations only; no game source or dependencies changed. The separate `rapier-021` job owns the upgrade. No gameplay benchmark or device playtest performed._

## Answer and evidence

**Use the allocation improvements and collision fixes; consider compound edge smoothing only for a demonstrated seam problem. There is little reason to add a new physics mechanic just because of this upgrade.** Most immediately useful work arrived in **0.20**, while **0.21** adds substantial soft-body capability and download weight. Neither version replaces Boogle's controller, train carry, authority rules or authored construction.

The report follows [the research index](README.md), [places-as-modules](places-as-modules.md) and [ultra-water](ultra-water.md). It serves [DESIGN.md](../../DESIGN.md)'s **Small and readable**, **Toys before chores**, **Physics toys are optional fun**, and **Pick how each feature shares state**. The [current decision index](../proposals/boogle-2.md#current-decision-index), its shape-of-game and train entries, and the [round-4 tracker](../plans/round-4-notes.md) take priority over older research: path first, staged efficiency, solid walkable construction, and an owner replay of the corrected loop. This is research, not approval to start another prototype before that gate.

Evidence labels: **[P]** published package inspected; **[U]** upstream source/release note; **[B]** Boogle code/plan inspected; **[H]** proposed benefit, work estimate or experiment. Source inspection establishes an API or implementation, not successful gameplay. All estimates below are engineering judgement, not measured delivery times.

### How the API comparison was done

Packed **six exact packages** into `/tmp/boogle-rapier-research`, without installing into this worktree: `@dimforge/rapier3d` and `@dimforge/rapier3d-simd`, each at 0.19.3, 0.20.0 and 0.21.0. Compared every `.d.ts` by relative path at the endpoints and across each intervening release; read affected JS wrappers for buffer and raw-call semantics. Reproduction: `npm pack @dimforge/rapier3d@0.19.3 @dimforge/rapier3d@0.20.0 @dimforge/rapier3d@0.21.0 @dimforge/rapier3d-simd@0.19.3 @dimforge/rapier3d-simd@0.20.0 @dimforge/rapier3d-simd@0.21.0 --pack-destination <scratch-directory>`. Extract each archive separately before diffing. [P]

There are **43 declaration files in 0.19.3 and 45 in 0.21.0**. At the endpoints, **27 common files differ**, including two generated WASM declarations; the two added files are `dynamics/soft_body.d.ts` and `soft_body_set.d.ts`. Plain and SIMD declarations are byte-identical in 0.19.3 and 0.20; in 0.21 the sole difference is ordering of two timing methods in `rapier_wasm3d.d.ts`, with no signature difference. This supports API interchangeability, **not** bit-identical trajectories. [P]

### SIMD and download cost

Rust's removal of the old `simd-stable` feature does **not** make the npm variants redundant. The [tagged build generator][generator21] still emits `+simd128` / `--enable-simd` for the SIMD package and not the plain package. Keep Boogle's existing SIMD-first dynamic import and plain fallback in [backend-rapier.ts](../../src/physics/backend-rapier.ts), with matching versions. Neither selected flavour is the separate enhanced-determinism build. [U/B]

These are **local measurements of published files**, not performance claims. They sit outside the upstream-performance table deliberately. Bytes are uncompressed `rapier_wasm3d_bg.wasm` lengths; npm `.tgz` sizes are not the browser's WASM transfer size. [P]

| Version | Plain WASM bytes | SIMD WASM bytes |
| ------- | ---------------: | --------------: |
| 0.19.3  |        1,570,176 |       1,622,757 |
| 0.20.0  |        2,021,200 |       2,196,730 |
| 0.21.0  |        3,082,103 |       3,292,228 |

0.21 is approximately twice the old raw WASM size. Its [build template][build21] enables FEM for both flavours, but the exact contribution of FEM versus other changes was **not** isolated. JavaScript tree-shaking does not remove individual features from an already-compiled WASM binary. Normal successful loading selects one flavour; the fallback can cause a second request after a failed SIMD load. Actual compressed deployment size, download latency, compile/startup cost and peak memory remain unmeasured. No custom slim WASM build is recommended without evidence that this cost matters. [P/H]

## Boogle integration findings for the upgrade owner

These are review notes for `rapier-021`, not duplicate implementation tasks.

- **Three concrete compile/API seams:** [backend-rapier.ts](../../src/physics/backend-rapier.ts)'s `world.narrowPhase.contactPair` needs `world.bodies`; `manifold.raw.normal()` no longer returns a raw vector to free; `h.time_of_impact()` on a raw sweep hit is replaced by `getComponents(buffer)` with TOI at element zero. The [published wrapper](https://unpkg.com/@dimforge/rapier3d@0.21.0/geometry/toi.js) confirms the buffer layout. Preserve the facade's distance-in-metres result and existing query filters. [P/B]
- **Train workaround has narrower meaning now:** [crossing/index.ts](../../src/proto/crossing/index.ts), [place/index.ts](../../src/proto/place/index.ts) and [water/index.ts](../../src/proto/water/index.ts) turn player CCD off. In the new engine that still excludes kinematic/dynamic sweep targets, but fixed scenery remains swept. The old downhill-deck bug concerns a moving target; the upgrade's fixed-target cache fix is a different bug. Neither establishes that the train workaround can be removed. [B/U]
- **Contact policy can change without a wire change:** `touching()` accepts distances at or below 0.005; [groundPlayer](../../src/entities/player/state.ts) uses normals for coyote time. Prediction distance is now larger. Preserve that gameplay filter unless evidence calls for tuning, and compare ball bounce, stair/terrain grounding, descending decks, construction collision replacement and camera sweeps. The safety-net comment claiming no CCD in [physics.ts](../../src/physics/physics.ts) is already stale relative to the backend; it is not a reason to delete `catchFallThrough`. [B/H]
- **Mixed builds:** keep physics Owner and existing pose messages unchanged. Different solvers may yield different trajectories after a ball ownership transfer; this is a feel/authority-continuity risk, not a new deterministic-world hash mismatch. New jointed/soft gameplay state would need an explicit sharing design and additive/versioned messages under [sync](../agents/sync.md) and [mixed-builds](../agents/mixed-builds.md). No automatic namespace bump is implied by this documentation or package upgrade. [B/H]

## Ranked recommendations

Size: **small** is roughly one backend-focused change; **medium** adds a facade capability and one consumer; **large** crosses physics, presentation, lifecycle and possibly authority. The day's work estimates exclude waiting for the owner and are provisional. Every runtime candidate still needs the existing look/feel workflow; this report did not run it.

### 1. Reuse body and manifold outputs — worth doing after the upgrade

**Gain:** less temporary-object churn during walking, riding and ball play; probably invisible until it prevents a hitch. In `pull()`, pass each mirror's existing position, quaternion, velocity and angular velocity into the new getters, preserving the previous-position copy before writing. Use `manifold.normal(reusedVector)` for the contact callback. The [published body wrapper](https://unpkg.com/@dimforge/rapier3d@0.21.0/dynamics/rigid_body.js) writes through a shared scratch buffer into the target, so this also avoids the old return-vector allocation path. Four body-result objects per moving body per fixed step can be avoided by inspection; that is allocation accounting, not a measured frame-time saving. [P/B/H]

**Files / size:** [backend-rapier.ts](../../src/physics/backend-rapier.ts), `pull()` and `contactManifold()`; **small, less than a day**. No public facade change needed. Coordinate with `rapier-021`, which already must repair the raw normal call. **Risks:** low feel risk if copy order is preserved; no wire change; no extra WASM beyond the upgrade. Do not assume the new query target removes input-WASM allocations: [BroadPhase.castShape](https://unpkg.com/@dimforge/rapier3d@0.21.0/geometry/broad_phase.js) still constructs raw inputs. Keep the cached camera sweep until a measured simplification wins. **Owner call:** no new design call; compare allocations and identical intended motion using the existing tools. [H]

### 2. Take the collision fixes, preserving movement tuning — worth taking through `rapier-021`

**Gain:** fewer missed grazing contacts around cliffs and thin construction, and correct CCD targets after scenery changes. [Parry's shape-cast fixes][parry30] fit [camera-arm.ts](../../src/player/camera-arm.ts) and the off-origin [place movement queries](../../src/proto/place/moves.ts); the [fixed-target cache correction](https://github.com/dimforge/rapier/commit/d90dd9569d74) fits newly laid structures. These are expected benefits, not reproduced bug fixes in Boogle. [U/B/H]

**Files / size:** the upgrade's [backend](../../src/physics/backend-rapier.ts); verification consumers are [platforms.ts](../../src/physics/platforms.ts), [rail.ts](../../src/proto/place/rail.ts), [train-load.ts](../../src/proto/place/train-load.ts), [player](../../src/entities/player/state.ts) and [ball](../../src/entities/ball/state.ts). **Small additional research follow-through; runtime verification belongs to the upgrade job.** **Risks:** medium feel risk from restitution/contact changes and fixed-scene CCD; mixed-build handoffs can change motion; package-wide WASM cost above. Do not spend this gain by removing fall guards, increasing speeds or changing the 60 Hz step. **Owner call:** none to preserve existing behavior; intentional bounce or traversal retuning needs the usual owner feel judgement. [H]

### 3. Test compound edge correction on one troublesome solid — conditional, not a bulk conversion

**Gain:** a ball or player crosses the join between collision pieces without an invisible ridge. 0.20's `ColliderDesc.compound` and 0.21's `CompoundFlags.FIX_INTERNAL_EDGES` permit a single collider whose touching convex parts are treated as one union. Boogle currently attaches separate colliders for `Shape[]`; that already supports multipart bodies, but it is not this new compound shape. [Collider declarations][collider20], [0.21 flags][shape21], [backend](../../src/physics/backend-rapier.ts). [P/B]

**Files / size:** [engine.ts](../../src/physics/engine.ts)'s shape contract, [backend-rapier.ts](../../src/physics/backend-rapier.ts)'s `colliderDesc/buildColliders`, and one selected [train-load.ts](../../src/proto/place/train-load.ts) or [land.ts](../../src/proto/place/land.ts) assembly; **medium, about 1–3 days** including comparison. Preserve `forEachStatic` consumers such as [guest/collision.ts](../../src/guest/collision.ts), mass distribution and per-collider camera thinness classification. A compound handle cannot preserve every previous thin-part filter automatically. Start only with a reproduced internal seam: [rail.ts](../../src/proto/place/rail.ts)'s documented outer-deck-edge creep is not that problem. **Risks:** medium feel/geometry risk; no wire shape change for unchanged geometry, but old/new collision response can differ; no additional WASM beyond 0.21, and runtime hull decomposition can introduce load stalls. **Owner call:** no new mechanic call for a faithful seam fix; approval needed if simplified geometry changes accessible paths. [B/H]

This follows normal engine practice: [Unity compound colliders](https://docs.unity3d.com/6000.0/Documentation/Manual/compound-colliders-introduction.html) combine shapes under one rigid body; [Unreal simple/complex collision](https://dev.epicgames.com/documentation/en-us/unreal-engine/simple-versus-complex-collision-in-unreal-engine) distinguishes simulation proxies from detailed query meshes; [Godot collision shapes](https://docs.godotengine.org/en/stable/tutorials/physics/collision_shapes_3d.html) recommends primitives for dynamic objects and supports V-HACD generation. Boogle should retain authored boxes/balls where they work and preprocess complex hulls if eventually necessary, not decompose every rendered building during startup. These engine comparisons support the collision-authoring choice, not a claim that their internal seam algorithms match Rapier's. [U/H]

### 4. Accept the mostly-static broad-phase savings; measure before adding sleep machinery

**Gain:** lower CPU overhead as solid trees, buildings and rails accumulate, without changing what a player does. Early collision-group filtering matches [physics.ts](../../src/physics/physics.ts)'s scenery masks; same-parent filtering fits multi-piece bodies. These engine improvements arrive through the upgrade automatically. [Rust changes][rust20], [implementation PR](https://github.com/dimforge/rapier/pull/973). [B/U/H]

**Files / size:** [backend-rapier.ts](../../src/physics/backend-rapier.ts), existing profiling tools and a representative constructed [place](../../src/proto/place/land.ts); **small measurement pass, no new optimization implementation justified yet**. Separate step time from Boogle's JS push/pull work. **Risks:** default solver feel still needs upgrade verification; no new mixed-build format; shared package-size cost. **Owner call:** no design call to measure. Defer a sleeping-policy change: the backend disables sleep and writes awake velocities/forces every step, so toggling `canSleep` alone will not deliver resting-pile savings. Revisit only when a real persistent-prop scene is expensive, with wake/write rules and ownership recovery explicitly designed. The [loose-log prototype](../../src/proto/haul/loose-logs.ts) is not permission to add a permanent physics pile to the core loop. [B/H]

### 5. Use motor-force limits for one optional articulated toy — defer until its play question exists

**Gain:** a powered gate or springy crane arm could visibly yield when a friend blocks it instead of forcing its authored path. New frame setters, separate local axes and spherical motors make differently oriented parts easier to join; a motor force cap bounds their push. [0.20 joint declarations][joint20]. These are genuinely newer APIs, but ordinary revolute/rope/spring joints predate the upgrade. [P/H]

**Files / size:** a small joint lifecycle API in [engine.ts](../../src/physics/engine.ts) / [backend-rapier.ts](../../src/physics/backend-rapier.ts), then a bounded experiment at [pair.ts](../../src/proto/place/pair.ts) or [forge.ts](../../src/proto/place/forge.ts); **large, several days for a toy, longer for shared production behavior**. The current crane and beam are authored motion, not joint simulations. **Risks:** high feel change and possible trapping/flinging; one connected mechanism needs coherent authority rather than independently owned parts fighting; new state cannot silently replace existing pose fields; no incremental WASM download, but extra solve work. **Owner call:** yes for a new toy or replacement of reliable construction animation. The [round-4 swing-hook request](../plans/round-4-notes.md#abilities-and-movement) already has its own gameplay goal; it does not require spherical motors or a soft rope. Prove that swing with the simplest constraint/control model first. [B/H]

### 6. Reserve soft bodies for a small optional squashable prop or decorative rope — defer gameplay use

**Gain:** a lumpy parcel squashes between friends, or a slack crane cable drapes naturally. `SoftBodyDesc.rope/cloth/volumetric`, pinned particles and clusters are present in the actual 0.21 npm API. Constraints and shape matching offer a simpler starting point than FEM; the [Dimforge soft-body article][soft-post] describes FEM as more expensive and warns of first-release edge cases. Do not conflate an existing distance-limiting `JointData.rope` with a colliding, many-particle soft rope. [P/U/H]

**Files / size:** [engine.ts](../../src/physics/engine.ts) and [backend-rapier.ts](../../src/physics/backend-rapier.ts) need owned soft-body creation/disposal and particle/mesh reads; a purely visual first consumer could be [forge.ts](../../src/proto/place/forge.ts). **Large: several days for an isolated visual proof; shared interactive deformation is a separate multi-day design/integration track.** **Risks:** high if it affects collisions, low gameplay risk if strictly decorative; particle/topology state does not fit the existing few-number rigid-pose presence contract, and tearing complicates handoff/rejoin; the standard binary already pays its compiled size, while using it adds CPU, transfer and mesh-update cost. **Owner call:** yes before new soft-body gameplay; a decorative cable remains a proposed art experiment. Prefer the current authored cable if the difference is not visible. Never make bridge access or mandatory cargo depend on an unproven soft-body solver. [B/H]

## Things that look relevant but aren't

- **Nexus GPU physics:** a different engine; Boogle's WebGPU renderer does not put Rapier's WASM solver on the GPU. [Dimforge Q3][q3]
- **Native 8-lane SIMD and multithreaded speedups:** native feature/backend claims, not extra lanes or workers automatically enabled by `rapier3d-simd`. [Build generator][generator21]
- **Deterministic physics for railway saves:** neither selected npm flavour is the deterministic one, and [Boogle explicitly keeps physics out of Lockstep](../../DESIGN.md#pick-how-each-feature-shares-state).
- **Voxels and terrain destruction:** voxel APIs and sparse storage already existed at the baseline; the current game uses authored terrain and construction, not a new voxel-world mandate. [Old notes][old-notes], [land.ts](../../src/proto/place/land.ts)
- **Rapier character/PID controller replacement:** older APIs; the player already has custom velocity steering, jump shaping, swimming and deck carry. [Old notes][old-notes], [player](../../src/entities/player/state.ts)
- **Raycast vehicle controller:** older API with new upstream fixes, but Boogle's [soapbox](../../src/proto/soapbox/index.ts) is a steered fixed-rotation sphere, and trains follow authored routes; adopting suspension is a redesign.
- **More PGS iterations everywhere:** 0.21 adds per-body control, but no diagnosed unstable joint/pile currently justifies spending it globally. [Body declarations][body21]
- **Rust quarantine reports, `ContactForceEvent.started`, geometric-mean friction and richer subshape hits:** not exposed as equivalent public JS APIs in the checked declarations; do not promise those controls from the Rust changelog. [Event declarations][events21], [combine enum][combine21], [ray declarations][ray21]
- **Two-sided mesh correction everywhere:** useful for a genuinely two-sided thin surface, not a replacement for solid bridge boxes or the existing trimesh flags. [Shape declarations][shape21], [backend](../../src/physics/backend-rapier.ts)
- **FEM cloth for the glider, full Buddy ragdolls or deformable trains:** technically possible directions, but disproportionately large changes to established movement, rendering and shared state; no approval follows from an engine feature. [Soft-body API][soft21], [current decisions](../proposals/boogle-2.md#the-shape-of-the-game)

## What remains unconfirmed

- No Boogle old/new physics timing, GC trace, real-time feel, mixed-build ownership-transfer run or device test was performed. The existing backend's historical SIMD speed comment is not new evidence for 0.21.
- No exact compressed deployed size, startup/compilation cost, peak memory or soft-body runtime budget. Raw WASM sizes are verified; feature-by-feature size attribution is not.
- No publication Cargo.lock for 0.20/0.21 was found. Package `gitHead`, tagged manifests and binary source paths agree on the mapping above, with the explicitly documented baseline lockfile discrepancy; this is not a reproducible upstream build attestation.
- Rust subshape metadata and other unbound knobs were not assumed to exist in JS. No live demos were played and no talk was claimed as watched.

The smallest useful follow-up is recommendation 1 after `rapier-021`'s compatibility fixes, plus that job's collision/ride verification. Recommendations 3–6 remain conditional or deferred; they do not expand the round-4 work order.
