# Places as modules: two shores, one world

> **Verdict:** A place is the unit of content, a chunk of residency, a room of simulation.
> **Top recommendations:** 1. Introduce explicit place identity and local authoring before replacing home — M, first. 2. Make place construction reversible through entities — L, first architectural risk. 3. Replace the global ground and square-bound contracts — L, before travel.
> **Status:** adopted. See [plan mainline-architecture](../plans/mainline-architecture.md).

_Research report, 2 November 2026. A codebase audit of Boogle's single-grid assumptions and the smallest architecture for two authored places linked by a kilometre-scale railway, with nearby collision and distant silhouettes. Inspected checkout `5f8b900991aed4dab0228e97446205af2729cabd`, Node 24.11.1, three r187 and Rapier 0.19.3; live engine documentation checked on the report date. Documentation only: no game code changed, no browser/physics experiment or device benchmark performed. Recommendations are proposals, not an approved implementation plan._

## Answer and evidence

**Make a place the unit of authored content, a chunk the unit of residency, and a room the unit of shared simulation.** Keep one renderer, one scene, one Rapier world per tab and one server-hosted lockstep world per room. Two terrain definitions, two cheap silhouettes and one explicit elevated rail connection are sufficient; a larger global height grid, a room per island and a general open-world engine are not prerequisites.

The largest job is **removing the assumption that importing a module creates the one permanent world**. The current physics facade already accepts multiple translated heightfields. The harder parts are singleton ground queries, boot-time POI/prop creation, global hooks without teardown, cell-addressed items, recovery, and view code that creates every shared object whether it is nearby or not. **Hypothesis H1:** explicit place factories and bounded residency will solve this more cheaply than stretching the global grid or implementing general spatial streaming first.

Keep today's island at the origin during the first proof, and put a second authored landing elsewhere. Changing which place is called home then becomes a world-layout/arrival decision. Moving the old island is a separate, harder proof because caves, the guest, toys, sources and NPCs contain authored absolute coordinates. The owner's [decision log, open questions 17–18](../decisions.md) has not settled the old island's role or The Boogler's location. This report does not settle them.

Serves [DESIGN.md](../../DESIGN.md): **Small and readable**, **Telegraph everything**, **Designed for drop-in, drop-out**, **Leave something for the next visitor**, and **Physics is never lockstep**. No principle change is proposed.

### What `home-land.json` and the server really mean

[home-land.json](../../src/world/home-land.json) contains `{ n, layout: { trees, perches } }`, **not heights, terrain tiles, collision or water state**. The browser [game-world.ts](../../src/world/game-world.ts) installs rules eagerly with `n = GRID_RES` and empty arrays, then log sources/gifts fill the arrays before tick 1. The server's [host/land.ts](../../server/src/host/land.ts) reads the pinned JSON. [walk-layout.ts](../../src/features/walk-layout.ts) restores those pinned cells under `?layout` so a visual layout cannot silently change server inputs. [world-inputs.ts](../../dev/scenarios/world-inputs.ts) compares the browser with the pinned land and separate state/op-order fixture. Tests, headless sim, peer-test and layout export also consume it. [L]

The current rules are `gifts, roster, stacks, piles, sites, sources, bank, ball, tune, opening`, in that order. Gifts/piles consume grid addressing; sources consume the palm list; ball has its separate bound. Roster/stacks are not terrain systems. Sites/bank/tune/opening depend on the single ordered `ROUTE`/age economy, not a sampled heightfield, and many of their edits carry meaningless `i:0,j:0`. The sync envelope checks integer i/j but has no universal `land.n` extent check; individual rules validate their own domain. [rules/index.ts](../../src/world/rules/index.ts), [types.ts](../../src/world/rules/types.ts), [sync.ts](../../src/world/sync.ts). [L]

Therefore **streaming terrain does not require streaming lockstep or running Rapier on the server**. The room server already ticks and saves a small logical world independently of geometry. Sending only nearby shared state would require a different hash/subscription design; it is not a free consequence of place modules and is not needed for this proof. [I]

## What the off-origin prototypes prove, and what they bypass

Only **place** is centred at x = 1000. **Crossing** starts at `(52,-12)` and extends predominantly in +z. Both remain Local prototypes; they are not two networked place modules. [L]

- [place/layout.ts](../../src/place/layout.ts) supplies an x offset and authored paths/rail elevations. [land.ts](../../src/place/land.ts) bakes a 520 m, 261-sample, 2 m field, adds world offsets to float32 render vertices and installs another heightfield at `(740,0,260)`. It uses its own `H` sampler, one uncullable terrain mesh, and a far landmark assembled eagerly. This proves the facade can _construct_ off-origin land; it does not prove residency or portable local-space rendering.
- [place/index.ts](../../src/proto/place/index.ts) sets `softWall.at = Infinity`, disables player CCD, adds a camera-ground constraint, suppresses old haul interactions, teleports to its own spawn, and lifts the player above its own ground if the singleton query placed them beneath it. It does not replace the game's shared gift/pile/ball/return-space contract. Its local economy, saved prototype state and clocks are not server authority.
- [crossing/world.ts](../../src/proto/crossing/world.ts) builds the route/landmarks at once, with solid deck/station pieces and decorative distant masses; it is not a streamed landing island with complete collision. [index.ts](../../src/proto/crossing/index.ts) disables the wall/CCD and provides a nearest-line recovery action after falling into sea. [line.ts](../../src/proto/crossing/line.ts) uses explicit rail y and locally computed trig/arc tables, which cannot simply be moved into lockstep code.
- [crossing/sky.ts](../../src/proto/crossing/sky.ts) changes near to **0.25 m**, far to `fogFar × 1.3`, overrides fog after the daily sky update and adds four coarse sea rectangles around the original ±650 m plane. Default fog **180–3600 m** yields far **4680 m**; the 4 km variant uses fog far **9200 m**, camera far **11960 m**. Place reuses this, then changes fog to **320–1700 m**; its optional light look changes it again to **170–1500 m**. There is no single production atmosphere policy here.
- [crossing/sea.ts](../../src/proto/crossing/sea.ts) blends the original island's depth to a constant **14 m** outside `HALF ± 20 m` and calms local vertex waves around the old region. Consequently place's new coast does **not** get its own bathymetry/shore foam from this graph. Its world-position glitter is reusable; the home-specific depth switch is not.

The default world's original terrain, props and unrelated lifetime hooks still exist when these flags run. Neither prototype replaces them with an unloaded silhouette. No new runtime claims are made from this inspection. [L/U]

## Smallest viable design

### Data and coordinate contract

Use three small layers, with proposed filenames rather than new files in this change. **[I]**

1. **Headless content:** `src/places/types.ts`, `src/places/old-island/definition.ts`, `src/places/home/definition.ts`, and `src/places/catalog.ts`. A place exports stable identity/content revision, local bounds, terrain patch specification, authored surfaces/structures, POIs, source/perch/socket IDs and safe arrival points. It does not import the renderer, register callbacks, install rules or create bodies. Pure site/blueprint builders remain reusable.
2. **World arrangement:** `src/places/world-layout.ts` assigns each instance an ID and translation, chooses `startPlace/startAnchor`, and connects named rail sockets. Keep axes +x east/+z south and one sea datum. Use translation only initially; arbitrary rotation/nonuniform scaling adds heightfield, shader and authoring complexity without serving the two-place question. Render buffers stay local; all physics/query placement crosses the same transform. A definition can be instantiated twice with **different instance IDs**.
3. **Local realization:** `src/places/residency.ts` owns records, readiness and retained resources; `src/entities/place-chunk/{state,view,index}.ts` owns resident mesh/body lifetimes. Definition and state remain available when views unload. A thin `src/features/places.ts` starts the service, with the normal entity glob registering kinds. If frame scheduling needs a new service allow-list entry, justify that single service in `eslint.config.js`; don't add a new loop or suppression.

Do not make `src/sim/` import the new presentation/authoring folder: current lint forbids it. Shared gameplay catalogs belong in a pure `src/sim/place-catalog.ts` or generated plain input passed through `Land`; rendering definitions may reference those IDs. The server imports only that small catalog/input. Geometry generators using trig stay outside lockstep; canonical route samples/lengths required by the schedule are baked inputs, or are computed with permitted deterministic arithmetic. Never derive source IDs or shared rail lengths from which mesh has loaded. [I]

Two distinct query contracts suffice initially:

- `terrainAt(worldX, worldZ)` selects a known place/patch by bounds, transforms to local coordinates, and returns a tagged hit or **no land**. Keep cheap patch height sampling; do not fake no land with an edge cell. Explicitly resolve overlapping patch priority. Match triangle interpolation to rendered/Rapier diagonals; today's bilinear sampler is not generally identical on twisted cells.
- `surfaceBelow(worldX, y, worldZ)` uses resident physical surfaces for contact-sensitive work and returns surface/owner identity plus height/normal, or **not ready/no hit**. Spawning uses an authored anchor and awaits its collision instead of treating either absence as seabed. Keep cave queries and camera constraints in a removable registry, not nested permanent global wrappers.

Retain legacy `(i,j)` only as `(placeId, patchId, i,j)` with a **fixed gameplay lattice** while old gift/pile rules need it. Visual resampling must never change that lattice. For new source/station/plot interactions use stable feature IDs; for arbitrary rail-deck drops choose a surface ID and local integer position, since a sea crossing has no terrain cell. Do not force rail gameplay into a giant rectangle to make `pile.drop` fit. The first proof can retain old toys in the original place and introduce only the connection's required IDs; making every toy portable is an explicit subsequent migration, not a hidden assumption. [I]

### Residency that can actually be torn down

**Start with one collision unit per modest island and several units for the long bridge.** Existing 51-cell render tiles can remain within the island unit. Split terrain collision into smaller patches only when loading time or resident cost demands it; render tile size is not automatically the correct collider size. Lightweight height/query data may remain CPU-resident for both places initially. This avoids a chunk-seam project before measuring one translated field. **H2:** two such heightfields with distance-managed detail can meet the first crossing's budget without terrain-collider subdivision; this needs Mac and M4 measurements. [I]

Always keep cheap world-space proxies for both shores. They depict the same shape, socket and major growth state as detailed content, with no distant bodies, small lights, NPC updates or dynamic shadows. Their presence is independent of whether detailed content is fetched. Initial policy can have only **proxy / resident detail**, with hysteresis; a middle LOD is optional after evidence. [I]

Residency records should distinguish **requested → prepared → collision-ready → active → retiring**. These are service states, not lockstep events. Factories need an explicit returned handle and cleanup for entities, resources, interactions, platform registrations, cave/ground/water overrides, obstacle indexes, sounds and lights. `despawn` removes only that entity's mesh/bodies and calls its disposal; it does not recursively despawn child entities or dispose shared materials automatically. `defineKind`, presence hooks and physics hooks register once per kind because they currently lack unregister APIs. Do not register them on every visit. Keep module code cached; release expensive instance data/resources, not an imaginary unloaded ES module. [entity.ts](../../src/entity/entity.ts). [L/I]

Loading sources are the local player, their predicted movement, the occupied train/layer, a pending return/teleport anchor, and any **locally simulated Owner/Host object**. A player-only radius is insufficient: a ball left behind may still be owned here, and the lead tab still runs The Boogler even after travelling away. Initially pin the small affected region until the object settles or authority changes. Do not silently stop its simulation when its mesh disappears. Remote player presence alone does not require every tab to load a remote island's static collision. [I]

For the first **1.2 km / 20 m/s** connection:

- Keep the simple bridge's collision spine, both minimal arrival decks and safe recovery anchors resident for the first proof; render distant spans in coarse batches. Detailed island collision loads near the player. A few primitive bridge bodies cost much less than a sea-sized heightfield and eliminate an avoidable first streaming hazard. Bound their count and measure it.
- Prepare the next place on departure, then activate within a distance based on measured readiness: `lead distance >= speed × (p99 preparation time + safety time)`. For an illustrative 3 s load and 2 s margin, that is **100 m** at 20 m/s, before accounting for collider extent, camera arm and off-deck travel. These are not measured timings or recommended fixed radii.
- Keep the departure shore long enough for a turnaround/jump and use larger unload than load thresholds. Cancel stale preparation results by generation token. A failed/late load leaves the old safe region/proxy usable; it must never remove the occupied deck.
- Cold return/teleport waits for its destination collision before placing the body. Local boarding can wait for essentials; an already running shared train cannot pause its timetable on just one tab. Thin, bounded landing essentials and early prefetch are the first protection; a missing floor during a ride fails the proof.

Later, if bridge bodies become material, stream intervals by route arc length and occupied-platform reach, not merely Euclidean distance to the camera. Keep the physical query radius larger than the interaction/camera/contact reach. Physics deletion must occur at a safe lifecycle boundary; do not replace a floor beneath a standing body just because render LOD changed. [I]

## Rendering and numerical limits at distance

### Precision: three different problems

**Coordinate precision.** JavaScript numbers are doubles, but render buffers and Rapier's height/trimesh arrays use float32. Adjacent float32 spacing is approximately **0.061 mm at 1000 m**, **0.122 mm at 1200 m**, **0.244 mm at 4000 m**, and **0.977 mm at 10000 m**. These are calculated representation steps, not bounds on solver or matrix error. Godot's [large-world guide](https://docs.godotengine.org/en/stable/tutorials/physics/large_world_coordinates.html) explains why precision degrades at powers of two and why double scalar values do not make all vector operations double precision. **H3:** 1.2–4 km needs no floating origin yet; compare identical deck/ball/foot contacts at several offsets before accepting that. [L/V/I]

Keep vertices place/chunk-local so future camera-relative rendering remains possible. It does not automatically make global Rapier bodies local. A future origin rebase would need all bodies, previous/interpolated poses, platform frames, camera, particles, cached landing points, query indexes and shader phases updated coherently; network/state coordinates must retain stable world meaning. Do not implement that machinery as insurance before evidence. [I]

**Depth precision.** [scene.ts](../../src/render/scene.ts) sets camera **near 0.1 / far 1500 m** and enables neither reversed nor logarithmic depth. The installed r187 `PassNode` creates a depth texture; `WebGPUTextureUtils` maps its default unsigned-int depth to `depth24plus`, and changes floating depth to `depth32float`. `PassNode.setup` explicitly selects `FloatType` for reversed depth. This was source-inspected, not queried from a live GPU. [L]

For an illustrative conventional **24-bit fixed** depth buffer, `delta-z ≈ z²/(near × 2²⁴)` gives **0.86 m at 1.2 km** with near 0.1, versus **0.34 m** with near 0.25; at 4 km the latter is about **3.81 m**. These figures are depth along the view axis, not distance from world origin. They do not establish the actual precision of a `depth24plus` implementation. [I] [NVIDIA's analysis](https://developer.nvidia.com/blog/visualizing-depth-precision/) explains the benefit of reversed Z with floating depth; [three's API](https://threejs.org/docs/pages/WebGPURenderer.html) exposes `reversedDepthBuffer` and documents that it takes precedence over logarithmic depth. [V]

Evaluate reversed depth in the existing single HDR/MSAA pipeline before extending the production far view. Preserve close-camera fit; do not copy 0.25 blindly. Audit depth-reading effects and `scene.ts:toScreen`, whose `ndc.z > 1` behind test assumes ordinary projected depth. Validate water intersections, shadow bias and sun occlusion on actual WebGPU. It is a rendering compatibility change, unrelated to Rapier float accuracy. [I/U]

**Stored coordinate precision.** Terrain centimetres, saved ball centimetres, item cells, 1 cm player-presence rounding and 0.1 m ping rounding are deliberately different representations. A new renderer depth mode fixes none of their range limits or addressing aliases. [L]

### Shadows, sky and fog

The **72 m wide** sun shadow box already follows the player in [entities/camera/index.ts](../../src/entities/camera/index.ts); it is not fixed over the origin. Its 1024² touch / 2048² desktop maps correspond to roughly **7.0 / 3.5 cm per texel** across that width. Keep this local coverage. Stretching it to kilometre spans would destroy nearby detail. Far proxies should receive inexpensive directional/ambient shading but not force distant dynamic shadow coverage. Check moving-window shimmer and vertical coverage around tall cliffs before adding cascades. [L/I]

Default fog reaches its full fog colour at **520 m**, and [sky.ts](../../src/render/sky.ts) rewrites it each frame, including underground transitions. Raising only `camera.far` cannot reveal a destination 1.2 km away. Centralize the distance/underground policy and preserve readable silhouette contrast over both shores; use the same atmosphere on proxies and detail. **H4:** a restrained long-range haze with local shadows is enough for the first crossing without an extra far-scene render pass. [L/I]

The 700 m camera-following sky sphere has depth writes disabled and renders early, so it need not geometrically enclose the world. However, sun/moon discs are placed **600 m** away, transparent, depth-tested with no depth writes; distant islands can lie behind them in depth. Inspect their occlusion explicitly rather than merely enlarging the sphere. Fog-off pitch-black proxies would avoid one problem while making the destination look detached. [L/I/U]

### Water

[water-render.ts](../../src/render/water-render.ts) has two separate limitations: the fixed **1300 × 1300 m** sea mesh and one **409²** height texture addressed by `(worldX + HALF, HALF - worldZ)`. Packed shore heights span **−10…10 m**, with default edge clamping; outside the grid it cannot discover another island. The physical [water-field.ts](../../src/physics/water-field.ts) already represents common sea level plus a cave override, not a world-sized fluid sim. [L]

The smallest production water change is one shared ocean surface with bounded near tessellation/coarse horizon coverage, and **explicit per-place shore fields**. With two places, sample two bounded fields or use local shore patches; return open-water depth outside valid bounds. Do not allocate high-resolution empty sea. Keep sampling/derivatives outside divergent TSL branches and prevent overlap/double shading between near and far patches. Wave phase must use stable world coordinates/offsets when the mesh recentres; today's `positionLocal` phase cannot simply follow a translated ocean. [I]

**H5:** a bounded near mesh plus coarse outer geometry and two static shore fields suffices, without FFT waves, a new water sim or a generalized texture-streaming atlas. Test both coasts, the ±650 m old sea seam, a bridge pillar and the view backwards in real motion. Physical buoyancy may stay the existing broad sea policy; visual coast foam must no longer sample the wrong place. [I/U]

## Migration and deletions

### Order without a giant rewrite

**A. Extract behavior-preserving old-place data and factories.** Retain old origin, terrain dimensions, source/perch order and all wire meanings. Separate geometry from registration; make cleanup real. First prove repeated load/unload of static ground/props while player/toy pins remain safe. Keep the existing old-place adapter for unconverted callers. [I]

**B. Add the second place and an explicit connection.** Use a small authored landing and an existing place-derived patch, not an entire new town. Keep the first bridge collision spine and arrival anchors resident; activate place detail by bounds. First demonstrate coexistence without network-schema churn, then establish the shared line's canonical catalog/schedule using the rail-slice authority model. Neither local prototype economy is promoted by copying its folder. [I]

**C. Remove global travel blockers as one coherent capability.** Ground/surface dispatch, player boundary/recovery, return/fall, camera, sea/fog/depth and required item/NPC validators move together. Decide explicitly which toys stay in old island and which can travel. Avoid a “two islands work” claim that silently disables the ball, guest or returning visits. Add per-place and connection validation alongside these changes. [I]

**D. Cut over shared addresses/catalog and select home.** Update rules/sims/adapters, pinned input readers and world-input fixture together under the namespace policy below. Then change `startPlace` and, if chosen, the old island transform. New-home selection need not physically move the old island at all. The fully translated old island proof includes cave holes/ponds, guest, Boogler, gifts, props and recovery. [I]

**E. Retire the compatibility seams once callers are gone.** Remove old global exports and startup ownership, not the authored old island. Measure repeated crossings, splitting large collision units only if evidence demands it. No generic streaming framework or interest-management rewrite in this milestone. [I]

### Delete, keep, or defer

- **Already gone; do not recreate:** shared sand/terrain edits, water ticks and mushroom lockstep state. [rules/index.ts](../../src/world/rules/index.ts) and [namespace.ts](../../src/world/namespace.ts) record their removal. Fixed `baseCm` is still terrain input, not a leftover editable simulation array.
- **Delete after migration:** universal `GRID_RES/CELL/HALF` exports; clamping world-to-home `cellOf`; the import-time terrain body; unconditional old terrain/props/stall construction; universal ±237 wall; scene-wide home height texture; raw singleton height imports/readiness checks; runtime mutation of `ROUTE`/site exports for production; prototype-only fog/wall/lift overrides when their real replacements graduate.
- **Replace, then delete:** `home-land.json` only when a canonical multi-place gameplay input covers its trees/perches and every reader; obsolete source-index/pile/gift address paths only when their replacement is used. The pinned-input check remains necessary even though its old filename and shape can disappear.
- **Keep:** authored old shape, `HOME_KEEP` within that definition, toys, all Boogler lines, the stamp grammar, mesh batching, Rapier facade, terrain data, useful scene queries, shared sea datum, one room/world/tick order, snapshot/hash verification and failed-load guards. Scope these rather than wiping them out.
- **Separate rail-economy cutover:** old `sites/sources/bank/tune/opening` and their `site.*`, `src.take`, `bank.wake`, `tune.*`, `open.*` callers are retirement candidates in rail-slice, not prerequisites for place modules. The server still invokes `bank.wake`, and active prototypes depend on this economy. Audit before removal; stacks/roster/gifts/piles/ball are not automatically obsolete.
- **Prototypes:** the newer owner decision says no further archiving without asking while place is active. Preserve dependent place/net/crossing/wagon code now. Later approved retirement follows archive tags/cards and removes graduated duplicate implementations; this report authorizes none of that removal.
- **Correct stale docs while implementing:** island README still describes nonexistent `HOME` and old grid migrations; physics.ts claims there is no CCD although the Rapier backend enables it for dynamic bodies; namespace comments mention the former PeerJS model. They are audit findings, not reasons to restore old architecture. Preserve The Boogler's copy even when it describes retired systems.
