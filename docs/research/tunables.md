## Summary

1. Reuse `rules.tune`, the Dev command/result path and water bindings; add metadata and adapters, not another editor or state service.
2. Distinguish **local**, **presentation** and **lockstep** settings, and separately declare when a change can take effect. Physics remains Owner even when its configuration is shared.
3. Persist and hash the complete effective lockstep configuration. Defaults, units and interpretation are part of compatibility, not harmless source edits.
4. Give UI, URL, window API and CLI the same validator and truthful pending/applied/rejected results.
5. Record full effective values at session start and accepted changes thereafter. A URL or preset name alone cannot reproduce a test.

## Existing seams and their limits

**V:** [rules/tune.ts](../../src/world/rules/tune.ts) validates `env.protoRoom`, integer bounds and cost-fit constraints, then applies `tune.set` in the ordinary ordered edit stream. It registers a saved/hashed `tune` state and exposes `rules.tune.get`. It does **not** restrict edits to a designated tester: any admitted sender in a matching proto room can request them. `tune.fill` and `tune.reset` are fixture actions, not parameter setters.

**V:** [sim/tune.ts](../../src/sim/tune.ts) saves and hashes **only overrides**, indexed in append-only catalog order. If builds disagree on a default, their empty override hashes can match while effective values differ. Loading an older override-only save under a new default also changes its behavior. The registry must not reproduce that ambiguity.

**V:** [Dev](../game-design/dev-menu.md) already provides lazy panels, `window.boogle.dev.run`, bounded commands, result records and reports. It currently has no shared tuning mutation authority. [Water](../../src/render/water/live.ts) provides `bindings`, captured defaults, scalar/vector setters and change callbacks; ordinary visits use constants rather than editable uniforms. [Water UI](../../src/debug/water-tuning.ts) separately owns bounds and persistence. [Frozen sky](../../src/render/water/frozen-sky.ts) adds expensive asynchronous rebakes. These should become adapters behind one descriptor contract, retaining their actual cost and lifecycle.

**V:** [Place coop](../../src/proto/place/coop.ts) and [job saves](../../src/proto/place/job.ts) are separate from the [isolated railway rules](../../src/world/rules/railway-index.ts). Neither is a generic lockstep tuning service. [Production-core](../plans/production-core.md) owns promotion; descriptors must not import prototype modules into headless sim or make old prototype snapshots authoritative.

## One small typed registry — proposed

### Shape and ownership

Use plain immutable descriptors and a small ID map. Owners retain typed values; debug adapters register getter/setter functions only when loaded. No proxies, reflection over arbitrary objects, generic property-path writes or per-frame registry traversal. Sketch only:

```ts
type Scope = 'local' | 'presentation' | 'lockstep';
type At = 'live' | 'next-action' | 'reload' | 'new-room';
type Meta = {
  id: string;
  owner: { module: string; symbol: string };
  scope: Scope;
  units: string;
  at: At;
};
type NumberSpec = Meta & {
  type: 'number';
  default: number;
  range: { min: number; max: number; step: number };
  integer: boolean;
};
type BoolSpec = Meta & { type: 'boolean'; default: boolean };
type EnumSpec = Meta & { type: 'enum'; default: string; values: readonly string[] };
type VectorSpec = Meta & {
  type: 'vec3';
  default: readonly [number, number, number];
  range: { min: number; max: number; step: number };
};
type Spec = NumberSpec | BoolSpec | EnumSpec | VectorSpec;
// A typed builder derives each value type and the ID union from `as const` specs.
// Lockstep specs narrow this union to integer numbers / booleans / coded enums.
```

`owner` names a module and symbol, not an agent/person. `scope` describes configuration delivery: **presentation** is a useful subset of Boogle's **Local** sync kind; **local** covers device/input and Owner-side control settings. Neither may alter conserved state. A room-wide movement profile can be lockstep configuration without making Rapier lockstep. Scope never comes from the caller's request.

Proposed module placement: keep the pure lockstep catalog/validation inside `src/sim/tune.ts` (or a small sibling as it grows), rules in `src/world/rules/tune.ts`, and lazy browser command/UI adapters under `src/debug/dev/`. Extract reusable local value blocks from features to a small owner-adjacent module outside `features/` only when needed; do not import features into each other. Water retains `live.ts` as its binding owner. A metadata-only manifest can compose descriptors for CLI listing without importing three.js, DOM, feature registration or prototype startup. This respects [lint boundaries](../agents/lint-boundaries.md); shared schema types may live in `src/sim/` and be imported outward, never the reverse.

A number's range is both validation and UI metadata; it is not proof that every point feels good. Reject nonfinite numbers, unsafe integers, negative zero, wrong types, malformed vectors, unknown/duplicate IDs and out-of-range input; show accepted units without silently clamping. Convert UI seconds to explicit integer ticks or milliseconds before submission. UI step snapping is display behavior; shared wire values must already be canonical. Use one owner-level validator for coupled constraints such as contact < restart ≤ duration, source work/yield, occupied capacity and funded recipe costs. No arbitrary expressions or executable presets.

Defaults remain authored source values. Effective values live in their existing owner; immutable defaults and current snapshots are copied on export. Read results include default, effective value, source (`default`, `saved-preview`, `look`, `url`, `session`, `room`), applied revision/tick, availability and reason. For action-latched values, also expose the active action's profile/revision. A setting for an unloaded feature is listed as unavailable, not “missing” and not auto-imported merely to answer discovery.

### Application and precedence

For local/presentation startup: **authored defaults → saved Dev appearance → selected Look → explicit `t.<id>` URL overrides**. Named Look selection retains its existing reset-to-defaults transaction; subsequent manual edits mark it modified. Later UI/API changes win within the session. API/URL writes are transient by default; explicit `persist: true` follows existing Dev-owned preference keys. Never persist room settings in localStorage. `dev=0` disables mutation even with stale settings; ordinary invite links continue stripping debug parameters. Reset restores the applicable authored default, not an unexplained older layer.

For lockstep: **the room's accepted configuration is the only effective source**. URL values are requests to the authorized host controller, never local overrides. Reconnect must not resubmit startup requests automatically. A new default only initializes a new room; an existing room keeps its saved profile. Layout/collider/recipe changes use `new-room` or explicit migration. In-flight swings, deliveries and funded builds retain their captured schedule; changing a duration cannot retroactively complete a job. Derived caches update on change, not by rebuilding every frame.

## Lockstep, host authority and saved rooms

This is the proposed contract, constrained by [lockstep](../agents/lockstep.md), [sync](../agents/sync.md), [room-safety](../agents/room-safety.md), [mixed-builds](../agents/mixed-builds.md) and [world tick ordering](../../src/world/README.md#ordering-inside-one-tick).

1. **Host means the server.** The Dev browser is a controller, not the world's host; the lead tab is not authorization. Initially permit writes only in explicitly enabled development/test rooms, with an operator-selected controller session bound server-side. The existing local harness can supply that assignment to the local server; hosted testing needs an equivalent server-configured assignment. Do not infer it from a room prefix, `tune=1`, `dev=1`, `coop=0`, client-supplied pid or “first person joined”. No admin UI, new account system or general remote-config endpoint is needed for the first slice. Other clients can read the room profile.
2. **Use existing edits.** A versioned bounded patch request contains stable IDs, canonical values, catalog identity, expected revision and a request ID. The host checks controller identity through `ctx.from` and host-only `ctx.env`, room mode, bounds and current state constraints. Do not read `env` in `apply`/ticks. Start with one key per request; related values can later be one bounded, all-or-nothing patch. Never split an invariant-dependent edit across separate ticks.
3. **Apply deterministically.** The host stamps the accepted patch in the normal sequence; every peer installs it at that tick before tick handlers. `apply` repeats state-dependent validation against the now-current world and returns an accepted change or a no-op reason. A stale expected revision fails; conflicting editors do not silently overwrite one another. Values are integer counts/ticks/milliseconds/fixed-point where shared math needs them, with the repo's permitted arithmetic only. Keep catalog order stable and retired wire identifiers reserved.
4. **Persist complete effective state.** Proposed tuning state is `{ catalog, revision, values }`, including all effective lockstep values, not only differences from today's defaults. Hash catalog/revision/values in fixed catalog order; local UI provenance and pending previews stay outside it. Use the normal room snapshot and server persistence. A room that reloads, empties or restarts gets the same values. Hash-verified/bad-save guards remain intact; do not report a setting as durable until the owning persistence path establishes that fact. Ordinary classic save cadence is not the production recovery envelope's crash guarantee.
5. **Expose truthful completion.** `submitEdit(true)` is only queued. Return a request handle with `pending`, then `applied`, `rejected`, `superseded` or `unknown` on disconnect/timeout. Resolve applied only from the accepted result/revision. Read-back of a later equal value is not proof that this request succeeded. The legacy path lacks correlated rejection receipts: add a bounded tuning result/status path through the room interface when implementing its writable version, or reuse the production request coordinator where actually installed. Do not claim this capability already exists in ordinary Dev. Reconnect reconciles against the authoritative snapshot and retained outcome before retry; no blind retry of a stale request.
6. **Protect existing work.** Reject a cap below occupied inventory unless the system already supports grandfathering without deletion. Cost changes cannot invalidate funded stock or allocations. Latch production timing at the accepted action boundary; shared timers read accepted ticks/ages, not each browser's clock. Recovery cannot mint material, and regrowth cannot bypass the source ledger. Host visibility/presence is validation evidence for a stamped maintenance action, never nondeterministic input to `apply`.

### Mixed builds and changing defaults

**A state migration alone cannot make an old client execute new tuning semantics.** Likewise, an additive op that an old client ignores is unsafe if new clients use it to change shared outcomes. Cosmetic metadata additions can remain additive; lockstep changes require compatible consumers, hashes and a supported catalog before joining simulation.

For the **legacy haul upgrade**, use the repo's explicit development clean-break route: bump [WORLD_NS](../../src/world/namespace.ts) with a dated reason when changing the override-only state/hash/meaning. Keep `RULES` append-only inside a namespace. This separates old tabs and saves rather than hoping they ignore a tuning op safely. It also starts fresh worlds for every room in that namespace: make that consequence explicit in the implementation plan, and keep it out of the first Local slice. Do not silently reuse old `tune.set` meaning in `v06`.

For the **production railway integration**, follow its owning catalog/admission and versioned recovery contract instead of resetting progress or bolting classic tuning onto `RAILWAY_RULES`. At this SHA the isolated [railway namespace](../../src/world/railway-namespace.ts), [catalog](../../src/sim/railway-layout.ts) and [wire](../../src/world/railway-wire.ts) do not provide a general tuning compatibility handshake. The writable production slice must add an explicit supported catalog check before participation, or use the owning namespace isolation with an approved save migration. Refuse incompatible clients before simulation; do not load a newer tuning profile as defaults. Preserve old snapshot verification with its old defaults/code before migration, as the [supply/slice-3 audit](slice3-plan-2.md) requires. This is a required integration task, not a claimed existing guard.

Pin full effective values on new room creation. On an authorized conversion from override-only saves, fill omitted values from the **old** baseline catalog, then validate and hash the complete result. If the old baseline cannot be identified, stop conversion and preserve the file. Changing an ID's units or meaning requires a new ID/catalog version; even unchanged defaults must be fingerprinted with their semantics. No silent fallback, no deleting failed saves, no automatically resetting a friend's room.

## Agent interface and playtest evidence

All examples below are **proposed**, except the existing `npm run session` transport. Add a `tunables` tool using [Dev's descriptors](../../src/debug/dev/types.ts); the window API remains `boogle.dev`, rather than another global with different permissions.

```ts
await window.boogle.dev.run('tunables', 'list', { scope: 'presentation' });
await window.boogle.dev.run('tunables', 'get', { id: 'post.centre' });
await window.boogle.dev.run('tunables', 'set', { id: 'post.centre', value: 0.18 });
await window.boogle.dev.run('tunables', 'snapshot');
await window.boogle.dev.run('tunables', 'reset', { id: 'post.centre' });
```

`list` returns descriptors plus availability; `get` returns effective value/provenance; `set/reset` use the same validated owner path as the panel. Keep the existing `{ ok, message, data }` envelope, with structured `data.status`, `requestId`, `revision`, `appliedTick` and error code. For lockstep, a successful queue operation explicitly says `pending`, and a `status` command reconciles it. Wrong type, unsupported catalog, disabled tuning, forbidden controller, busy owner, stale revision and reload-required are distinct results. UI controls use those results too. No raw setter on `rules.tune.v` or the water binding map is exposed to callers.

URL example: `?tune=1&t.post.centre=0.18&t.post.underwaterEV=0.81`. Keep `tune=1`'s existing opt-in meaning. Parse only allow-listed IDs, at most 32 entries and 4 KB of tuning parameters, reject duplicates/invalid values and show the failure. Apply after defaults/Look restoration but before the first relevant warm draw. Unsupported runtime bindings return reload-required. A URL containing `t.haul.yield=6` queues a host request only after connection and authorization, or reports refusal; it never changes a joining client's sim alone. Setup links may include explicit preview values; ordinary invites do not. Export includes the pinned build/catalog, and importing a mismatched preset requires an explicit compatible mapping, not best-effort gameplay substitution.

Proposed thin wrapper, `dev/tune.ts` / `npm run tune`:

```sh
npm run tune -- list --json
npm run tune -- get post.centre --session --json
npm run tune -- set post.centre 0.18 --session --json
npm run tune -- set haul.yield 6 --session --expect-revision 3 --wait --json
npm run tune -- snapshot --session --out .look/tuning.json
```

Offline `list` reads the pure descriptor manifest and labels defaults as defaults. Effective `get/set` require an explicitly running session; no hidden browser/server startup. Reuse [dev/look/session.ts](../../dev/look/session.ts)'s private local transport and fixed `boogle.dev.run` calls, with structured serialization rather than interpolated user JavaScript. Its existing `eval` can already call the future API, e.g. `npm run session -- eval 'return await window.boogle.dev.run("tunables", "snapshot");'`. In a managed worker use the supported broker path instead; missing capability returns an actionable error. Exit nonzero on rejection or unknown outcome; `--wait` waits for application, not arbitrary sleep. Defaults are promoted by a normal reviewed source commit, never by runtime CLI mutation of a live save file.

### Record the values that were actually in force

[Playdata](../../src/proto/playdata/record.ts) records build/flags and flat events; [server validation](../../server/src/playdata.ts) allows at most 24 fields/event and 300 characters/string. Existing flags truncate at 199 characters. A giant nested JSON configuration in `session.flags` will not work. Reuse the event stream, with bounded records:

- `tune.begin`: snapshot ID, build, namespace, catalog, room revision, effective tick and expected entry count.
- One `tune.value` per ID: scope, value (RGB split into three numeric fields), source, revision and snapshot ID. Record full effective values, including defaults; a named preset is supplementary metadata.
- `tune.end`: snapshot ID, count and canonical manifest digest. Start after owner registration/room snapshot readiness; record later lazy-owner registrations as additional complete groups.
- `tune.change` only after local application or accepted room application, with old/new value, revision, local monotonic time and shared tick where applicable. Record action-latched activation separately when the new profile first takes effect. Pending/rejected commands belong to diagnostic outcomes, not the effective-value timeline.

Each peer records its own presentation/local profile and the authoritative room configuration it observes. Rejoin begins a fresh complete configuration segment. Extend [Dev report](../../src/debug/dev/report.ts), [local traces](../../src/proto/trace/record.ts)/[protos store](../../protos/store.ts), and [playtest summaries](../../dev/playtest/summary.ts) with the same manifest identity and timeline; keep full values available in the report/export. Existing event limits and `notrack=1` remain. Batch initial values once, not every position sample; when queue loss or a missing begin/end prevents reconstruction, label the configuration interval incomplete instead of guessing. Re-emit a complete snapshot after recovery. A configuration manifest reproduces settings, not world state, inputs or exact physics.

## Cost, migration order and smallest first slice

**P estimates and budgets, not measurements.** Descriptor storage grows with the number of parameters; normal frame reads remain direct fields/locals. Validation, lookup and derived-cache updates happen on edit, registration or snapshot load. UI, browser bindings and CLI stay lazy/off the ordinary game path. Lockstep defaults/values necessarily remain eager on server and clients. At 100 numeric entries, budgeting roughly 80 JSON bytes per entry gives about **8 KB** per full manifest; a roughly 180-byte flat playdata event would make an initial 100-entry recording about **18 KB**. Measure actual encoding and the entire world snapshot against its existing **60,000-byte production recovery envelope**, including pending stamps; this budget cannot be borrowed blindly.

No new polling loop, steady network heartbeat, GPU readback or shader pass. Numeric water edits reuse uniforms. Expensive sky/geometry/pipeline edits expose `reload` or a bounded owner-controlled prepare/apply operation; debounce rebakes and report completion/failure. Commit room changes on slider release rather than every pointermove; local cheap sliders may update live. ## What this means for Boogle

Numbered so an implementation plan can cite these recommendations. All are **P**, subject to the existing owner gates.

1. **Add one typed descriptor contract around existing owners.** Adapt [sim/tune.ts](../../src/sim/tune.ts), [water/live.ts](../../src/render/water/live.ts) and [Dev](../game-design/dev-menu.md); keep direct hot-path reads and explicit owner/scope/units/ranges/application timing.
2. **Make shared tuning an authorized, ordered room edit.** Extend [rules/tune.ts](../../src/world/rules/tune.ts) and its server admission with host-controlled writes, correlated outcomes, revision checks and action-boundary semantics; never treat `tune=1` or a queued edit as authority/success.
3. **Pin complete effective profiles and fence incompatible builds.** Replace override-only ambiguity under an explicit [namespace transition](../../src/world/namespace.ts); integrate production separately through its [catalog/recovery plan](../plans/production-core.md), preserving old-save verification and refusing unsupported peers.
4. **Expose one interface through Dev, URLs and the session CLI.** Use [Dev tool descriptors](../../src/debug/dev/types.ts) and [session transport](../../dev/look/session.ts); support discovery, effective reads, validated writes, reset and export with provenance and truthful status.
5. **Attach the effective configuration timeline to every playtest.** Extend [playdata](../../src/proto/playdata/record.ts), [reports](../../src/debug/dev/report.ts) and [summaries](../../dev/playtest/summary.ts) with complete bounded manifests and applied changes; mark gaps rather than reconstructing from today's defaults.
6. **Migrate according to real playtest questions and existing authority.** Follow the inventory and [round-4 tracker](../plans/round-4-notes.md): axe, machine, supply and ability pacing have different owners and safe boundaries. Do not replace route design with timers or conserved recovery with visual despawn.
7. **Start with the two existing exposure controls, then prove one shared value.** First deliver slice A using [exposure.ts](../../src/render/exposure.ts); only then undertake the namespace/receipt work for haul yield. Measure overhead and stop at the relevant owner playtest before widening gameplay scope.
