# State ownership: whose railway, whose hands?

> **Verdict:** Keep T1 boundary; conserved work moves to server authority.
> **Top recommendations:** 1. Keep T1 unchanged and execute its existing authority/recovery contract after the owner replay. 2. Repair the two beam capability consumers before core as one small integration task. 3. Fix local discovery keys and cosmetic claim serialization without centralizing profiles.
> **Status:** partly adopted. See [plan production-core](../plans/production-core.md).

_4 November 2026. Audit and proposal against live `main` at `dc1949f65c19d03879adc59d0133e451123a27f7`, verified with `git ls-remote` at the start; this branch began at that commit. Default Place first, its complete save-slice registry and gameplay owners, then the adapters, transport, server and classic systems. Live primary-source research; file/line references below refer to this pinned build. **V** = code/source inspected, **O** = recorded observation from an earlier build, **I** = inferred code consequence; recommendations are proposals. No gameplay source changes, public-room connections or shared-state mutations. One isolated in-memory classic-rule probe is described below; no new browser run or device test._

**Keep the approved T1 production-core boundary. Move conserved work into its existing server-authority plan; keep movement, physical handling, cosmetics and presentation with the player where they belong.** The default game has a server-hosted connection, but its railway is still owned by browsers. That is the important distinction, not whether every number lives on the server.

The test is DESIGN.md's **Cooperation is automatic, not negotiated**: can I help simply by playing, leave without taking the railway with me, and return to honest shared work? Server-authoritative stock helps that. Server-simulating every jump, pet or splash does not follow from it. [Mainline architecture, findings 1–2](../plans/mainline-architecture.md#1-persistent-railway-state-still-belongs-to-tabs) already identifies the railway and animation-authority problem. [Production-core](../plans/production-core.md#state-and-authority) already specifies the replacement, receipts, conservation, recovery and promotion order. This report inventories the exceptions and remaining seams rather than proposing that conversion again.

The owner approved all eight production-core recommendations on 4 November ([decision:149](../proposals/boogle-2.md#L149)); implementation still waits for the corrected round-4 replay. **Room ownership of time of day is already decided**, reaffirmed in this audit's brief. The unresolved implementation is how the room represents intentionally chosen lighting phases, not whether each player gets their own gameplay time.

## Read the ownership and persistence columns literally

- **Place shared / S:** `sharedSlice` data in each browser's `boogle-place-coop-v2:<room>` localStorage, alongside personal data; solo uses `boogle-place-v4:<room>` ([job.ts:63–119](../../src/proto/place/job.ts#L63)). **Reload:** restores that browser's last successful save, then joins the current tab authority. **Everyone leaves:** saved browsers can revive their copies; a new browser cannot obtain this railway from the server. There is no browser-free Place progression. **Server restart:** does not erase browser storage, but the server cannot reconstruct these slices. Storage failures are caught; these are not guaranteed durable saves. This qualification applies to every **S** row.
- **Place personal / P:** the same document's `personal` section. **Reload / everyone leaves / server restart:** retained only in that browser and room, subject to a successful save; another browser/device has no copy. Shared snapshots do not distribute it. Two tabs on the same origin/room write the same document, not isolated cloud profiles. Explicit Start fresh removes Place saves across rooms, as its warning says ([job.ts:91–106](../../src/proto/place/job.ts#L91), [index.ts:128–135](../../src/proto/place/index.ts#L128)). This qualification applies to every **P** row.
- **Server world / W:** registered deterministic rule state, server-stamped operations, snapshots and hashes. Reload/late join loads the server snapshot; empty rooms save and may be evicted; restart restores the last successful disk checkpoint. **Published acceptance is not yet a crash-durability receipt.** Details and the failure window are below. This is distinct from S even in the same room.
- **Transient / T:** no durable save for this state. Reload recreates it; everyone leaving removes its live authority; a server restart does not recover it, although connected owners can republish their current presence. Static authored geometry is recreated from code, not lost progress.
- **Place authority:** oldest visible, recently heard compatible participant, with peer-id tie-break ([coop.ts:351–376](../../src/proto/place/coop.ts#L351)); independent of the server-selected lead used by `addHostField`. Messages and roughly one-second snapshots converge each client's copy ([coop.ts:814–843](../../src/proto/place/coop.ts#L814)). An empty authority can adopt a returning browser's nonempty save ([coop.ts:322–333](../../src/proto/place/coop.ts#L322)). Neither this nor choosing the furthest-progress save is a durable transaction log.

Bare URL selects Place/co-op in `boogle`; explicit prototype and classic routes remain separate ([flags.ts:6–25](../../src/proto/flags.ts#L6)). `fresh=1` is the clean presentation, not a command to erase the railway. The default switch did not move Place into server rules. The actual registered list is `gifts, roster, stacks, piles, sites, sources, bank, ball, tune, opening` ([rules/index.ts:17](../../src/world/rules/index.ts#L17)).

**Where W really lives:** `DATA_DIR/<namespaced-room>.json`, with `DATA_DIR` defaulting to `./data` relative to the server process ([server.ts:68](../../server/src/server.ts#L68), [store.ts:20–23](../../server/src/store.ts#L20)). The namespace is currently `v06` ([namespace.ts:12–25](../../src/world/namespace.ts#L12)); Place's browser key uses the plain room name instead. The server schedules changed saves about every two seconds, periodic tick saves every 30 seconds, and awaits a save on orderly close ([world-host.ts:41–66](../../server/src/host/world-host.ts#L41), [90–119](../../server/src/host/world-host.ts#L90)). Writes serialize through temp-file/rename ([store.ts:67–78](../../server/src/store.ts#L67)); publication does not await that write. Dynamic rooms can unload after ten empty minutes; explicitly configured rooms are retained ([rooms.ts:44–54](../../server/src/host/rooms.ts#L44), [server.ts:78](../../server/src/server.ts#L78)). These are code defaults, not an inspection of deployed environment variables or disk volumes.

The server binds actor identity for rule edits, validates and stamps their order ([sync.ts:208–235](../../src/world/sync.ts#L208)); it merely relays Place application messages/presence ([hosted-room.ts:164–180](../../server/src/host/hosted-room.ts#L164)). Its current host environment supplies `protoRoom`, not a server simulation of player reach or movement ([world-host.ts:47–49](../../server/src/host/world-host.ts#L47)). Even the future core's reach checks will use Owner-reported pose plausibility, as its plan states. Authority over stock does not turn that into anti-cheat physics.

## Primary-source comparisons and their limits

- **Unity — durable-in-session values and anticipation have different jobs.** NGO 2.4.2's [NetworkVariables](https://mp-docs.dl.it.unity3d.com/netcode/current/basics/networkvariable/index.html) distinguishes current state available to late joiners from one-off RPCs; it also supports distributed authority. Its [2.3.2 anticipation documentation](https://docs-multiplayer.unity3d.com/netcode/2.3.2/advanced-topics/client-anticipation/) separates anticipated visuals from authoritative values and says this is not full rollback prediction. These are versioned primary pages, now marked unmaintained, not claims about the latest package. Boogle should retain immediate swing/flight intent while letting accepted state own goods and unlocks. Network replication alone does not promise disk persistence.
- **Unreal — “owning a pawn” is not the same as deciding shared game truth.** Epic's [Networking Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine) describes an authoritative server world and clients rendering approximations. That supports shared construction authority, but copying the whole movement architecture would add a separate prediction/reconciliation project. Boogle's noncompetitive Owner motion is a deliberate difference. Keep the current platform/epoch mechanisms unless a specific player failure requires more.
- **Godot — choose an authority and a state contract, not a mesh identity.** [High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html) distinguishes authority/any-peer RPCs; [MultiplayerSynchronizer](https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html) synchronizes authority-owned properties and excludes peer-local object instance ids. Boogle's stable platform ids and numeric construction catalog serve that boundary. A reliable message can deliver a request; it does not by itself arbitrate two requests or save the accepted outcome.
- **Shipped-game lesson: Factorio's authoritative and latency states are distinct.** Wube's developer account, [Friday Facts 302](https://factorio.com/blog/post/fff-302), describes deterministic game state and separate speculative latency state, including a real bug where unreliable speculative history drove a packet cascade. For Boogle, decoration or prediction must not become a second spendable stock account. This supports the existing core's accepted-transfer design; Factorio's scale and movement requirements do not justify copying its entire simulation.
- **Counterexample to server-everything: responsive physical toys.** Glenn Fiedler's Oculus-sponsored [Networked Physics in Virtual Reality](https://gafferongames.com/post/networked_physics_in_virtual_reality/) chooses distributed authority for low-latency, noncompetitive physical interaction, with explicit conflict rules. It is a research sample, not a Boogle benchmark or a shipped-game persistence solution. It supports preserving Owner avatar/ball handling, while reminding us that shared-object handoff still needs an epoch/claim rule. It does not justify browser ownership of permanent track.
- **Persistence is a separate promise.** [Redis's own persistence documentation](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) distinguishes periodic snapshots from logged operations and their flush policies. The applicable lesson is the crash window between publication and durable storage, not a recommendation to install Redis. Boogle's existing core already chooses the required process-crash guarantee and bounded recovery envelope; retain that approved requirement.
