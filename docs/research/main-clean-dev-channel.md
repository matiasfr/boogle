# Clean main, a separate dev channel

_Research, 4 November 2026. Scope and migration proposal against `5b356980e7ccd56f0edff79010e7e92c35e8e393`; repository audit and live primary-source research, no implementation, deployment, deletion or policy change. Counts describe this checkout, not newer parallel jobs. Not tested on a device._

## Decision

**Keep `main` deploying to boogle.club; put a selected prototype branch on `dev.boogle.club`, using a dedicated Cloudflare Pages project and a separate Fly server/volume. Graduate Place and its actual dependencies before clearing prototype code from main. Prefer bounded `prototype/<topic>` branches over a permanent accumulating `dev` branch.** A channel is a deployment destination; it need not be a forever branch.

This serves **Small and readable**, **Clear authority** and **Designed for drop-in, drop-out** in [DESIGN](../../DESIGN.md). Disposition: **owner decision needed for the policy and removal list; infrastructure scoping can proceed independently of the replay**. [Production core](../plans/production-core.md) already has approved scope but still waits for the corrected round-4 replay. Renaming Place cannot close its persistence/lifecycle findings or bypass that gate.

Evidence: **L** = inspected local source; **V** = primary source read live; **P** = proposal/calculation; **U** = unverified. Format follows [places-as-modules](places-as-modules.md) and [level-design-tools](level-design-tools.md). `inflight` and `codex-status` checked: `remove-proto-bar`, `sw-precache` and `production-harness` are active parallel work. Assume the bar and `?play` playlist gone, as requested; reconcile their final commits before implementing this report. **Do not interpret their presence in the measured baseline as remaining work assigned here.**

**Owner, 4 November: no second paid server.** This overrides the separate Fly server and volume wherever they appear below. The dev client uses the production server in `dev-` or `proto-` rooms, so it can only carry prototypes that leave the server image's code alone. The dev deploy refuses a candidate whose `server/`, `src/world/`, `src/sim/`, `src/net/ids.ts` or `src/net/ws-wire.ts` differ from what production runs. Prototypes that change those stay local (`npm run dev` hosts its own rooms) until they graduate. Add the dev origin to `ALLOWED_ORIGINS`, and tell dev reports apart by room name. Not yet deployed or tested.

**Owner, 4 November, later: keep things as they are for now.** No dev site, no archive batch and no change to the standing prototype call: prototypes stay on `main` behind their flags. This document is scope for later, not a plan in progress. When it is picked up, the preferred start is testing prototype branches locally, with a one-build-at-a-time dev site only when someone else needs to play.

## Five recommendations

1. **Create an isolated dev destination first.** Dedicated Pages project, `BASE=/`, dev build identity and `boogle-server-dev` with its own data and reports; leave production Pages intact. Prove both channels open together without cross-room, cache or save interference. Owners: [deploy.yml](../../.github/workflows/deploy.yml), [deploy-server.yml](../../.github/workflows/deploy-server.yml), [fly.toml](../../server/fly.toml), [SW policy](../../src/boot/sw-policy.ts).
2. **Make Place's production dependencies explicit, then graduate them.** Move the accepted game out of `src/proto`; extract shared cargo, geometry, sound and environment leaves before removing their experiments. Preserve classic as an explicitly named regression/content mode initially. Follow [mainline architecture](../plans/mainline-architecture.md) and [production core](../plans/production-core.md), not a mass rename presented as production readiness.
3. **Keep main as the integration trunk; deploy bounded prototype branches.** Automatically merge current main into the active candidate through checked integration commits, publish only a matching client/server revision, and graduate a reviewed production delta through ordinary `npm run ship`. Never merge an accumulated dev branch wholesale. Owners: [ship.sh](../../scripts/ship.sh), [automerge](../../.github/workflows/automerge.yml), [Codex launcher](../../dev/codex/run.ts).
4. **Archive by dependency, with a named owner decision.** Tag the last complete, runnable source `archive/<name>`, remove the implementation, loader and orphan seams together, and retain an archived card with the tag. Move unresolved experiments to dev only. Preserve The Boogler's copy and dated evidence. Proposed disposition inventory follows; none is deletion authority.
5. **Move verification and reporting with the code.** Main must exercise the promoted default Place as well as retained classic contracts; dev runs its candidate's scenarios against its own server. Add channel/source/base/server identity to artifacts and reports. Update [CI](../../.github/workflows/ci.yml), [smoke](../../.github/workflows/smoke.yml), [level tooling](../../dev/level/), [playtest reader](../../dev/playtest/cli.ts) and [Codex evidence](../../dev/codex/evidence.ts) together.

## Hosting choices and isolation

GitHub documents **one project Pages site per repository**. Two Actions environments or two deployment workflows do not create independent sites: publishing a second artifact replaces the same site. A single artifact can contain both `/` and `/dev/`. [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) **V**

Separate origin, but another repo and artifact handoff. [GitHub custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages) | Good fallback if avoiding Cloudflare. |

The live Fly price page quotes North American internet egress at **$0.02/GB**, snapshots at **$0.08/GB-month with the first 10 GB free**, and optional dedicated IPv4 at **$2/month**; shared IPv4 needs no extra address fee. A separate 256 MB static VM would add about **$2.19/month** before traffic. These are list-price calculations, not the owner's invoice; volume size is proposed. Keep auto-stop off initially to match websocket behavior; stopping idle dev later changes availability and does not eliminate volume billing. [Fly pricing, read 4 November](https://docs.fly.io/about/pricing) **V/P**

Use a dev-only Fly token, report token, volume and origin allowlist; no copying or mounting production saves. Configure `VITE_BOOGLE_SERVER` explicitly for dev and refuse a dev build whose endpoint resolves to production. `WORLD_NS` still versions the world inside each environment; branch changes that alter its wire/sim contract still require the documented namespace/version decision. A separate app prevents production contamination, but **does not solve old versus new dev clients**. A `build` label is diagnostic, not a verified protocol compatibility gate. ## Branch model: what the precedents actually support

| Model | Clean main source? | Cost for Boogle |
| --- | --- | --- |
| Permanent `dev` branch holding every experiment | Yes, if main never merges it wholesale. | Two evolving integration lines; regular main→dev conflicts, dependencies between experiments, selective graduation, and old code accumulating again on dev. Worth it only if the owner needs several simultaneous prototypes integrated into one build and accepts a branch steward. |
| Main-only, build flag excludes experiments | **No.** Can keep the production artifact clean, not main's source. | Lowest integration cost; useful for dev tools and bounded presentation variants. Eager feature discovery and build graph must exclude experiments, not merely hide links. Doesn't meet the stated source-clean goal. |
| Main trunk plus bounded `prototype/<topic>` branches; one selected dev candidate | **Yes**, after graduation/extraction. | Main remains the common core; each candidate has an owner, question and retirement/graduate decision. One canonical dev URL cannot show several incompatible simulations against one server at once: select a session build, run other work locally, or pay for another complete preview pair. **Recommended tradeoff.** |

**V:** [Steamworks beta branches](https://partner.steamgames.com/doc/store/application/branches) assign a build to a distribution branch, optionally restricted; they are not prescriptions for Git history. Wube's [Factorio 2.1 experimental announcement](https://factorio.com/blog/post/fff-444) describes opt-in experimental distribution and forward-only save changes. Neither establishes that Boogle needs a permanent dev source branch.

**V:** [Unity Build Automation](https://docs.unity.com/en-us/build-automation/basic-build-configuration/overview) selects a source branch per build configuration, and [per-target environment variables](https://docs.unity.com/en-us/build-automation/advanced-build-configuration/environment-variables) support staging/production. [Unreal configurations](https://dev.epicgames.com/documentation/en-us/unreal-engine/build-configurations-reference-for-unreal-engine) distinguish Development/Test/Shipping and client/server targets. [Godot feature tags](https://docs.godotengine.org/en/stable/tutorials/export/feature_tags.html) support export-specific features, settings and icons. Borrow explicit build targets, paired servers and recognizable builds; none removes unwanted source from main automatically.

**V/P:** [Trunk-based development](https://trunkbaseddevelopment.com/short-lived-feature-branches/) recommends branches lasting roughly a day or two, with continuous convergence; [release toggles](https://martinfowler.com/articles/feature-toggles.html) trade branch divergence for temporary code paths and cleanup. A prototype waiting a week for the owner is **a deliberate exception**, not strict trunk-based development. Freeze its playtest build, mark its age, and refresh/test it before graduation; don't perform continuous gameplay tuning while waiting.

**Measured drift exposure:** local `origin/main` first-parent history has **269 commits dated November 2, 158 November 3, and 79 through this November 4 snapshot** (committer dates, not unique agents or PR counts; remote was not refreshed). A week-old branch can miss hundreds of changes to imports, entity ownership and tools. Conflict hours were not measured. Compared with a build flag, clean source costs merge maintenance and separate checks; compared with a permanent kitchen-sink dev branch, bounded candidates avoid cross-prototype promotion dependencies. **L/P**

### How the recommended flow would work

1. **Select and record a candidate** (`prototype/<topic>`, pinned SHA, base SHA, owner, gut question, namespace). The initial dev-only collection can be a temporary migration branch, then split/retire it; don't turn it into the second permanent trunk. A dedicated Pages project can publish any selected source SHA into its canonical production deployment slot via Actions; retain the true source branch in metadata.
2. **Main flows outward automatically.** After successful main CI, coalesce pending sync work per active candidate. Create a merge commit through a candidate-targeted sync PR, run candidate CI, then merge if green. On conflict, stop that candidate's refresh and report its stale base; keep its last checked build available. No force pushes or automatic “ours/theirs” resolution. During an owner session freeze the deployed SHA while sync candidates continue to queue; publication resumes on the next selected sitting.
3. **Publish a pair.** A trusted channel workflow checks out the selected SHA and checks/builds both artifacts **before deployment**, then deploys the dev server followed by the client using per-channel serialization. This is not an atomic pair swap: incompatible updates need a drain/maintenance boundary, and dev may be unavailable until revision identity and room join/rejoin pass. Keeping the old pair live throughout requires compatible server updates or another complete environment. Do not let an older run overwrite a newer selection. Old incompatible preview URLs need their matching server or an unsupported-build page; retained artifacts alone are insufficient.
4. **Graduate from current main.** Bring the candidate current, select only accepted content plus its dependency closure into a fresh production branch, remove prototype selectors/debug mutation and duplicated versions, and apply production-core gates. Review/check the resulting main delta, then ordinary `npm run ship`. Pull the graduated core back into still-active candidates and delete their duplicate implementation. No wholesale merge from a multi-prototype branch.
5. **Close the experiment.** Tag its last complete source before removal; preserve question/verdict/build evidence and archived card. If a later experiment wants it, branch from current main and port only what it needs. Tags preserve code, not a promise that its historical server/binaries still run on today's service.
