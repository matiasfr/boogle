# Becsy as Boogle's enforced gameplay model

> **Verdict:** Build the in-house ECS toward the declared-access, groups and command-buffer contract. Keep its current storage for now. Becsy's **checked build** offers substantially better access enforcement today, but its perf build removes essential guarantees and hangs on the tested ordering cycle. bitECS storage alone does not improve enforcement or engine portability.
> **Next:** Close live-row mutation escapes, establish one registration/scheduling contract, then migrate tune and the remaining gameplay domains through it. Do not make save compatibility a prerequisite.

## Decision and scope

The [13 November owner call](../agents/owner-calls.md) prioritizes enforceability. The brief places migration to Unity/Unreal second and makes save resets free. These supersede the old studies' performance-first ranking, playtest deferrals and mandatory no-reset conversion work. This recommendation serves **Understandable at a glance** and **Determinism from day one**; growing the core bends **Small and readable**, so the proposed core extension must stay bounded.

Use [engine-long-term](engine-long-term.md)'s target contract and stages A–I, with a correction: A's differential runner and B's tune pilot come first, but historic-save migration is optional. C moves the nine classic states, D normalizes commands and events, E unifies scheduling, F changes replication/authority separately, G moves player/seats, H supplies scopes/prefabs, and I compares replaceable storage. Resetting saves removes compatibility work, not validation, stable identity, reliable publication or ordering requirements.

The railway is **Server** state. Tune is still one of nine **Lockstep** states. This branch changes neither authority nor transport. Inspection covered all three `src/ecs` files, tune and its rules, railway scheduling, core/jobClock, and relevant line-one/trade system sections. It did not review every railway rule.

## What actually runs

[`becsy.ts`](../../dev/spikes/becsy-model/becsy.ts) is a native Becsy implementation, not an E wrapper:

- `Values` has one scalar field per `TUNABLES` key; `Revision` holds authoritative revision and the legacy view-invalidation counter. Float64 storage preserves JavaScript safe integers; domain checks still enforce valid integer values. We do not squeeze revisions into int32.
- `TuneCommands` handles `tune.set` and `tune.commit` through separate admission/application turns, with declared write access. Tests compare **the real registered legacy handlers**, including results, every value, revision, view counter, serialized tune and old-projected hash after each step. They cover all keys' boundaries, malformed keys/numbers, room/controller refusal, request-ID bounds, equal-value changes, two commits admitted at the same revision, a stale commit, and a site starting between admission and apply.
- `JobClock` ports the real `rail.jobClock`, including both `Job/JobRun` and `QJob/QJobRun`, retaining every field of these components. It reads run state and writes `ahead/end` only when changed. A separate recorded-input fixture advances clocks; it is not a second ported gameplay system.
- The explicit graph is `Inputs → TuneCommands → JobClock → Inspect`, using `before` and `after`. Every query declares reads/writes; job queries sort by an immutable stable-ID component. Inspect copies data into a detached projection.
- Component classes are created per world. Becsy binds component types to their world, so reusing one global class set across rooms is not the supported model. The tests run independent worlds and reconstruct one midway through a 50-tick trace.

Tests run both checked and perf builds. They compare complete job/run rows after **every tick**, including continuation after JSON reconstruction, rather than accepting only a final hash. The bitECS reference also matches E after each of 40 ticks and a real E snapshot reload. Existing `test/tune.test.ts`, `test/ecs.test.ts` and `test/world-rules.test.ts` remain unchanged and pass in the same selected run.

Limits: the tune boundary is a serial mailbox, not a concurrent or durable command service. Site constraints remain a legacy read adapter, and permissions are admitted facts, not Becsy components. `tune.fill/reset`, classic-state conversion, production sync wiring, generic save validation and replica transport are not ported. The reconstruction test consumes a trusted exported fixture; it is **not** a production snapshot loader. Becsy's asynchronous `World.execute` also needs explicit ownership at Boogle's currently synchronous dispatch boundary. Do not discard its promise or let commands overlap.

[`enforcement.test.ts`](../../dev/spikes/becsy-model/enforcement.test.ts) asserts the exact failure categories. The bounded cycle child prints a start marker, so slow child startup cannot pass as the observed hang. Source explanation: Becsy `src/datatypes/graph.ts` puts cycle detection behind `CHECK` and the topological-sort no-progress guard behind `DEBUG`; both disappear from perf. This is a reproducible 0.16.1 finding, not a reported upstream issue or a claim about later versions.

E's existing checks live in `src/ecs/world.ts`: `table(c, need)` checks declarations, `run` selects the active system, `audit/rowsText` detect unmarked mutations retrospectively, `structural/ops` defer structural edits to system end, and `createSchedule` sorts numeric slots. The bitECS branch's `src/ecs/bitecs.ts` is a **94-line storage adapter**, with no access or scheduler guarantee of its own. Raw bitECS arrays cannot know which system is touching them.

To supply the same useful guarantee in E or bitECS, we would own:

1. **Scoped access:** change `get/mut/each` so no mutable backing row escapes. Read snapshots or checked read handles, and scoped setters/patches whose write capability expires at system exit; invalidate retained handles. Check values at the mutation boundary. Do not rely on TypeScript `Readonly`: `Object.assign` bypassed it in code that typechecks.
2. **Graph and groups:** extend `defineSystem/createSchedule` with stable system/group IDs, read/write resource declarations, explicit edges and a topological sort that rejects cycles and unresolved conflicting accesses in every supported build. Keep command, tick, fixed-physics and frame rates distinct.
3. **Command buffer and lifecycle:** extend the existing structural queue into an explicit barrier API, while preserving one-command-at-a-time settlement and first-success railway fallback. Define failure invalidation; neither E's audit nor Becsy's exceptions are transaction rollback.
4. **One authoring door:** extend `dev/lint/policy.ts`, `dev/registry/check.ts` and the scaffold/manifest to reject raw storage imports, new gameplay globals, stateful views, unregistered components/systems and broad unrestricted access. Require authority, lifetime, schema and persistence/replication policy. Generated contract checks should cover every newly declared component.

Becsy does not eliminate item 4. A model can still keep a module-global counter, use mutable `Type.object` data, or declare overly broad access. Restrict those patterns. Its perf build cannot be the enforced default without restoring access and cycle checks; forking its build becomes maintenance we own.

## Determinism, saves and late join

Native Becsy order is **history dependent**: creating stable IDs `[1,2,3]` versus `[3,1,2]` yields different query sequences. `orderBy(entity => entity.read(StableId).id)` gives `[1,2,3]` in both checked and perf tests. The shipped `PackedArrayEntityList.remove` fills a hole with the last entity. Immutable unique game IDs and ordering at every order-sensitive traversal remain necessary; sorting only the final snapshot does not fix competition outcomes.

E's `ids/each` already use ascending stamped IDs. The measured bitECS facade preserves that order; its native queries and the raw library remain distinct from that promise. Stable game IDs must stay separate from recycled backend handles. Named system ties and admitted command order must also be canonical.

A server-authoritative world can use its own native order if clients only consume authoritative results and the order has no gameplay significance. It cannot assume the same order after loading, rebuilding or prediction. Resource competition, reproducible server replay and the nine remaining client-lockstep states need canonical order and deterministic math. Server authority reduces who executes rules; it does not make hidden history dependence harmless.

**Becsy supplies no built-in serializer.** Boogle would own stable component/field IDs, schema versions/defaults, safe-integer bounds and encodings, stable entity/reference remapping, canonical hashes, full and audience-filtered snapshots, staged validation/publication, delta journals with independent cursors, and atomic room saves. Late join needs a snapshot at a known tick/revision plus ordered later updates, component removal/despawn semantics, duplicate/gap detection and resynchronization. Prediction needs independent scratch state, reconciliation and effect deduplication. Accepted command/event durability is also ours. Query change tracking is not a network protocol, a persisted command log or a multi-consumer replication journal.

Snapshots need not preserve old save shapes. A namespace reset is acceptable; retain current-build round-trip validation and deterministic trace fixtures. Bumping a version does not justify accepting malformed state or leaking private server components to clients.

All three options still require C# for a full Unity sim port or C++ for a full Unreal sim port. Renderer/materials/TSL, input/UI/audio, resource lifetime, scene authoring, physics integration and netcode must be rebuilt or replaced for the new engine. ECS does not turn Rapier into Unity/Unreal physics, and neither DOTS nor Mass automatically reproduces our room protocol. What survives is a language-neutral schema/catalog, stable IDs, access manifest, group graph, admitted traces, receipts and expected canonical results. Dynamic strings, optional fields, float bits, overflow and collection order need explicit cross-language rules.

### Keep TypeScript on the server and port only the client

This is a credible alternative and avoids rewriting the economy/command rules. The native client implements the versioned room protocol, mirrors components, interpolates/predicts its declared subset, and sends commands. Rendering and physics/view/input still move; client netcode still needs a native implementation.

For it to work, server-owned gameplay must be executable headlessly with no browser/three.js dependencies; authoritative outcomes cannot depend on client scene state; IDs/units/content schemas must be language-neutral; replication must support full baseline plus ordered deltas and private-field selection; command admission, duplicate receipts and validation must belong to the server; presentation effects need committed event identity. Client physics observations enter rules as validated recorded inputs. Match physics/collision content versions where interactions depend on them.

The railway already fits much of this authority shape. **The nine classic lockstep states do not yet permit a simulation-free client.** Migrate them to server replication before removing native-client simulation, or port/host their TypeScript rules in the native client as an explicit interim cost. Required client prediction also needs a native rule subset or an embedded runtime. Keeping the TS server does not automatically provide offline play or a replacement for all client-side simulation.
