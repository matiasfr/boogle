# Route Codex work by uncertainty, then measure completed jobs

_2026-11-03. Model and reasoning-effort selection for Boogle on Codex CLI 0.166.0. Live official documentation, an authenticated CLI inventory, independent API benchmarks, and nine local jobs were inspected. Repository references use this worktree at `2086f12c`; run evidence lives in the main checkout. This is a routing recommendation, not a launcher/configuration change or a new gameplay plan. All external sources were accessed on **2026-11-03**; publication dates appear where available. “Live, undated” means the page supplied no publication date, not that its contents are timeless._

**Evidence labels:** **[O]** official documentation or OpenAI's own evaluation/claim; **[I]** independent evaluator's own measurements; **[L]** inspected local CLI, code or run record; **[A]** an operator's anecdote; **[R]** recommendation/inference, not a measured result. Reading a report establishes what it recorded, not independent reproduction of its gameplay or visual judgment. No model trials, game captures or GPU benchmarks were run for this research.

## Answer

**Keep GPT-6.1 Terra low for implementation whose shape and acceptance checks are already clear; use GPT-6 Astra high when discovering the cause, validating the test itself, or recovering through several tool/action/check cycles dominates.** Trial Terra medium and GPT-6.1 Sol medium before adding a permanent middle route. Do not make `xhigh` the automatic price of the words “research” or “review.” Reserve it for a concrete unresolved question; use `max` only when a comparison demonstrates value.

This serves [DESIGN.md](../../DESIGN.md)'s **Small and readable** and **Light tests, real playtests** principles. [AGENTS.md](../../AGENTS.md)'s Codex-first, verification, test-diet and owner-playtest calls remain binding: routing cannot reduce the required evidence, replace a failed check with a claim, or continue development after the owner needs to play. A cheaper successful job is useful; a cheaper incomplete job is not the objective.

## What changes from low through max

**[O]** [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning), **live, undated**: effort guides internal reasoning; models adapt to task difficulty within a setting. Reasoning consumes context and is billed as output. There is no published fixed “low = N tokens” budget, guaranteed speed multiplier, or guarantee that higher effort improves every answer. The [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist), **live, undated**, explicitly asks for representative evaluations before using xhigh/max.

| Effort | Documented intent [O]                                                   | Boogle interpretation [R]                                                                                                  |
| ------ | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| low    | Modest reasoning, lower latency/usage; execution and focused tool work. | A known edit, known files, known acceptance command. Still perform every required check.                                   |
| medium | More planning/judgment with balanced latency and quality.               | First trial for a bounded job with one or two unknowns; Terra medium is not yet locally validated.                         |
| high   | Complex debugging, planning and multi-step work.                        | Astra's locally supported choice for root-cause work, sync reasoning and recovery across failed attempts.                  |
| xhigh  | Deeper long-running research/review when evaluations justify it.        | Escalate a named ambiguity: competing failure causes, contradictory sources, or an invariant the high pass cannot resolve. |
| max    | Greatest reasoning depth on the hardest tasks.                          | One bounded hard question with a discriminating check, followed by an assessment of whether it helped.                     |

Higher effort does **not** grant a new tool, larger CLI context, extra permission, guaranteed persistence or better frame capture. API `none` exists for several models but is absent from this CLI's advertised effort lists; Boogle's launcher accepts only low–max. The launcher currently rejects `ultra`; that is not a model failure. API `reasoning.mode: pro`, the ChatGPT Pro subscription, Ultra delegation and `max` effort are different concepts.

**When more effort wastes usage [R]:** the answer is already specified; the bottleneck is a port, missing file, approval or wrong camera; successive attempts gather no new evidence; repeated full checks add nothing after affected checks pass; or the remaining decision belongs to the owner. Fix the environment/brief, narrow the diagnostic question, or stop at the owner gate. Do not turn a 404 into longer thinking, rerun a flaky bot without preserving the failure, or spend max on cosmetic wording.

This is also a prompting issue. **[O]** Eric Provencher's [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), **2026-09-11**, describes premature stopping from overly strong review boundaries and redundant testing from accumulated instructions. Define done as implementation **and** the applicable checks/captures/recovery. This supports clearer briefs; it does not authorize removing Boogle's binding rules.

## Numbered recommendations for Boogle

1. **Route by remaining uncertainty and acceptance risk.** Keep Terra low for known implementation and Astra high for unknown-cause/multi-step recovery, following [AGENTS.md](../../AGENTS.md)'s Codex-first call. Classify the actual task, not just its file extension: a one-line ownership bug can be harder than a whole clothes adapter.
2. **Pass model and effort explicitly.** [`dev/codex/run.ts`](../../dev/codex/run.ts)'s mode defaults are coarser than this report. Use `--model gpt-6.1-terra --effort low` or `--model gpt-6-astra --effort high`; retain `meta.json`/per-turn provenance. Propose changing the research/review xhigh defaults only after the trials, not silently in this documentation commit.
3. **Give every worker a completion contract and an honest stop rule.** Include exact files, known evidence, scope, required checks, capture question, and permitted recovery. For [two-player.md](../plans/two-player.md), distinguish committed steps, conservation/sync checks, bot tolerance and the final Round-4 checkbox. A failure report can be correct behavior; escalation should use it.
4. **Escalate with the failed evidence, not a fresh vague brief.** Use [`run.ts resume`](../../dev/codex/README.md#follow-up-feedback) with an explicit model/effort override when the job still owns the right checkout. Preserve the reproduction, patch, failed command and artifact; state the unresolved hypothesis. Correct capture/setup faults before spending more reasoning. Go straight to Astra high for consequential sync uncertainty rather than requiring a cheap failure first.
5. **Trial Terra medium and Sol medium before institutionalizing them.** Compare against the same pre-fix build and identical brief, using the existing [deposit checks](../../dev/look/evals/place-coop.ts) and [bot](../../dev/look/bots/place.ts). Our data cannot distinguish model capacity from effort, briefing or inherited diagnosis. Luna high is a separate candidate for exact extraction, not an automatic replacement for Terra implementation.
6. **Use xhigh/max only for a question that can change the result.** Apply this to [`run.ts`](../../dev/codex/run.ts)'s research/review modes and [architecture-review](../../.claude/skills/architecture-review/SKILL.md): seek a concrete unresolved claim, counterexample or dependency. For review, judge actionable findings and false positives; for simplify, preserve behavior and inspect the required playthrough. Do not create more findings or refactor scope to justify effort.
7. **Keep visual and multiplayer acceptance independent of model choice.** Follow [`dev/codex/README.md`](../../dev/codex/README.md)'s broker/handoff contracts and [AGENTS.md](../../AGENTS.md)'s look workflow. Inspect the changed action and PNGs, use curves where appropriate, and say real-time motion is unverified when it is. Previz explores a target; it cannot pass a playable feature or approve a shipped image.
8. **Measure total accepted-job cost and keep Standard speed for unattended work.** Extend the reporting practice around [`dev/transcript.ts`](../../dev/transcript.ts) with full input/cache/output, effort, speed, wall time, retries, review and outcome; no new telemetry implementation is part of this report. ## Three small trials to resolve the gaps

Use independent checkouts of a **fixed pre-fix commit**, identical instructions, tools, permission boundaries and acceptance criteria. Hide the historic diagnosis/final patch from workers. Include a no-change baseline to catch broken fixtures. Serialize GPU runs; record model/effort/speed, all input/cache/output, wall time, caller interventions and acceptance evidence. These are screening trials, not statistically reliable rankings; repeat a surprising result before changing a default. A stop at the diagnostic timebox is “unfinished,” never a pass. Continue necessary production work separately.

1. **Does medium fix Terra's recovery gap?** Use one reproducible failing subcase of the existing deposit/conservation check from `two-player-build`'s starting commit, after the director validates the criterion. Compare **Terra low, Terra medium, Astra high**, each with the same criterion and no diagnosis; cap each diagnostic trial at 15 minutes. Pass requires corrected conservation, no new departure loss and the existing focused check. This separates effort from inherited help and asks whether medium avoids an expensive restart.
2. **Is Sol the missing coding middle route?** Give **Sol medium** and **Astra high** the same small unknown-cause bot failure from `bot-reliable-2`'s pre-fix build. First prove it reproduces cheaply; otherwise choose another frozen failure. Allow 15 minutes of diagnosis, then have the director replay the candidate fix with the same existing bot segment. Pass requires the reproduced failure to be fixed and an unchanged control segment to remain healthy, with identical baseline, seed and runtime conditions for both routes. Compare cause accuracy, accepted fix, review/rework and full usage. Do not rerun the entire 28-minute historical investigation just to fill a leaderboard.
