# ECS alternatives: live health, enforcement and an honest engine exit

> **Verdict:** Under the owner's criteria in their stated order, **standalone Bevy ECS in a Rust simulation core ranks first; checked Becsy ranks second and is the strongest TypeScript choice reviewed**. Bevy buys language-enforced access as well as a maintained scheduler; Becsy buys useful runtime rails without changing languages, but has concentrated maintenance and deliberately unsafe performance builds. Becsy improves the specification for a later port, especially DOTS/Mass; it does not make TypeScript or TSL portable engine code. Basis: [Bevy access model](https://docs.rs/bevy_ecs/latest/bevy_ecs/), [Becsy build contract](https://lastolivegames.github.io/becsy/guide/deploying) and [portability evidence](#what-a-becsy-shaped-game-actually-ports-to).
> **Top recommendations:** 1. Compare one Rust/WASM Bevy rule slice before choosing the foundation. 2. If retaining TypeScript, adopt checked Becsy as the model, never `/perf`. 3. Preserve schemas, ordered command traces and renderer boundaries. 4. Prefer retaining the authoritative server when replacing the client. 5. Reconsider newer TS candidates only when they reject undeclared access in supported production builds.
> **Status:** open. Research and ranked advice, not an implementation decision; no game code changed.

_2026-11-13 UTC; **every live observation and fit judgement below is dated this day**. Checkout `b6a304396c4da43260882558c9f29f27b7810659`. Package dates are publication dates, not access dates. Judgements are mine; upstream guarantees, reports and unverified claims are distinguished. The owner's [Engine foundations first](../agents/owner-calls.md) ranks enforceability first, later engine transition second; save resets cost nothing. This supersedes neither that call nor the adopted [E plan](../plans/ecs-e.md). It refreshes the offline spikes' health sections, not their measurements._

This corroborates the 0.16.1 spike's bounded hang; it is not a new execution test. The [systems guide](https://lastolivegames.github.io/becsy/guide/architecture/systems#execution-order) promises cycle rejection without that build caveat. An older [cycle-finder bug #13](https://github.com/LastOliveGames/becsy/issues/13) was fixed **2021-11-16** for 0.10.0; it is a different failure. Searching all issues/PRs for `cycle` and `perf` found **no report specifically acknowledging this perf-build hang**; Discord/private knowledge is unverified. Keep the checked build in production, with an import gate; adopting a patched perf build would make its safety patch ours.

**Becsy multithreading remains unimplemented.** The [introduction warning](https://lastolivegames.github.io/becsy/guide/introduction) says so; the latest [dispatcher](https://github.com/LastOliveGames/becsy/blob/c92f00be4666eb6c3712165052c7955f208ce008/src/dispatcher.ts#L130) rejects `threads > 1`. The headline is aspiration. A separate worker hosting one serial world is an application choice, not Becsy parallel systems. Raw [bitECS](https://github.com/NateTheGreatt/bitECS/blob/main/docs/Intro.md) likewise supplies no declared-access worker scheduler.

**The boundary is the work, not a free speedup.** With any WASM core, pass a command batch in and a compact projection/event batch out; TS systems making per-entity FFI calls retain JS logic and weaken the core's access model. Strings/object conversions, copies, callbacks and handle lifetime add costs; memory views need care after growth, and neither [Embind](https://emscripten.org/docs/porting/connecting_cpp_and_javascript/embind.html#performance) nor [wasm-bindgen](https://rustwasm.github.io/docs/wasm-bindgen/contributing/design/js-objects-in-rust.html) erases those semantics. Expect mixed-language stacks/source maps and DWARF tooling, WASM startup/build artifacts, and extra debugging around IDs and buffers. No Boogle boundary cost, bundle size, native-versus-WASM equality or device compatibility was measured. Keeping three.js/Rapier is possible with data bridges; replacement physics is a separate choice, as [engine-long-term](engine-long-term.md#target-architecture-one-page-contract) proposes.

| **Phaser** [**4.2.1, 2026-07-09**, P12 6](https://registry.npmjs.org/phaser); [C12 ≥100, push **2026-08-21**; MIT](https://api.github.com/repos/phaserjs/phaser) | [Scenes and GameObjects with mixed-in components](https://docs.phaser.io/phaser/concepts/gameobjects), primarily 2D; no per-system RW contract or checked dependency DAG. JS with TS types. Object lifecycle is supplied, deterministic gameplay order is not implied. | Replaces the presentation framework with a 2D-oriented engine; a three.js layer is custom composition, not a port of TSL. Keep the Node sim separately; headless mode is not automatic server authority or network determinism. Poor fit for Boogle's current 3D renderer. |
| **Godot web export** [**4.7.2-stable, 2026-08-18**, C12 ≥100, push **2026-11-12**; MIT](https://api.github.com/repos/godotengine/godot) | [Nodes/scenes/scripts](https://docs.godotengine.org/en/stable/getting_started/step_by_step/nodes_and_scenes.html); [no built-in data ECS](https://godotengine.org/article/why-isnt-godot-ecs-based-game-engine/). Lifecycle, deferred calls and deletion do not provide declared RW access or system-graph cycle rejection. GDScript/C++ model, not native TS. | [Stable web docs](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html) require WASM/WebGL2, use Compatibility rendering, and still exclude Godot 4 C# web export. Three.js/TSL must be replaced; browser budgets change. Either keep Node behind a custom protocol, or replace it with a headless Godot server; Godot high-level RPC is not our WebSocket protocol. |

None of these four can, merely by adoption, stop an agent placing gameplay state in a script global or mutating another object's state. Their documented object APIs above support broader mutation than criterion 1 permits. Repository import/schema/registration gates remain necessary with **every** candidate; an engine is not a sandbox for its authors. That is why stronger graphics/editor support does not outrank Bevy/Becsy here, despite much healthier engine development.

## What a Becsy-shaped game actually ports to

The useful shape is **plain data + stable game IDs + declared RW + named groups/edges + explicit structural barriers**, not Becsy classes themselves. These are conceptual mappings inferred from the linked engine APIs, **not executed ports**. Full sim ports require language rewrites; a retained native core or server is a different strategy.

| Target | Mapping and what must change |
| --- | --- |
| **Unity DOTS/Entities** | Scalar components → `IComponentData`/buffers; systems → C# `ISystem`/`SystemBase`; reads/writes → typed query/Job access; groups and before/after → [ComponentSystemGroup, UpdateInGroup/Before/After](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/systems-update-order.html); structural changes → [EntityCommandBuffer and playback systems](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/systems-entity-command-buffers.html). **Closest conceptual match**, but TS classes/handles, JS strings/objects, schemas, order rules, prediction and views are rewritten/adapted; adoption does not establish equivalent release-build safety. |
| **Ordinary Unity GameObjects/MonoBehaviours** | [GameObject component composition](https://docs.unity3d.com/6000.0/Documentation/Manual/GameObjects.html) maps objects and adapters; pure C# rule services can preserve the sim's design. `Update`/`FixedUpdate` callbacks do not inherit Becsy RW entitlements or its group graph. Keep an explicit rule runner if those guarantees matter; do not mechanically turn each ECS system into an arbitrary MonoBehaviour callback. Scene/prefab, input, rendering and physics work still changes. |
| **Unreal Mass** | Components → fragments/tags/shared fragments; systems → C++ processors with [fragment access requirements](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/MassEntity/FMassFragmentRequirements); composition changes → [MassCommandBuffer](https://dev.epicgames.com/documentation/unreal-engine/overview-of-mass-entity-in-unreal-engine). Named phases/group ordering are a strong conceptual match. Types, handles, serialization, actor representation and networking are separate integrations; Mass is not ordinary Actor gameplay. Command batching is not automatically Boogle's admission order; [Mass operation-type flush order](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/MassEntity/EMassCommandOperationType) makes that distinction concrete. |
| **Ordinary Unreal Actors/components** | Stable-ID projections → [Actors, ActorComponents and subsystems](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-framework-in-unreal-engine); groups/edges can inform [tick prerequisites](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UActorComponent). These do not automatically restrict component reads/writes. Rewrite TS in C++/Blueprints or keep a separate sim core. Native Actor replication requires Unreal's replication model; a custom Node server needs a protocol client instead. |
| **Godot nodes/scenes** | Data → Resources/plain records or a separate sim; projections → Node/Node3D scenes; rule groups → a deliberate central runner, not automatic node callbacks. [Godot scenes combine behavior and data](https://docs.godotengine.org/en/stable/getting_started/step_by_step/nodes_and_scenes.html), so Becsy decomposition is useful separation but not a direct model transplant. GDScript/C#/C++ and scene lifecycle replace TS classes; C# web restriction above applies. |

**Godot community ECS is optional, not a built-in portability promise.** [GECS (`csprance/gecs`)](https://github.com/csprance/gecs) is GDScript/Node-oriented (**C12 ≥100; push 2026-09-19; CC0-1.0**); [Godex](https://github.com/GodotECS/godex) is an engine module (**C12 0; push 2023-09-18; MIT**, README still development); [Stagehand](https://github.com/VerdantInteractive/Stagehand) integrates Flecs through GDExtension (**C12 16; push 2026-09-21**, licence grant needs review). Other bindings include [GdFlecs](https://github.com/ArborExMachina/GdFlecs), [godot-glecs](https://github.com/GsLogiMaker/godot-glecs) and the [godot-turbo engine module](https://github.com/callmefloof/godot-turbo). Demos and working bindings are evidenced; **no shipped commercial game using these particular add-ons was verified**. Godot successes such as unrelated shipped games cannot establish add-on maturity. Native-extension web builds and engine-version compatibility require their own proof.

## Port reports: preserve the game, expect to rebuild integration

- **Unity, web origin:** Kingdom's developer [2016 interview](https://www.gamedeveloper.com/design/road-to-the-igf-noio-and-licorice-s-i-kingdom-i-) describes the 2012–13 Flash game becoming the Unity desktop game; art and core design carried forward, not an automatic Flash-code conversion. **Unity, custom origin:** inkle's [2015-09-10 80 DAYS announcement](https://www.inklestudios.com/2015/09/10/once_more_around_the_world) explicitly describes rebuilding in Unity with Cape Guy while expanding existing narrative content. These support content/design continuity, not reusable ECS source.
- **Unreal, custom origin:** Croteam's lead programmer [2023-10-18 interview](https://www.unrealengine.com/developer-interviews/inside-croteam-s-transition-from-in-house-tech-to-ue5-for-the-talos-principle-2?lang=en-US) describes moving from Serious Engine to UE5 and retraining programmers/content developers. This is a **sequel/team transition**, not a same-game portability measurement. A concrete counterexample to “all code is always rewritten” is TOSE’s [2023-06-07 Crisis Core Reunion account](https://www.unrealengine.com/developer-interviews/crisis-core-final-fantasy-vii-reunion-modernizes-a-psp-classic-using-unreal-engine?lang=en): it retained the original **C++ gameplay code**, skeletons and animation data, used Unreal chiefly for graphics/assets, and rebuilt environment/UI/effects assets. Same-language reusable logic made that possible; TypeScript/Becsy cannot claim the same source compatibility.
- **Godot, web origin:** Kaetram's developer [2024-04-23 port report](https://www.reddit.com/r/godot/comments/1cbegtv/converted_my_mmorpg_to_godot/) describes replacing its HTML5 client while retaining custom NodeJS/WebSockets; the [2025-02-04 follow-up](https://www.reddit.com/r/godot/comments/1ihr34e/kaetram_a_godotbased_mmorpg_8_months_later/) describes NodeJS/MongoDB and server/client path reconciliation. Developer testimony, not our code audit; the [Steam page](https://store.steampowered.com/app/2716120/Kaetram/?l=english) retains older forward-looking port wording, so current shipped binary/protocol parity is unverified.

**What to retain for Boogle:** schema/catalog data, art/audio source assets, design rules, stable IDs/units and expected command traces can specify the next implementation; tests' expected behavior transfers even when their TypeScript harness must be rewritten. That is an inference from those reports and [E's schema contract](../plans/ecs-e.md#result), **not a claim those studios retained their tests**. No primary report found here measures test reuse or demonstrates a Becsy → DOTS/Mass/Godot conversion. Three.js materials/TSL, physics glue, input/UI, resource ownership, scene authoring and client prediction all need target-specific work, consistent with [engine-long-term's identified seams](engine-long-term.md#target-architecture-one-page-contract).

## Keep the TypeScript authoritative server; port only the client

This is the strongest **source-preservation** route and does not depend on Becsy. [Colyseus's Unity SDK](https://docs.colyseus.io/getting-started/unity) explicitly connects Unity clients to Node rooms. Heroic's [Fish Game](https://heroiclabs.com/blog/unity-fishgame/) is an actual open Unity/Godot multiplayer reference using a non-engine Nakama backend, not evidence of a commercial shipped title; [Unreal's Nakama SDK](https://github.com/heroiclabs/nakama-unreal) establishes the same boundary is supported for Unreal. Kaetram above is direct developer evidence for Godot + a retained Node server. None is a drop-in Boogle transport.

For Boogle, preserve the server's command validation, receipts, economy and schemas; implement baseline + ordered deltas, stable-ID/entity mirrors, events, interpolation, input and local prediction in C#/C++/GDScript. The railway is already server-owned according to [engine-long-term](engine-long-term.md#what-the-code-actually-says); **the nine classic lockstep states still require either a compatible native sim or the authority cutover described in [replication R3/R4](../plans/replication.md#4-migration)** before a simulation-free engine client works. Porting only the client does not supply offline play or identical engine physics. A Rust/C++ core could instead survive via native FFI/plugin adapters, but this is a proposed integration with platform/build costs, not a verified cross-engine shortcut.

## Ranked recommendations for Boogle

1. **First by the two criteria as written: evaluate standalone Bevy ECS for the authoritative/predicted rule core.** Safe Rust access types plus maintained graph/command-buffer machinery are stronger than JS conventions; keep three.js/TSL views. Start with tune + job-clock using the [existing spike's same rule slice](https://github.com/matiasfr/boogle/blob/codex/becsy-model-spike/docs/research/becsy-model-spike.md), compare admitted traces and canonical results in browser WASM and native server builds, then choose. Restrict exclusive/unsafe access and expose commands/projections, not arbitrary mutable world handles. **Large language/build/ABI rewrite**, not a recommendation to build a whole custom Rust engine or a measured performance win. Basis: [Bevy's standalone/access model](https://docs.rs/bevy_ecs/latest/bevy_ecs/) and [schedule validation](https://docs.rs/bevy_ecs/latest/bevy_ecs/schedule/enum.ScheduleBuildError.html).
2. **Runner-up, and first if keeping TypeScript is an additional requirement: checked Becsy.** Pin 0.16.1 checked ESM in both browser/server, forbid perf imports and uncontrolled object components, make every gameplay domain register through one manifest, and reject missing/overbroad declarations. Replace [E's storage/access/scheduler](../plans/ecs-e.md), not merely its Maps; retain Boogle's schema, stable-ID, authority and receipt contracts. Require the spike's undeclared-access/cycle failures to remain failures in the actual production bundle. [Upstream's documented build distinction](https://lastolivegames.github.io/becsy/guide/deploying) makes this a deliberate supported-build choice; low maintainer redundancy remains a real ownership risk.
3. **Third: Flecs with C/C++ systems if the team deliberately wants a native core; do not choose raw bitECS/Koota to outsource access policy.** Flecs supplies more execution machinery, but binding maintenance and release-build access/cycle guarantees need proof. [EnTT's organizer](https://github.com/skypjack/entt/wiki/Entity-Component-System#organizer) and the TS storage libraries leave more scheduling/policy to us. In-house E is a fallback for bounded needs, but continuing to grow its framework contradicts this brief's desire to outsource the core; its earlier spike ranking is not binding against the owner's reopened criteria.
4. **Make the exit an explicit server/protocol/content boundary.** Extend the schema/trace assets of [E](../plans/ecs-e.md#result) and [replication](../plans/replication.md#4-migration); choose DOTS/Mass only if their workflow is wanted at port time. Ordinary Unity/Unreal/Godot object models can host a clean sim without adopting their data ECS. Keeping the TS authoritative server usually preserves more actual source than selecting an ECS because its terminology resembles an engine; the cross-engine client examples above establish feasibility, not zero work.
5. **Change the answer when evidence or scope changes.** A retained-TS requirement promotes checked Becsy to first; production-enforced access plus credible released/shipped validation could promote ecsia or another entrant. A committed Godot/Unity/Unreal move with an editor/content need justifies evaluating that engine directly. A Boogle WASM slice exposing unacceptable ABI/debugging/deployment cost can reject Bevy on demonstrated fit. Two-to-four players alone does not justify workers; don't trade safety for upstream throughput claims. Save resets and a pending playtest do not change any ranking, per [owner calls](../agents/owner-calls.md).
