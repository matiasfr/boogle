# Material pipeline: enough shading, missing shared authoring

_2026-11-03. Research only; source audit at `2e647d9e`, installed Three r187, live engine documentation and developer sources. **[V]** = code/source text read; **[A]** = talk abstract only; **[S]** = secondary account, unconfirmed; **[D]** = recommendation/inference. No implementation or new device test._

**Yes: Boogle needs a small shared material library. It already supports sophisticated materials; it does not need a new shading engine.** Standard PBR, imported glTF, vertex colours, procedural TSL and a complex custom ocean are present. What is missing is a named, consistent contract for agents to author timber, painted toys and foliage, and for the owner to tune them together. Keep faceted scenery, softened kit edges and Buddy's smooth shoulders; **no Buddy rim light**. The [look decisions](../proposals/boogle-2.md#look) make frozen late-morning sky plus AgX the reference for the new-water route.

## Recommendations, in order [D]

1. **Calibrate materials before adding post.** At `tod=0.24`, lock exposure and compare Buddy, timber, foliage, metal and knockdown stars. Fix the stars' colour-space tag and establish an explicit linear-HDR brightness parameter; preserve Buddy's intentional `0.15` fill, without rim. Review `skyOnSteel()` against the real environment before removing its fake emissive reflection. Owners: [impact.ts](../../src/features/impact.ts), [avatars.ts](../../src/player/avatars.ts), [place/look.ts](../../src/proto/place/look.ts). Follow the [colour report's material-first recommendation](../../../color-grading-research/docs/research/color-and-post.md), not its experimental 8× star gain as a shipping value.
2. **Introduce six named presets with one small typed schema:** `timber`, `paintedToy`, `foliage`, `stone`, `steel`, `feedback`. Build on [flat()](../../src/proto/flat.ts), [paint()](../../src/proto/place/look.ts) and [patchNode()](../../src/render/material-patch.ts), initially migrating the four identical place-stone definitions. Put reusable definitions outside prototypes, proposed `src/render/materials.ts`; do not make production import `proto/place/look.ts`. Keep special terrain and water graphs separate. Preserve authored glTF values unless an asset explicitly opts into a named preset.
3. **Expose the same presets in the asset stage and Dev dock.** The [dev-tools research](../../../dev-tools-agentic/docs/research/dev-tools-agentic.md#a-separate-asset-and-animation-stage) proposes extending `/character/`; reuse that work and the [existing Dev-menu direction](dev-menu-plan.md). Show preset/override/source, swatch **and actual asset**, studio/shipped-sky comparison, colour/data channels and material/draw/pipeline counts. Preview overrides are Local and reversible; copy a typed diff for an agent to commit. Record camera, exposure, build and asset hashes with the owner's comparison.
4. **Prove consistency and cost on one kit before migrating broadly.** Compare unchanged and preset-backed stone/timber/foliage/Buddy/stars through [precompile.ts](../../src/render/precompile.ts) and existing startup/profile tools. Hold route, camera, light and quality fixed; report material objects, distinct shader stages, render/compute pipelines, draw calls and cold reveal separately. Target **no additional pipelines or draws for equivalent output**, not an invented millisecond saving. Coordinate expensive-feature choices with the graphics-settings job; stop for the owner's look review.
5. **Add textures or richer models only for a visible need.** First prove one normal/ORM/emissive KTX2 asset through [build.ts](../../dev/assets/build.ts) and [assets.ts](../../src/render/assets.ts). Consider one trim sheet for repeated station beams only if geometry/grain cannot deliver the needed detail. Defer JSON material files until both Blender scripts and runtime genuinely need the same data. Do not build a node editor, universal master shader, layer stack, Substrate clone, general subsurface system, or a whole-project material migration now.

**Schema boundary:** preset ID; sRGB colour token; roughness/metalness in `[0,1]`; optional linear emissive colour plus nonnegative HDR gain; explicit opaque/mask/blend mode and sidedness; vertex-colour use and authored/flat normals. Grain axis/scale belongs only to the timber family. Colour/scalars are parameters; maps, alpha mode and graph features are structural choices. Cache equivalent immutable materials; use instance colours for compatible batches and explicit clones for per-player colour or temporary previews. A global preset edit must be intentional, never an incidental mutation of a shared cached material. A generated shared data file can come later without changing this contract.

## What exists today [V]

### Counts and duplication

These are **constructor sites in all `src/**/*.ts`**, including dormant prototypes/debug code, counted with the TypeScript AST. They exclude imported GLB materials, runtime clones, loops and Three's internal materials; they are not simultaneously visible materials or shader variants.

| Family    |   Sites | Actual use                                                                                                      |
| --------- | ------: | --------------------------------------------------------------------------------------------------------------- |
| Lambert   |   **4** | Simple toys/fall scene; diffuse lighting, no Standard specular model                                            |
| Standard  | **124** | 35 ordinary + 89 node constructors; most world, kit, character and prop surfaces                                |
| Physical  |   **0** | Available through Three/loader, absent from authored code and built GLBs                                        |
| Sprite    |  **12** | 10 ordinary + 2 node; labels, impact stars, particles/snow                                                      |
| Basic     |  **35** | 5 ordinary + 30 node; unlit effects, sky, custom water                                                          |
| Other     |   **6** | 2 PointsNodeMaterial, 1 debug ToonNodeMaterial, 3 bare NodeMaterial output helpers                              |
| **Total** | **181** | **127** explicitly node-material constructor sites; **36 files** assign relevant node slots or call `patchNode` |

“Custom TSL” overlaps those families: a Standard node material can retain its stock PBR lighting while replacing colour or normals. The 36-file count detects assignments to colour/position/normal/emissive/AO/mask/opacity/fragment/output/roughness/metalness slots and `patchNode` calls; it is **not 36 unique shader graphs**. Built-in materials are converted to node equivalents by the renderer ([contract](../../src/render/reference/materials.md), installed `StandardNodeLibrary.js`).

**Hand duplication:** whitespace-normalized constructor arguments identify **13 repeated shapes across 35 sites (22 repetitions beyond the first)**. This is a syntactic candidate count: `{map: tex}` can refer to different textures, and later patches can differ. Two concrete identical starting recipes are stone at [chop.ts](../../src/proto/place/chop.ts#L85), [drop.ts](../../src/proto/place/drop.ts#L34), [pieces.ts](../../src/proto/place/pieces.ts#L101), [stations.ts](../../src/proto/place/stations.ts#L51), and steel at [track-machine.ts](../../src/features/track-machine.ts#L48) / [net/rails.ts](../../src/proto/net/rails.ts#L23). Do not call all 22 safe deduplications. `flat()` and `paint()` already cache; this is consolidation of existing practice.

### Channels: used versus merely wired

[assets/src](../../assets/src) contains three Blender Python generators and an animation GLB. Reading the four **built GLB JSON chunks** found **7 explicit materials** (Buddy 4, scaffold 3), **0 images/textures**, and no material extensions. `place-kit.py` deliberately exports geometry without materials; `hero-clips` supplies animation. Thus **no imported texture channel, including KTX2, is currently demonstrated by these assets**.

| Channel               | Working code/content path                                                                                                                     | Import/build status                                                                                                            |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Albedo                | Material colour, vertex colours, canvas maps, procedural grain/terrain                                                                        | Base-colour factors exercised; glTF base-colour texture wired, unexercised                                                     |
| Normal                | Authored/smooth/flat mesh normals; terrain mixes smooth grass and faceted rock; water derives slopes                                          | glTF normal map wired, no shipped normal-map asset                                                                             |
| Roughness / metalness | Standard scalar controls; steel `.45/.7`, timber typically `.85/0`                                                                            | GLB roughness and dielectric metalness exercised; packed roughness **G**, metalness **B** wired                                |
| AO                    | [bakeContact()](../../src/proto/place/look.ts) darkens vertex colours; blobs add contact shade; optional GTAO is post, not a material channel | glTF AO **R** wired; no AO texture. Vertex darkening also affects directly lit colour, unlike proper indirect-light AO         |
| Emissive              | Buddy fill, crystals, signs, fire, fake steel reflection; values chosen locally                                                               | Emissive factor/map and strength extension wired in loader, unused by built assets                                             |
| Opacity               | Transparent sprites, ghosts, additive glow; node masks/fades                                                                                  | glTF OPAQUE/MASK/BLEND wired, built materials opaque. Alpha coverage is not optical transmission                               |
| Height                | Custom water vertex displacement, terrain geometry                                                                                            | No generic authored height/parallax workflow; core glTF has no height material channel                                         |
| Clearcoat / sheen     | No Boogle preset or content use                                                                                                               | Loader extensions → Physical → PhysicalNodeMaterial exist; build registers extensions, but export/render round-trip not proved |
| Transmission          | Custom water refraction/absorption works in its own graph                                                                                     | Physical transmission/volume route exists in loader; no imported glass fixture; current train “glass” is opaque Standard       |
| Subsurface            | Water's hand-written crest scattering approximation only                                                                                      | No general skin/foliage SSS workflow; volume attenuation is not proof of subsurface scattering                                 |

Evidence: [loader and conversion](../../src/render/assets.ts), [build/encoding](../../dev/assets/build.ts), installed `GLTFLoader.js` and `MeshPhysicalNodeMaterial.js`, [terrain](../../src/proto/place/look.ts), [water surface](../../src/render/water/surface.ts). The water alone combines wave displacement, computed normals, depth refraction, absorption/scattering, sky reflection, GGX sun/glitter and foam in a **MeshBasicNodeMaterial**: class name does not measure shader complexity.

**Authoring today:** an agent writes a code constructor or calls `flat/paint`, adds TSL slots and uses `patchNode` when extending someone else's material. Alternatively it writes `assets/src/<name>.py` with Principled BSDF factors/vertex colours → `npm run assets -- <name>` → committed optimized GLB → `loadAsset().instance()`. The build deduplicates/welds/prunes, optionally simplifies, then meshopt-compresses; textures resize and use **ETC1S for sRGB colour, UASTC+zstd for data/normal** when `ktx` is available. Checks reject non-KTX2 textures above 256 px. This is asset packaging, not a shared material vocabulary or validation of Blender's arbitrary node graphs.

**Geometry and sharing:** [land.ts](../../src/proto/place/land.ts) stores the ground palette in vertex colours and batches tree crowns/trunks; [props.ts](../../src/render/props.ts) merges coloured geometry; [look-kit.ts](../../src/proto/place/look-kit.ts) batches by part/material and supplies code colours/contact shading. Kit bevels use authored smooth/weighted normals while rock keeps facets. `Asset.instance()` clones objects with shared geometry/materials; Buddy deliberately clones `M_Main` per player before tinting in [body.ts](../../src/player/buddy/body.ts). Shared materials alone do not turn separate meshes into one draw.

### Frozen sky, AgX and suspicious values

[frozen-sky.ts](../../src/render/water/frozen-sky.ts) bakes `tod=0.24` once, installs the cube as environment/background, aligns the real sun and derives hemisphere fill for Lambert. Standard surfaces gain environment response; unlit sprites do not. [water/post.ts](../../src/render/water/post.ts) meters linear HDR, applies AgX then sRGB. The old route retains Neutral; the short agent rendering summary still saying “Neutral” is incomplete for this route.

- **Stars:** [impact.ts](../../src/features/impact.ts#L267) has one unlit SpriteMaterial for four stars, a CanvasTexture with no sRGB tag and no HDR brightness budget. Lighting changes cannot brighten it. The sibling [colour research](../../../color-grading-research/docs/research/color-and-post.md#why-the-stars-are-dark) inspected actual comparisons; this audit confirms the code, not a new screenshot. Correcting the tag alone darkens the raw midtones; calibrate radiance too. `toneMapped=false` cannot bypass a later full-scene AgX pass.
- **Emission is ad hoc:** Buddy `.15`, crystals `1.5`, far shard/sign `1.6`, museum `3`; HDR emission above 1 is valid. `skyOnSteel()` explicitly fakes a missing environment that the new sky now supplies: a potential double contribution, not measured proof of a visible defect. [look-world.ts](../../src/debug/look-world.ts) has experimental toon/detail/sway/rim patches; they are debug capabilities, and its rim must not graduate onto Buddy.
- **Range scan:** direct numeric property assignments across `src` gave roughness `.02–1`, metalness `0–.7`, opacity `0–.95`, emission `0–3`; no scalar range violation found. This does not bound expressions/uniforms. Intermediate metalness `.3–.7` is an artistic mixture, not a clean-metal calibration; scaffold's material named `iron` actually exports metalness **0**. Grain multipliers reach **1.24**, so white inputs can exceed unit reflectance; inspect the resulting colour, rather than banning HDR globally. Raw TSL `vec3` is linear; hex `THREE.Color` and generator hex conversion decode sRGB ([colour contract](../../src/render/reference/colour.md)).

### Shader variants and cold start

**There is no verified current whole-game variant count.** Counts depend on route, geometry attributes/skinning/instancing, node graph, lights/shadows, blending, targets and MSAA. Installed Three `Pipelines.js` shares shader stages by generated code and pipelines by stages plus render state. Equal colour/roughness parameter changes need not create another shader; baked TSL constants or structural features can. One named master with many switches can increase permutations, while a shared preset that only removes duplicate JS objects may leave GPU counts unchanged.

**Historical native-call baseline, inspected directly:** at `c03eff9a`, the first cold traces in `water-metal-tool/.look/cold-start/1793759116225` (new water) and `1793759778224` (old) recorded:

| `proto=place`, historical | Shader-module creation calls | Render-pipeline creation calls | Compute-pipeline creation calls |
| ------------------------- | ---------------------------: | -----------------------------: | ------------------------------: |
| New water                 |                          207 |       118 (82 async + 36 sync) |          24 (2 async + 22 sync) |
| Old water                 |                          164 |       101 (80 async + 21 sync) |                         2 async |

These include utility/post/compute work, **not unique material variants or current cache sizes**. Local raw [new trace](../../../water-metal-tool/.look/cold-start/1793759116225/1-cold-timeline.json) / [old trace](../../../water-metal-tool/.look/cold-start/1793759778224/1-cold-timeline.json) are machine-local, uncommitted evidence. Both reports retain `trueCold:false`; no isolated Metal compiler-time claim. The later [cold-start report](water-metal-cold.md) records 4.5–4.8 s reveal freezes before warm-up changes, then 318–400 ms longest reveal gaps in two coarse cold runs with a 16 s deadline. [precompile.ts](../../src/render/precompile.ts) now warms actual frame targets/passes as well as scene materials; `shadersMark()` reports cached stage-program and pipeline counts. Reduce **unnecessary structures**, retain warm-up, and measure; a material library alone cannot promise to remove the cold compile cost.

## What engines and shipped games teach

**Primary engine documentation read [V]:**

| System           | What it provides; what Boogle should borrow                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Unreal**       | [Master/instance inheritance](https://dev.epicgames.com/documentation/en-us/unreal-engine/instanced-materials-in-unreal-engine) exposes scalar/vector/texture parameters; ordinary parameter edits avoid recompilation, **static switches compile permutations**. [Functions/layers](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-material-layers-in-unreal-engine) reuse graph pieces and expose artist-editable layer stacks. [Domain, blend and shading model](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-material-properties) separately choose purpose, compositing and light response. [Substrate](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-substrate-materials-in-unreal-engine) composes principled BSDF slabs. Borrow parameter discipline and reuse; Boogle has no demonstrated need for a general multi-layer BSDF authoring system. |
| **Unity**        | [URP Lit](https://docs.unity3d.com/Packages/com.unity.render-pipelines.universal@17.0/manual/lit-shader.html) supplies standard PBR inputs; [Shader Graph](https://github.com/Unity-Technologies/Graphics/blob/master/Packages/com.unity.shadergraph/Documentation~/First-Shader-Graph.md) authors custom shaders. [Material variants](https://docs.unity.com/en-us/engine/6000.3/manual/materials-and-shaders/materials/materialvariant-landingpage/properties) inherit/override/lock values. [SRP Batcher](https://docs.unity3d.com/6000.0/Documentation/Manual/SRPBatcher.html) reduces CPU setup across draws using the same shader variant; it does **not** merge all those draws. Borrow defaults/overrides, not a claim that Boogle gains Unity's batching by adopting the naming.                                                                                                                                    |
| **Godot**        | [StandardMaterial3D/ORMMaterial3D](https://docs.godotengine.org/en/stable/tutorials/3d/standard_material_3d.html) cover common channels and shading modes. [ShaderMaterial](https://docs.godotengine.org/en/stable/classes/class_shadermaterial.html) shares shader code with different uniforms; [VisualShaders](https://docs.godotengine.org/en/stable/tutorials/shaders/visual_shaders.html) provide graphical authoring. Closest Boogle fit: a small preset resource over an existing shader, with custom TSL only where needed.                                                                                                                                                                                                                                                                                                                                                                                         |
| **glTF / Three** | [glTF PBR](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#materials) transports factors/textures, not an engine master graph. Extensions add optical features such as [transmission](https://raw.githubusercontent.com/KhronosGroup/glTF/main/extensions/2.0/Khronos/KHR_materials_transmission/README.md) and [sheen](https://raw.githubusercontent.com/KhronosGroup/glTF/main/extensions/2.0/Khronos/KHR_materials_sheen/README.md); installed loader also handles clearcoat, volume, IOR, specular and emissive strength. Three's [NodeMaterial](https://threejs.org/docs/pages/NodeMaterial.html) and [PhysicalNodeMaterial](https://threejs.org/docs/pages/MeshPhysicalNodeMaterial.html) already supply extensible shading. KTX2 compresses textures; it adds no new shading model.                                                                                                                         |

**Stylized production evidence:**

- **Astroneer [V]:** Bromell's [2016 developer interview](https://www2.unrealengine.com/developer-interviews/inspired-space-inside-the-development-of-astroneer?lang=fr) describes eliminating textures/UV work and using broad vibrant shapes for a small team's iteration. This supports Boogle's vertex-colour/code-first approach; it does **not** establish that today's Astroneer uses one atlas or one shader.
- **Sea of Thieves [V]:** Rare's [SIGGRAPH paper](https://history.siggraph.org/wp-content/uploads/2022/09/2018-Talks-Ang_The-Technical-Art-of-Sea-of-Thieves.pdf), pp. 1–2, documents stylized scattering/foam over FFT water and cheap art-directed cloud shading. A simple visual language can coexist with a specialized complex sea. Keep Boogle's ocean separate from common prop presets.
- **A Short Hike [V, mirrored primary text]:** [Robinson-Yu's thread](https://threadreaderapp.com/thread/1113100182655262721.html) describes triplanar terrain, selecting the strongest splat channel for crisp boundaries, and depth-based shore foam. Reusable targeted rules beat demanding every PBR channel on every object; this source does not establish a shared palette-atlas implementation.
- **Tunic [S, unresolved]:** a [republication of Unity's interview](https://d-data.ro/smoke-mirrors-and-scrolling-textures-behind-the-scenes-of-tunic/) attributes Shader Forge, batching, precomputed GI and scrolling-texture effects to Shouldice. Both original Unity URLs returned 404. Treat this as a research lead, **not verified technical evidence for this recommendation**; no claim about Tunic's master-material or atlas architecture.
- **Fortnite [V]:** Epic's [UEFN library](https://dev.epicgames.com/documentation/fortnite/material-library-in-unreal-editor-for-fortnite) exposes `M_FortniteBase_Parent`, simple colours and tiling materials, including shared wobble/destruction support. Borrow a consistent authoring entry point; this public creator API does not reveal every shipped Fortnite shader.
- **Trim sheets [A]:** Olsen's [Sunset Overdrive GDC abstract](https://gdcvault.com/play/1022323/The-Ultimate-Trim-Texturing-Techniques) describes standardized trim/normal layouts, UV scripting and a shader to improve small-team production and memory. Abstract read; talk not watched. A palette atlas stores colour swatches; a trim sheet stores reusable strips of surface detail. Both require coordinated UVs/padding/mips and only help draws when geometry/material batching is compatible.

**Boogle differs [D]:** agents already author readable TypeScript and Blender Python, so a visual graph editor saves less labour than it does for non-programming artists. The owner needs dependable previews and a few meaningful knobs. Browser startup compiles on the player's device, and asset download matters. Shared presets solve inconsistent defaults and repeated edits now; heavy layering solves a problem not yet demonstrated here.

## Options and decision [D]

| Option                      | Benefit / cost                                                       | Pipelines and cold start                                                                                    | Draw calls                                                               | Agent / owner workflow; viewer and dock                                                                                                                           |
| --------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stay ad hoc                 | No migration; drift and repeated fixes continue                      | Uncontrolled structural growth; no immediate change                                                         | No change                                                                | Agent copies constructors; owner asks for scattered edits. Viewer can inspect, dock has no coherent preset controls                                               |
| **Small shared library**    | Consistency, bounded schema, cheap incremental migration             | Same or fewer structures; uniform tuning avoids new variants; measure savings                               | No automatic reduction; enables compatible instancing/merging            | Agent selects preset + explicit overrides; owner tunes named groups. **Both tools: yes**                                                                          |
| Master material + instances | Powerful central graph; higher design/debug cost                     | Parameter edits cheap, many static feature combinations costly; one giant dynamic graph also costs GPU work | Still requires batching; instances are not mesh instances                | Agent configures switches; owner gains many knobs. Both tools needed, scope excessive now                                                                         |
| Data-driven material file   | Blender/runtime share values; schema/version/validation/export work  | Neutral by itself; backend graph choices decide                                                             | Neutral by itself                                                        | Agent edits data; owner saves validated diffs. Both tools useful once more than one authoring consumer needs it                                                   |
| Palette / atlas             | Shared colour control and fewer bindings; UV/tooling/mip constraints | Can unify structures; atlas alone does not collapse variants; adds texture loading                          | Can reduce material splits **with** merging/instancing, never guaranteed | Agent assigns palette indices/UVs; owner edits swatches. Viewer: atlas/UV inspection; dock: palette preview. Start with colour tokens/vertex colours, defer atlas |

The **graphics-settings** checkout was clean at `0562c947` when inspected; no new settings report or quality API was present, and its [graphics chapter](../../../graphics-settings/docs/game-design/graphics.md) still said no quality setting. This is a coordination dependency, not a completed integration: let that job own quality selection. Keep palette/emission semantics consistent across tiers; reduce costly normal/detail/transmission features only through explicit prewarmed families, not arbitrary per-object switches. The colour and dev-tools links above are sibling research snapshots, not merged contracts.

**Evidence limits:** source/build-data audit and historical trace inspection, not a fresh render or benchmark. Imported texture/Physical round-trips, present-build shader counts, savings and final material appearance remain unverified. No Boogler copy changed. Serves **Small and readable**, **Code first, images by approval**, and **Show, don't tell**.
