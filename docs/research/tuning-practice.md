# Tuning practice: named data, explicit authority, reproducible playtests

> **Verdict:** Typed defaults with owners, explicit authority, reproducible playtests.
> **Top recommendations:** 1. Edit a workbook revision or Git-tracked source table, with stable IDs and units in the schema. 2. Export evaluated values and retain the exact export. 3. Parse strictly: reject duplicate IDs, unknown/missing columns, empty required cells, locale-dependent numbers.
> **Status:** partly adopted. See [tunables](tunables.md).

## Summary

The useful precedent is not a giant bag of mutable globals. Games separate **authored defaults**, **effective runtime values**, **permission and timing of changes**, and **the record of what actually ran**. Consoles, inspectors, spreadsheets, scripts and dashboards are interfaces to those responsibilities.

Boogle already has two good starting points: the classic haul's validated, room-wide `tune.set` and the water renderer's local bindings. Its main gaps are a common inspection vocabulary, effective-data identity across builds, and tuning provenance attached to playtests. Build those seams around existing owners; do not move all constants into one file or build a designer editor before an agent can read, validate, change and export a value. [I]

The smallest useful first delivery is **descriptors plus read/export tooling and playtest snapshots**. Keep committed TypeScript defaults, current room operations and existing local setters. Add no remote service, spreadsheet dependency or generic production-room mutation endpoint. Shared default changes still require the repository's mixed-build decision; a manifest is not itself a compatibility mechanism. [I]

## What shipped games and tools do

### Console variables: a small API before a UI

**Quake.** id's released `cvar.c` registers named variables, rejects duplicate registrations and command-name collisions, supports name completion, routes console read/write through `Cvar_Command`/`Cvar_Set`, and writes archived values to configuration files. Values are strings with numeric conversion. Crucially, its `server` flag broadcasts a notice; that code is not evidence of Source-style client enforcement or deterministic tick scheduling. Borrow discovery and one setter path, not permissive parsing. [id Software's implementation](https://github.com/id-Software/Quake/blob/master/WinQuake/cvar.c). [V]

**Source.** Valve's `ConVar` exposes defaults, typed access, optional bounds and change callbacks. Its flags distinguish persistence, cheats, notification, connection restrictions, reload requirements and demo recording. `FCVAR_REPLICATED` sends server settings at sign-on and on changes, while `FCVAR_DEMO` records designated values at demo start. Replication describes authority and distribution; it does not promise Boogle's same-tick lockstep semantics. [ConVar API](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/public/tier1/convar.h), [flag definitions and comments](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/public/tier1/iconvar.h). [V]

**Unreal.** Registered CVars have help, discovery and explicit source precedence; inspection can report `LastSetBy`. Project, device, command-line and console values do not simply win by execution order. Epic also describes sinks that process changes at a defined point before rendering, and warns about callbacks firing at awkward times or recursively. Its reference-variable shortcut bypasses several console-manager protections. For Boogle, record where a value came from and batch expensive local work; do not reproduce Unreal's full precedence hierarchy. [Epic's CVar documentation](https://dev.epicgames.com/documentation/en-us/unreal-engine/console-variables-cplusplus-in-unreal-engine). [V/I]

The reusable contract is `describe → inspect → validate → request change → observe applied result → export`. It works equally for a human console, an agent tool and a slider. The interface must distinguish a variable assignment from a command such as resetting a world: they have different consequences. [I]

**Do not confuse a data asset with mutable simulation state.** A character definition can be shared and immutable; health and accepted upgrades belong to the run. Photon Quantum makes the distinction explicit: simulation assets are immutable; changing an asset reference in rollback state is safe, but mutating the referenced asset's fields is not rolled back. [Quantum asset rules](https://doc.photonengine.com/quantum/v3/manual/assets/assets-simulation). [V]

Boogle's equivalent need not be an asset database. Small pure TypeScript objects and readonly tables already fit its source-first agent workflow. Keep a derived quantity derived: editing speed, duration and distance independently can create contradictory data. For a future deterministic progression curve, start with a versioned table of integer breakpoints and a specified interpolation/rounding rule, or precompute integer outputs. Do not import a visual spline evaluator with native nonlinear math into `src/sim`; [lockstep restrictions](../agents/lockstep.md) still apply. [I]

### Spreadsheets as source of truth: the importer is the architecture

Unreal's CSV workflow demonstrates a spreadsheet-to-typed-asset boundary, including field/key options and reimport from the source path. That is different from having each game client read a live workbook. [Data-driven gameplay](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-driven-gameplay-elements-in-unreal-engine). [V]

Metaplay provides a fuller production pipeline: Google Sheets or CSV become typed game-config libraries and compressed archives. Contents determine a version ID; offline development can hotload configs, while connected sessions retain their negotiated version after a newer config is published. Dashboard actions leave an audit trail. The docs explicitly warn that different active sessions can therefore use different versions when players interact. This is vendor-documented tooling, not proof of a particular game's unpublished pipeline. [Working with Game Configs](https://docs.metaplay.io/feature-cookbooks/game-configs/working-with-game-configs). [V]

If Boogle later needs broad economic tables, choose one authority for each dataset and use this pipeline: [I]

1. Edit a workbook revision or Git-tracked source table, with stable IDs and units in the schema.
2. Export evaluated values and retain the exact export. A formula is authoring logic, not runtime JavaScript; pin exporter/schema versions and exclude volatile formula results from repeatable builds.
3. Parse strictly: reject duplicate IDs, unknown/missing columns, empty required cells, locale-dependent numbers, non-finite values and broken references. Distinguish zero from missing.
4. Validate relationships, then emit canonical rows in stable order and compare the semantic diff. Do not depend on spreadsheet display rounding or row positions for identity.
5. Review and commit the source/export provenance and generated artifact together; CI regenerates or verifies its digest. Publish that artifact, never an unreviewed live sheet.

For the current eight haul knobs, a spreadsheet adds an export and merge problem without reducing authoring effort. A CSV view can be generated for comparison without becoming another editable authority. Start a real importer only when designers need repeated bulk edits or formulas across many rows. [I]

### Hot reload and live tuning: four different operations

| Change                                                        | Correct boundary for Boogle                                                            | Hidden work to expose                                                         |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Local uniform or audio mix value                              | Apply through its owner at a suitable frame boundary                                   | Refresh derived values; keep the old value available for reset.               |
| Local baked spectrum, material topology or allocated resource | Explicit rebuild/recreate action with completion status                                | Dispose replaced resources, invalidate caches and rebuild once per patch.     |
| Lockstep room rule                                            | Validated accepted operation at an authoritative tick, or restart with a pinned preset | Every peer, late join and restored save must see the same effective data.     |
| Code, catalog layout or incompatible rules                    | Build/reload plus compatibility policy                                                 | Updating source does not update all live instances or remote tabs coherently. |

These are proposals, not claims that every current setter handles them. Unreal Live Coding documents one concrete trap: changing constructor defaults in a `.cpp` file does not update existing instances. Godot custom resources do not automatically emit `changed` for custom properties; setters must do it when needed. Vite exposes explicit `accept`, `dispose` and persistent HMR data hooks, not a multiplayer transaction protocol. [Unreal Live Coding](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-live-coding-to-recompile-unreal-engine-applications-at-runtime), [Godot Resource](https://docs.godotengine.org/en/stable/classes/class_resource.html), [Vite HMR API](https://vite.dev/guide/api-hmr). [V/I]

For Boogle, disable in-place HMR of authoritative rules during a comparative run; restart/rejoin with a declared build. Local visual experiments can keep the existing water setters. Make a patch's validation complete before any mutation, and report whether it applied immediately, rebuilt successfully or requires reload. A successful setter call is not evidence that a shader, cached lookup or remote peer now reads the new value. [I]

### Remote config and live operations

Unity Remote Config supports environment-specific defaults and targeted overrides, with priority when several apply. Its SDK exposes an assignment identifier for analytics. These are useful facilities for controlled experiments, but selecting values separately for each user would be unsuitable for shared Boogle rules. [Unity overrides](https://docs.unity.com/en-us/remote-config/game-overrides-and-settings), [SDK reference](https://docs.unity.com/en-us/remote-config/sdk-api). [V/I]

Firebase explicitly separates **fetching** from **activation**, including activation on a later startup; it advises bundled defaults and warns against disruptive mid-use activation. Its template system provides version history and rollback. These are release-management mechanisms, not deterministic room agreement. [Loading strategies](https://firebase.google.com/docs/remote-config/loading), [template versioning](https://firebase.google.com/docs/remote-config/templates). [V]

If remote balance delivery eventually becomes necessary, the room authority should choose one immutable compatible bundle before play, persist its identity with the world, and admit only clients able to run it. Cohort assignment belongs to the whole room for shared rules; accessibility and quality settings can remain per player. Stage, validate, canary and promote a bundle, with a known-good fallback for new sessions. Rolling back a config publication must not silently reinterpret existing saves or remove already-earned goods. Active worlds need an explicit transition policy. [I]

That machinery is unnecessary now. Browser deployment already distributes new data with code; use the existing namespace/version rules for incompatible shared changes. Remote delivery does not remove compatibility work, and a client-side config service does not become the authority for resource costs merely because it returned JSON. [I]

### RTS and fighting games: identical inputs include the rules

**Age of Empires I/II.** Bettner and Terrano describe identical simulations receiving scheduled commands, synchronized random usage, checksum debugging and recorded games used as reproducible bug reports. Their Age of Kings lobby integration also locked selected settings at launch. This supports treating match setup and data as replay inputs, not just recording button presses. The paper does not document a modern tuning-bundle hash handshake. [GDC 2001 paper, pp. 2–6 and 8–9](https://www.gamedevs.org/uploads/1500-archers-age-of-empires-network-programming.pdf). [V]

**Factorio.** Wube describes periodic state comparison and desync recovery in its multiplayer development diary. Its API separately names startup, runtime-global and runtime-per-user settings and exposes defaults/bounds; runtime setting-change events carry a tick. Those are useful distinctions between when a setting can change and whose setting it is. [Wube multiplayer diary](https://www.factorio.com/blog/post/fff-55), [setting prototypes](https://lua-api.factorio.com/latest/classes/LuaModSettingPrototype.html), [setting events](https://lua-api.factorio.com/latest/events.html#on_runtime_mod_setting_changed). [V]

**Mortal Kombat X / Injustice 2 and GGPO.** Michael Stallone's GDC slides describe a substantially bit-for-bit deterministic loop, checks at points within a tick, and rollback re-executing frames. GGPO requires game-state save/load and deterministic frame execution. Neither source establishes the games' exact balance-patch distribution protocol. The necessary consequence is that a rollback must use the tuning that belonged to the replayed frame; an external mutable damage table would break that assumption. [NetherRealm's slides, especially slides 7, 10 and 14](https://media.gdcvault.com/gdc2018/presentations/Stallone_Michael_8FramesIn16ms.pdf), [GGPO integration model](https://www.ggpo.net/). [V/I]

Boogle should borrow the invariants, not adopt rollback physics. Its [sync contract](../agents/sync.md) explicitly keeps physics out of Lockstep. Shared economy rules need identical code semantics, catalogs, effective values, tick/order and seeded randomness. Owner physics can have separately governed movement parameters without claiming cross-browser deterministic Rapier. Local camera and rendering values must never become hidden rule inputs. [I]

**Recommended room lifecycle:** resolve and validate a compatible configuration before accepting play; pin it for the room; if a permitted rule changes, schedule it through the existing authority and record the applied tick; include the effective configuration in snapshot/recovery semantics; validate it on rejoin. A state checksum detects divergence after the fact. A startup data fingerprint prevents a known data mismatch, but cannot prove two different rule implementations are equivalent. Use an explicit rules/namespace compatibility decision as well. [I]

### Versioning and validation

There are at least four different identities; do not call all of them `version`: [I]

| Identity                    | What it answers                                             | Proposed Boogle treatment                                                                                                    |
| --------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Schema version              | Can this payload be parsed with these field meanings/units? | Version exported presets and telemetry manifests; reject unknown versions.                                                   |
| Rules/catalog compatibility | Can this build execute this world's rules?                  | Retain `WORLD_NS`, catalog revisions and state migrations; never infer compatibility from a cosmetic build difference alone. |
| Effective-data digest       | Which actual values, including defaults, were active?       | Canonical full values, explicit domains and units/schema identity; retain the payload behind the digest.                     |
| Session change sequence     | Which accepted revision was active at this tick?            | Room tick and ordered applied-change sequence; local changes use their own sequence/time.                                    |

Epic's Data Validation system supports custom rules in the editor and a command-line commandlet for CI. That separation is useful: convenient editor constraints are not the only validation boundary. [Epic validation](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-validation-in-unreal-engine). [V]

Boogle needs both **static** checks (known keys, types, finite/safe values, bounds, stable IDs and references) and **state-dependent** checks (cost not below stock, capacity changes preserving conserved items, no reinterpretation of in-progress jobs). Its existing `fits` check is already an example of the second. A typed TypeScript source does not validate an imported preset or an agent's runtime request. Reject invalid input with a useful error; do not silently clamp an experiment into a different experiment. [I]

Canonicalization should specify key order, numeric representation, missing/default handling and schema version. Keep deterministic integers in their existing units; calculate diagnostic digests outside hot ticks. A cryptographic content digest is useful for artifacts, while the current lightweight state hash serves ongoing simulation checks. Do not replace one with the other. Default-only edits and retired keys need deliberate compatibility treatment, even if their JSON shape did not change. [I]

### Playtest telemetry: identify the treatment, then measure the outcome

Source's demo-recording flag is a concrete precedent for recording configuration alongside a replay. Unity's assignment ID supplies an analytics join key. Mega Crit's GDC abstract describes balancing Slay the Spire using metrics alongside community feedback and game feel; only that abstract was checked, so this report makes no claims about their event schema or stored tuning values. [Source flags](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/public/tier1/iconvar.h), [Unity SDK](https://docs.unity.com/en-us/remote-config/sdk-api), [Anthony Giovannetti, GDC 2019](https://www.gdcvault.com/play/1025731/-Slay-the-Spire-Metrics). [V/A]

Boogle currently records the label of a variant, not a complete record of its effective tuning. A name such as `quick` or a development build ID cannot reproduce a run if values changed locally. Recommended records, fitting the current flat-event ingestion model: [I]

- One manifest event: schema, full build/source identity, namespace, catalog/rules revision, room tuning digest, local tuning digest, experiment label and expected row count.
- One bounded value row per registered key: manifest ID, domain, key, value and source. Split vector components into explicit scalar rows if needed. Write the full exported manifest into the existing evidence artifact too; never rely on a digest whose payload was discarded.
- An applied-change event: key, previous/new values, request identity, resulting digest and authoritative room tick; local changes have monotonic time and a local sequence. Record rejected requests separately, not as exposures.
- A completion marker for the manifest. Missing rows, uploads or application acknowledgements make provenance incomplete; summaries must not quietly group those sessions with complete baselines.

Use the applied configuration segment to compare time-to-verb, trips, failures and idle intervals. Do not compare an entire session against its final values after several mid-run changes. For the owner's small sample, a paired run and a gut question are more useful than an automated significance claim. Telemetry helps explain the playtest; it does not authorize more tuning after the [owner's playtest stop](../agents/owner-calls.md). [I]

## Numbered recommendations for Boogle

Ordered by usefulness; these are proposed implementation priorities, not approved work beyond this report.

1. **Keep typed defaults with their owning systems; add small descriptors.** Extend [the haul spec](../../src/sim/tune.ts) and describe [local water bindings](../../src/render/water/live.ts) with stable key, domain, type, unit, bounds, default source and apply policy. Help text should say what increasing a value does. Generate inspection data from those definitions instead of copying constants into a global tuning file. Keep renderer imports out of pure descriptors consumed by Node/sim. **Smallest proof:** enumerate the existing eight haul keys and one water value; each exported default matches its owner. [I]

2. **Preserve distinct local, Owner and Lockstep write paths.** [Haul-kit](../../src/debug/haul-kit.ts) already separates local and room knobs; retain that pattern in an agent adapter. A tool routes to local setters or accepted ops, never writes `rules.tune.tune.v` directly. Classify movement separately from purely cosmetic settings; follow [sync](../agents/sync.md). **Smallest proof:** a local look change stays local; a room change is refused outside `proto-` rooms and is reported applied only from `onApplied`. [I]

3. **Fingerprint full effective data and retain explicit compatibility rules.** Add defaults-inclusive manifests alongside [tune serialization/hash](../../src/sim/tune.ts), [build identity](../../src/build-id.ts) and [railway catalog identity](../../src/sim/railway-layout.ts). For future room admission/restoration, verify compatible rules plus the pinned data; changing the current hash/save semantics requires the [mixed-build contract](../agents/mixed-builds.md). **Smallest proof:** default-only differences yield different manifests; equivalent canonical values match; an unsupported saved configuration cannot become a fresh healthy world. [I]

4. **Use accepted single-key edits now; make future related patches atomic.** Keep [tune.set](../../src/world/rules/tune.ts). Until a versioned batch operation exists, use a fresh preset room for a coordinated cost/yield/cap experiment rather than claiming the Defaults button is transactional. A future batch validates all keys and cross-field/world constraints against a candidate state, then applies once at a stamped tick. **Smallest proof:** rejection leaves every value unchanged; both peers and a late join observe the same committed revision. Extend existing rule/replay checks for that sync contract. [I]

5. **Expose an agent API with results, not a mutable object or mandatory panel.** Use the existing [session harness](../../dev/look/session.ts) as transport for a bounded debug adapter: `list`, `get`, `validate`, `set`, `diff`, `export`, `reset-local`. Names here are proposed, not existing commands. Include expected current value/revision to prevent two agents silently overwriting each other. A response distinguishes queued, applied, rejected, pending rebuild and reload-required. **Smallest proof:** a script can inspect, try an invalid change, apply a valid one and export observed results without clicking a UI. Do not expose world reset as an ordinary setting. [I]

6. **Make reload cost and lifetime explicit.** Annotate [water bindings](../../src/render/water/live.ts) and [panel controls](../../src/debug/water-tuning.ts) as immediate, rebuild or reload-required, preserving current owner callbacks. Batch local rebuilds and dispose subscriptions/resources through existing ownership. Keep authoritative code reloads out of live comparisons. **Smallest proof:** change, reset and reload reproduce the same values; an expensive rebuild executes once, and an unavailable binding returns an error rather than a false success. Use existing look evidence for visual effects, not new UI unit tests. [I]

7. **Attach complete tuning provenance to the existing playtest stream.** Extend [record.ts](../../src/proto/playdata/record.ts), respect [playdata ingestion limits](../../server/src/playdata.ts), and show digests/completeness in [summary.ts](../../dev/playtest/summary.ts). Include snapshot rows and accepted change boundaries, plus full manifests in evidence artifacts. **Smallest proof:** two sessions on the same build with different runtime values are distinguishable and reconstructable; a missing row marks the snapshot incomplete. [I]

8. **Validate at authoring, load and accepted apply, including relationships.** Reuse [okTune](../../src/sim/tune.ts) and [fits](../../src/world/rules/tune.ts); put missing local range/type validation below the optional UI. Preserve progress and job semantics when a capacity or cost changes. **Smallest proof:** existing [pure tuning tests](../../test/tune.test.ts) and [world replay tests](../../test/world-replay.test.ts) cover new lockstep validation boundaries, including a world change between request and apply. Do not expand the test suite for ordinary feel adjustments. [I]

9. **Version presets and imports; defer spreadsheets until bulk authoring needs them.** Commit named, schema-versioned preset data with source/build provenance, referencing the actual owners in [production-core](../plans/production-core.md). Resolve partial authoring patches into a complete runtime snapshot before comparing them. If a sheet is added, use the strict export/validate/canonicalize pipeline above and a single source of truth. **Smallest proof:** export/import reproduces full values; stale schema and duplicate keys fail before mutation; a source change has a reviewable semantic diff. [I]

10. **Defer remote live ops and a universal editor; stop at the owner playtest.** Ship reviewed defaults through normal builds first. A future remote system needs room-level assignment, immutable bundles and save/rollback policy before runtime activation, following [mixed builds](../agents/mixed-builds.md) and [production-core recovery](../plans/production-core.md). Use agents to prepare a small named comparison with one gut question, then obey [owner calls](../agents/owner-calls.md). **Smallest proof now:** a clean exported baseline and one reproducible alternative, without adding a service or changing gameplay in this research task. [I]

## Smallest design, adoption boundary and gaps

**Adopt first:** add metadata beside existing definitions; provide read/list/diff/export through a lazy debug adapter; record resolved values in playtest evidence. Reuse current single-key room edits and local setters. Defaults remain Git-reviewed source.
