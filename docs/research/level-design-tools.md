# Level-design tools for agents: describe the place, prove the placement

_4 November 2026; source/live research began 3 November. Research, source audit and measured Node checks at `279cbc7167913401254113a21a9fe337daedcd51`, on `codex/level-design-tools`. Scope: reliable placement and traversal while Boogle grows into more authored locations; engine/studio practice, agent tooling, authoring options and a smallest proof. Recommendations only; no game changes, editor installation, browser playthrough or historical runtime replay. Not tested on a device._

**Implementation update:** [Executed results, 4 November](#executed-results--4-november-2026) supersedes the paper predictions where tested. The bounded implementation is **partial**, with failed coverage and a missed historical discriminator; it has not met section 9's acceptance.

## Answer

**Extend the existing checks around one inspectable description of each place's physical content. Keep TypeScript authoring; integrate Rapier queries and the existing bots before buying a new authoring workflow.** Agents need to ask which surface supports an object, what blocks its approach, what changes after construction, and which source owns the answer. A better editor or a larger language model cannot answer those questions reliably when the description omits the relevant geometry. [I]

The immediate gap is more specific than “Boogle has no level tools”: **`npm run level-check` still checks the classic island, while the default browser URL opens Round 4. A separate, fast `dev/economy/place-level.ts` already checks Round 4's terrain and ability gates.** Neither provides complete physical-scene coverage. Unify discovery and reporting first; then close the missing geometry and interaction coverage on one difficult place. Do not replace both with a new navmesh system before measuring that improvement. [L/I]

This serves **Show, don't tell**, **Telegraph everything**, **Leave something for the next visitor**, and **Small and readable** in [DESIGN](../../DESIGN.md). The desired player outcome is solid-looking things that behave solidly, discoverable routes with reliable returns, and new locations that preserve already-earned progress. [I]

**Disposition: prerequisite first, then a bounded experiment.** The current phase is a working Round 4 loop under repair, not a validated campaign-production pipeline: [the 3 November playtest](../playtests.md#2026-11-03-round-4-two-players-the-default-url) records both successful efficiency payoffs and spatial failures; [its tracker](../plans/round-4-notes.md) still distinguishes shipped fixes from owner replay. The [decision index](../proposals/boogle-2.md#current-decision-index) and Design Table call own the direction: path before train, movement abilities, materials/upgrades rather than global eras, and many places. Two owner calls bound this report: the [1 November entity decision](../proposals/boogle-2.md) says no level editor, because levels are made agentically (part 5 of [entity architecture](../plans/entity-architecture.md#part-5-a-headless-engine-for-agents) builds headless equivalents instead), and the later “not yet” list includes a level-building tool. Everything below stays inside those calls: queries, checks and evidence for agents; a read-only inspector at most. A drag editor would reopen them, and only the owner can do that. This research does not authorize a migration, a new island, or work beyond an owner playtest gate. [L/I]

- **[V]** Live primary documentation, developer account or research paper checked 3–4 November. **PROVEN** below means an identified production use; **DEMOED** means a bounded experiment; **VENDOR** means documented tooling capability. These labels are not interchangeable.
- **[I]** Inference or proposal. Effort and future runtime budgets are estimates unless explicitly measured.

## 1. What the tools actually check today

### Default does not mean classic

[`src/proto/flags.ts`](../../src/proto/flags.ts) makes a browser with no explicit selector equivalent to `proto=place&fresh=1&coop=1`; when `location` is absent, its explicit fallback is `classic=1`. [`dev/level/check.ts`](../../dev/level/check.ts) imports the classic composition in [`level.ts`](../../dev/level/level.ts): POI sites, classic `ROUTE`, classic prop scatter and the origin-centred ground. Its `today` label therefore means **classic today**, not the current entry experience. `--island=low` installs a synthetic classic/low URL before importing site modules, and checks only that comparison surface. A fabricated `--proto=place` option would not add coverage: unknown switches are ignored and the loader remains classic. [L]

[`dev/economy/place-level.ts`](../../dev/economy/place-level.ts) explicitly documents this split. It loads the pure place `layout`, `terrain` and `tech-layout`, connects footbridges and laid rail to a 2 m terrain flood, checks staged access to devices/pads, and reports rail grades and walk lengths. It checks jump, second jump, hook and glide expectations already; the movement report's proposed capability checks are therefore **partly implemented**. It is not called by the current `package.json` `check` chain. [L]

## 2. Source of truth and the cost of moving things

**Classic:** [`src/island/index.ts`](../../src/island/index.ts) discovers sites in sorted order, applies layout overrides, composes [`stamps.ts`](../../src/island/stamps.ts), and bakes centimetre samples. A `Site` contains x/z/direction, terrain stamps, keep-out discs and two-dimensional reach points; its separate content module creates the actual structure. [`src/blueprints/props.ts`](../../src/blueprints/props.ts) is a better existing pattern: plain placement/shape data drives both render and collider construction. Its sequential seeded draws are fragile to additions: an added RNG draw shifts later objects. [L]

[`src/island/layout.ts`](../../src/island/layout.ts) loads `dev/layouts/*.json` with Vite; it mutates moved POI sites and only the first existing `ROUTE.length` sections. Caves cannot move because their stamps use world coordinates. Spawn/court remain fixed. [`walk-layout.ts`](../../src/features/walk-layout.ts) pins the simulation's palms/perch back to [`home-land.json`](../../src/world/home-land.json), which contains **36 tree cells and one perch**. The server loads that land separately. This preserves shared addresses while changing scenery; it does **not** establish that moved scenery is at the same interaction location as a saved source. [L]

**Round 4:** [`place/layout.ts`](../../src/proto/place/layout.ts) is already a substantial declarative map: local coordinates around `ORIGIN={x:1000,z:0}`, paths, lines, station tables, groves, plots and named anchors. [`terrain.ts`](../../src/proto/place/terrain.ts) bakes a **391×271** sample grid, 2 m spacing over 780×540 m; [`land.ts`](../../src/proto/place/land.ts) renders it and creates a heightfield. Bridges and other solids are separate. [`tech-layout.ts`](../../src/proto/place/tech-layout.ts) supplies pads, rings, gates, devices and secrets to both checks and runtime. Other solids, contacts and interactions still live inside `rooms`, `sites`, `stations`, `rail`, `chop`, `tech`, `verbs` and related rendering modules. A tree's ground, a crate's arrival, an NPC's goal and a room doorway do not yet share one complete spatial record. [L]

[`job.ts`](../../src/proto/place/job.ts) stores shared and personal JSON slices under room-specific localStorage keys; [`coop.ts`](../../src/proto/place/coop.ts) coordinates the temporary co-op snapshot authority. **This is not production server-saved Lockstep railway state.** A new place tool must identify which model it is inspecting rather than treating every visible object as a server entity. Current prototype IDs and saved positional data still matter: moving or reordering objects may change a slice's meaning even if no core rule changes. [L/I]

**Other prototypes are individually routed content, not another uniform level format.** [`src/main.ts`](../../src/main.ts) eagerly discovers feature entries; [`flags.ts`](../../src/proto/flags.ts) selects `?proto=<id>`, a `?play` combination or chapter/variant. Entries such as [`proto-soapbox.ts`](../../src/features/proto-soapbox.ts) and [`proto-place.ts`](../../src/features/proto-place.ts) dynamically import their own implementations; the latter joins loading warm-up. Soapbox's authored route/markers live in [`course.ts`](../../src/proto/soapbox/course.ts), while its local ghost is saved separately in [`ghost.ts`](../../src/proto/soapbox/ghost.ts). Its vehicle and frame/physics callbacks belong to the loaded prototype, not to classic `Site` discovery. Shore is a different variant path: [`island/terrain.ts`](../../src/island/terrain.ts) loads [`shore/slice.ts`](../../src/proto/shore/slice.ts), whose mode switches the surface and collision together. A prototype must declare its own entry, state/lifetime and verification adapter; classic checks cannot certify either soapbox markers or smooth-shore triangles merely because they share the island. Existing targeted look/scenario evidence applies only to its named selection. [L/I]

### Reproducible coordinate inventory

At the inspected commit, a TypeScript AST count found the following. The measure is **numeric literal property assignments named exactly `x`, `y` or `z`**, accepting signed literals; not a claim that every literal is a level position or a bug. Numeric two/three-element array counts are reported separately because they also contain dimensions, colors and directions. Expressions, `.set(…)`, computed coordinates and imported constants are not counted. [L]

Within place, `layout.ts` contributes 114 and `tech-layout.ts` 79: **193/359, or 54%**, are in those two numerical owners. Reproduce the main measure without modifying the checkout:

```sh
node --input-type=module <<'JS'
import ts from 'typescript';
import fs from 'node:fs';
import path from 'node:path';
const walk = d => fs.readdirSync(d, { withFileTypes: true }).flatMap(e =>
  e.isDirectory() ? walk(path.join(d, e.name)) : [path.join(d, e.name)]);
const numeric = n => ts.isNumericLiteral(n) || (ts.isPrefixUnaryExpression(n) &&
  [ts.SyntaxKind.MinusToken, ts.SyntaxKind.PlusToken].includes(n.operator) && ts.isNumericLiteral(n.operand));
const files = walk('src/proto/place').filter(f => f.endsWith('.ts'));
let count = 0;
for (const file of files) {
  const ast = ts.createSourceFile(file, fs.readFileSync(file, 'utf8'), ts.ScriptTarget.Latest, true);
  const visit = n => {
    if (ts.isPropertyAssignment(n) && /^(x|y|z)$/.test(n.name.getText(ast)) && numeric(n.initializer)) count++;
    ts.forEachChild(n, visit);
  };
  visit(ast);
}
console.log({ files: files.length, xyzNumericProperties: count });
JS
```

## 6. The smallest useful machine interface

Build a **readable, versioned place manifest**, not a parallel game engine. Existing layout/site/blueprint authors should compile into it; initial adapters can preserve their current source formats. The manifest must record unsupported/missing systems explicitly so a green report cannot silently mean “all the objects the exporter happened to know about.” [I]

Suggested fields, not an existing API:

```text
place: stable ID, content version, origin, local bounds, source/dependency hashes
surfaces: stable ID, terrain triangles or primitive/hull data, material, walkability
objects: stable ID, source path/symbol, kit/version, transform, active condition
         visual bounds, physical shapes, support sockets/contacts, allowed overlap pairs
targets: stable ID, interaction ID, activation volume, valid stance region, approach/exit
edges: from/to surface, ability/state requirements, direction, action parameters
coverage: included creators, excluded creators with reason, missing expected IDs
budgets: per place/chunk/state geometry, materials, instances, colliders, bytes
```

Use explicit **support policy**: grounded, socket-attached, suspended, intentionally embedded, or nonphysical. A suspended sign should not trigger “floating”; a rock may bury its base deliberately; a load-bearing post needs declared contact. Model placement validity as relations rather than an arbitrary universal maximum ground gap. Likewise, intentional structural intersections need named pair/rule reasons; this is different from adding global `allow.ts` suppression debt. [I]

The same records should support three views:

1. **Node source queries:** `objectsIn(bounds)`, `describe(id)`, `dependencies(id)`, `surfaceBelow(position, context)`, `validate(region,state)`. Return local and world coordinates, source pointer and whether a result is exact or approximate. No renderer import.
2. **Headless physical queries:** construct the same Rapier primitives/triangles; probe support points, normal/height mismatch, initial body overlap, full body/head clearance, interaction stance and swept approaches. [Rapier scene queries](https://rapier.rs/docs/user_guides/javascript/scene_queries/) provide ray, shape-cast and intersection primitives with filters; its [JS guide](https://rapier.rs/docs/user_guides/javascript/getting_started_js/) explicitly separates physics from rendering. [V/I]
3. **Runtime readback:** enumerate actual active colliders/interaction IDs and compare with the expected manifest for that state. Overlay visual mesh, collider, support and rejected approach. A source manifest cannot detect a renderer forgetting to instantiate a collider unless readback checks that agreement. [I]

A support ray finds the first surface under a point; it does not prove footprint support, clearance or the correct floor. Query from a bounded expected elevation and named surface, sample feet/corners, and sweep the actual player's body/head shapes. Reject “unknown support” when geometry was omitted. Ground-height interpolation, heightfield triangulation and axis order must agree; `H(x,z)` cannot identify a room roof versus its interior floor. [I]

Start with advisory results containing measured residuals, ownership and a concrete suggested edit. Auto-fixes should be **proposed patches** with before/after witnesses: snap a grounded post to its named support, rotate a gate relative to a route socket, or move decor out of an approach. Never silently move a saved resource, shrink a collider or remove a gate merely to satisfy the checker. [I]

### Lockstep and saved addresses are part of placement correctness

All recommendations in this report retain the current [Lockstep](../agents/lockstep.md), [mixed-build](../agents/mixed-builds.md) and [registry](../agents/registries.md) contracts. Tooling/Local geometry may use floats, trig, Rapier, three.js and offline optimizers. Conserved shared quantities stay integers; Lockstep floats use only `+ - * /` and `Math.sqrt`, with seeded RNG, fixed order and ticks. **Quantizing a result after runtime native trig does not make its generation reproducible.** Bake and hash accepted sim-facing geometry/addresses, or generate them entirely under the deterministic rules. No `Math.random`, wall time, three.js or Rapier in Lockstep. [L/I]

Use stable authored IDs such as `(placeId, featureId)` independent of world origin, array order, render LOD and collider handles. This is a proposed future addressing boundary, not permission to reinterpret today's cell-addressed saves. Classic `home-land.json`, rule catalogs and world-input generation must agree on both server and client. A moved saved source requires a versioned migration or the project's documented dev-phase `WORLD_NS` clean break; catalog changes are not ordinary decoration edits. Keep `RULES` append-only within a namespace, validate old/missing data and respect hash-verified save guards. Prototype localStorage may take a new round key under the existing policy, but that is not a production persistence strategy. [L/I]

Runtime construction should derive the active physical state from accepted facts. Inspection may instantiate start/empty/part-built/settled states in a disposable fixture; it must not run a private second economy. Check routes and occupied space before solids appear; a later join reconstructs the current state without replaying an obstructive historical build. State changes affecting permanent walkable routes need the real shared-state contract when promoted. [I]

Capability checks should distinguish **base**, **double jump**, **hook**, **glide**, plus relevant built paths/gates and carrying restrictions. A new ability must be obtainable in the preceding state; required destinations should not become unavailable after acquiring it. Check intentionally forbidden early routes separately from required routes. Both may be broken by the same newly placed roof. [I]

For jumps, use the real controller's launch and shaped-gravity envelope, horizontal approach, second-press timing, head clearance and landing footprint; sample a forgiving interval, not one perfect arc. For hook, require 3D acquisition range, aim visibility, swept body corridor, supported arrival and reverse exit. For glide, account for entry/deployment height loss, steering, speed, descent and landing reserve. For trains and construction, static graph connectivity needs a state/time condition and a safe wait/board stance. Reuse [movement-abilities' proof design](movement-abilities.md#8-level-check-and-the-smallest-honest-proof), but replace its old tuning assumptions with current controller measurements. [I]

Headless Rapier provides cheap body-clearance and movement experiments **after the relevant place geometry and behavior have headless adapters**. Today's classic sim harness does not automatically run `place/moves.ts` or all its solids. Browser witnesses remain necessary for real interaction selection, camera-based hook acquisition, GPU-visible collision mismatches, lifecycle activation and co-op transitions. [L/I]

Engine file formats do not remove this problem. Unity's [Smart Merge](https://docs.unity.com/en-us/engine/6000.0/manual/get-started/project-configuration/version-control/smart-merge) performs semantic scene/prefab merges but can need conflict resolution; Unreal's [One File Per Actor](https://dev.epicgames.com/documentation/en-us/unreal-engine/one-file-per-actor-in-unreal-engine) reduces actor-file overlap but partial changes can leave dangling references. Godot's [text scene format](https://docs.godotengine.org/en/4.6/engine_details/file_formats/tscn.html) is version-control-friendly, while editor serialization rewrites some text. [V] Boogle should preserve small semantic patches and run dependency/ID/geometry validation after merges, whichever editor produced them. A text merge that succeeds can still join two incompatible bridge endpoints. [I]

Scaling means bounded work, not merely more polygons. Keep a far silhouette and actual local collision separate, prefetch before arrival, budget active material programs/draws/instances/colliders, and unload owned callbacks/resources.
