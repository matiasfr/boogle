**Extend frozen shot lists and the existing tunables interface. ### LUTs are useful, but their colour domain is part of the asset

Epic's [LUT guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-lookup-tables-for-color-grading-in-unreal-engine) describes a 16³ LUT flattened to 256×16 and warns that its display-referred LDR method does not transfer unchanged to HDR output. Scene-referred grading is a different operation. Pixar's [colour-management tutorial](https://renderman.pixar.com/color-management) likewise distinguishes linear rendering from the display transform. **S**

For Boogle, first reuse the existing contrast/saturation controls. If those cannot reproduce an approved grade, prototype an **optional** LUT in the existing output graph, with a declared input/output space, identity LUT, strength, content hash and reference image. A LUT authored from final sRGB captures must operate in that domain; never sample it as though it were scene-linear. A scene-linear creative transform would sit before the output curve and needs a defined HDR domain/shaper. Keep tone mapping and sRGB encoding exactly once. Verify identity, neutral ramps, saturated swatches and highlights across all chosen views. HDR scene storage is not evidence of HDR display output: this renderer currently outputs sRGB. **P, C**

### Programmatic interfaces and URL flags

[catalog.ts](../../src/tunables/catalog.ts) currently accepts finite numeric descriptors only. It aggregates haul settings, `post.centre` and an Owner feel spring. [dev/tunables.ts](../../src/debug/dev/tunables.ts) offers `list/get/validate/set/status/snapshot/diff/reset-local`, with provenance and revisions. Its Local read/write implementation is exposure-specific; adding descriptors alone does not make arbitrary visual values work. The [CLI](../../dev/tune.ts) already supports `--session` and `--broker`. Broker mode explicitly opens a fresh page per invocation, so it is unsuitable for a persistent sequence of local edits. **C**

Existing commands, source-verified but not executed here:

```sh
npm run tune -- list
npm run session -- start --query 'proto=place&dev=1'
npm run tune -- get post.centre --session
npm run tune -- set post.centre 0.12 --session
npm run tune -- snapshot --session
node dev/look/shots.ts dev/look/beats/dev-looks.ts --name looks-a
```

`dev=1` or `tune=1` enables water live uniforms; ordinary visits fold many settings into constants. The central URL path accepts numeric `t.<id>=<value>` overrides, e.g. `t.post.centre=0.12`. `lookPreset` selects a named Look. `evening=1` prepares day/evening and starts evening; `evening=preview` prepares both and starts day, with [setEveningLook](../../src/render/water/evening-transition.ts) requesting the fade. `skySize=512|256` selects smaller cubes; otherwise 1024. These change startup preparation, not cheap per-cell uniforms. `sky=toy` and its toy controls are retained opt-in experiments. `water=old/new` are retired selectors in [flags.ts](../../src/render/water/flags.ts), even though an older example list still includes `water=new`. **C**

### What one iteration costs now

**There is no defensible current seconds-per-iteration measurement in this checkout.** It has no `.look` evidence directory. Historical reports describe shared-machine runs; those timings are not performance evidence. A source wait, timeout, advertised command duration or old manifest is not an end-to-end benchmark. The useful current finding is the work repeated and avoided. **C, R**

| Path                       | Where time/work goes                                                                                                                                                                                                                                                                                                                                         |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Repeated standalone `look` | Stack/browser/page startup, entry/load and precompile, sky/water preparation, checkpoint restore or authored setup, warm-up, capture/PNG transfer, cleanup. Repeating a source edit can repeat the world lifecycle. `look.ts` defaults to 10 game seconds warm-up; warp means that is not 10 wall seconds.                                                   |
| Current shot queue         | [shots.ts](../../dev/look/shots.ts) groups beat/query/viewport/resolution; MSAA is encoded in the query. Each group loads once. Local mode starts a persistent session **for that group but stops it in `finally`**; broker mode submits a fresh `look --action` per group. A second submitted queue does not automatically reuse the previous frozen world. |
| Within one group           | [shot-page.ts](../../dev/look/shot-page.ts) warms every camera/variant with two draws, then captures each, repeats it, switches to another setting and back. That is six explicit draws per cell before restoration, plus pixel copies, diffs, PNG encoding/transfer and board assembly. These are deliberate correctness costs, not just rendering.         |
| Owner/agent review         | Opening many individual images, finding the correct build/camera, remembering previous values and reconstructing favourite settings. Existing labels/manifests help; repeated baseline preparation and missing reference/pick records still cost attention.                                                                                                  |

Existing strengths: fixed world cameras (player-relative cameras resolve once), requested/effective settings, actual scene submission checks, frozen shader/game clocks, repeat and switch-back pixel equality, lossless individual cells and native-pixel single-column boards through [sheet-render.ts](../../dev/look/sheet-render.ts). A/B slots/swap already exist in [Dev Looks](../../src/debug/dev/looks.ts). **C**

Two source-derived hazards matter before claiming universal live tuning. First, key/fill setters update their owner object while scene lights update on the normal frame loop; the frozen draw intentionally does not run that loop. A successful getter and identical repeat pixels could therefore capture an unchanged light. Second, the sky's debounced bake has no awaitable effective-state receipt, and a frozen timer is not a safe readiness signal. Treat both as integration risks requiring the first proof, not as browser-reproduced bugs. **C, P**

## Proposed fast loop and smallest first build

### The first build: a persistent nine-cell lighting wedge

Keep the current scene/camera and accepted look. Reuse the town camera from [dev-looks.ts](../../dev/look/beats/dev-looks.ts), resolving its player-relative coordinates once. Use the same authored Place setup, clearly labelled as a fixture. Add `sky.keyGain` and `sky.fillGain` to the numeric tunables path through adapters; retain the existing bindings as implementation owners. Include a synchronous presentation-only flush that updates the real lights while advancing neither simulation nor shader time. Do not call the whole game's update loop to flush one setting. **P**

At `post.centre=0.12`, Current/Neutral, fixed resolution and bloom off, sweep key `[0.96, 1.12, 1.28]` against fill `[2.4, 3.2, 4.0]`. The middle cell is the accepted baseline. These are bounded experiment values, not proposed new defaults. Freeze one settled scene for all nine cells; save requested values, effective owner values **and actual light state**. If a meaningful key/fill change produces no corresponding light-state change, fail. Pixel equality is expected for repeats, not necessarily between distinct candidates. **P**

Extend the existing session/capture transport with an explicit reuse mode for successive same-fixture lists. Reuse is conditional on source fingerprint, fixture/checkpoint identity, query, camera, viewport and resource settings. Source changes invalidate the warm session; numeric preset changes do not. For managed jobs, add equivalent ownership to the trusted broker rather than launching another browser implementation. Do not claim existing `tune --broker` retains local changes. **P**

First deliverables: the nine-cell PNG, full-resolution cells, manifest and a selected-cell JSON containing the exact patch plus baseline/build identity. Start with the existing board renderer; keep its readable native-pixel column, and add a compact 3×3 overview only as a derivative with links/IDs back to native cells. The owner can simply answer “keep 5; compare 2 and 8.” No in-game tuning UI is required. **P**

No cold-start promise and no subsecond promise for sky rebakes, pipeline compilation or MSAA changes. Measure the three targets separately. On a quiet machine run five warm batches, report median, maximum and failures; report cold preparation separately. Instrument queue wait, page/load, setup/restore, resources/compile, variant apply/flush, draw/GPU completion, pixel copy/encode/transfer and composition. Use the existing `--baseline` only to compare lifecycle costs with the same cells/probes; do not call it an exact replay of the old screenshot workflow. Log concurrent load and discard loaded runs as timing evidence. **P**

### Expand to a small representative fixture set

After the first proof, add three reusable views, not a full-game contact sheet:

1. **Calibration/Buddy:** actual Buddy and one wood, painted, foliage, stone and steel sample; 18% linear diffuse grey ball, chrome ball, neutral ramp and explicit linear/sRGB colour patches. Use owned diagnostic materials and the real output pipeline. Do not assume 18% reflectance should equal one fixed output pixel under every light/tone curve.
2. **Town/doorway:** sunlit cream, open shade, dark interior, physical sign and camera-facing label at actual play distance. This catches the exposure-versus-fill-versus-ink tradeoff the past reports exposed.
3. **Shore/horizon:** sky, sun lane, foam, water/land contact and distant silhouette. A separate underwater/waterline sequence validates motion after still selection.

Seed/freeze animated state and lock camera, FOV, resolution, look, exposure, overlay policy and source identity. Save the full resolved baseline, not only deviations from mutable defaults. Reference images carry their path/hash, colour-space assumption, crop and provenance; distinguish accepted previz, inspiration and actual game captures. Place each selected candidate beside its reference and baseline without stretching aspect ratios. Never grade the reference to make a match look better. **P**

### One tunables surface, explicit application costs

Extend [catalog.ts](../../src/tunables/catalog.ts) and [dev/tunables.ts](../../src/debug/dev/tunables.ts), rather than adding a second visual catalog. Owners retain direct runtime fields; no descriptor lookup per frame. Numeric controls come first, then typed booleans, enums and linear colour/vector values. Expose defaults, units/bounds, availability/reason, current value, source, revision and application mode. The needed modes are live uniform, presentation flush, asynchronous prepare/rebake, pipeline rebuild and reload. An unavailable prepared-evening sky edit must say so, not silently succeed. **P**

Apply a variant as one validated local transaction: restore baseline → select Look → apply explicit overrides → prepare/flush affected owners once → await effective revision/resources → draw. On failure restore the complete baseline and mark the cell failed. Coalesce sky fields into one bake; do not trigger one expensive operation per numeric setter. Cache a bounded number of prepared environments by full parameter hash, cube size and source version; reuse existing day/evening endpoints. Evict/dispose unused resources. A 1024 RGBA16F cube with mips is about 64 MiB of texels before PMREM and other allocations, so caching every sky wedge is not free. **P, R**

Parameter hot reload means updating this local transaction while retaining the world. It does **not** promise arbitrary TypeScript or shader-topology HMR without reconstruction. Material previews clone shared recipes; resource-changing settings declare rebuild/reload explicitly. Keep previews local and isolated; shared room time and gameplay tunables retain their existing authority and are outside this visual sweep. **P**

Choose one or two axes per batch, keep a baseline in every board, then narrow around two or three favourites. Once a look is selected, replay only the relevant motion—water shimmer, shadow movement, evening fade, rewards and label readability—through the [look skill](../../.claude/skills/look/SKILL.md). Save the owner's picks as evidence, then promote values through a reviewed source change. A selection file is not a deployment instruction. **P**
