# Entity components: a convention before a framework

> **Verdict:** Document a composition convention, no component runtime; one name-label proof.
> **Top recommendations:** 1. Approve a convention before a runtime. 2. Prove it with name labels in two real entities. 3. Keep ordering where agents can read it.
> **Status:** adopted. See [plan entity-components](../plans/entity-components.md).

_3 November 2026. Source audit at `050d6e252f5d`, with live primary engine documentation and a shipped-game developer account. Research and an approval-ready [plan](../plans/entity-components.md), not implementation authority. Counts are `wc -l` physical lines, including comments and blanks; code ranges refer to that commit. No runtime experiment or device test._

## Result: where the pain actually is

**A small composition convention is worth documenting; a component runtime is not worth building now.** The named production entities are already split and modest. There is real repeated resource-lifetime code, and some large prototype modules mix responsibilities, but neither establishes a need for automatic component scheduling, discovery or dependency resolution. Unreal migration is a small conceptual bonus, not the justification.

The most defensible first proof is **one reusable name-label behaviour used by two existing entities**, remote players and the arrival preview. It replaces duplicate change-detection/replacement/disposal logic without touching physics, networking or phase orders. Approve that bounded proof if useful; doing only the convention is also a reasonable outcome. The changed round-4 loop still awaits play according to [its tracker](../plans/round-4-notes.md); this work is not a prerequisite for that playtest or the production railway conversion.

## What the engines actually offer

**Unity GameObject/Component.** Components add behaviour to a GameObject. `Awake` initializes an instance; ordering across objects is not a dependency mechanism. `Start` runs before the first enabled update, and `Update` is frame-driven while enabled. `GetComponent<T>` performs typed lookup, returns null if absent, and does not promise which matching instance is first. `RequireComponent` installs dependencies when adding a component; it does not retroactively repair existing instances after changing the declaration. Boogle can obtain the useful part—explicit dependencies and reusable behaviour—with factory arguments and typed fields; its factory/module initialization already replaces an Awake/Start pipeline. Sources: Unity [GameObjects](https://docs.unity3d.com/6000.0/Documentation/Manual/GameObjects.html), [Awake](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.Awake.html), [Start](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.Start.html), [Update](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour.Update.html), [GetComponent](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/GameObject.GetComponent.html), [RequireComponent](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/RequireComponent.html).

**Unreal ActorComponent/SceneComponent.** ActorComponent is behaviour without a transform; SceneComponent adds spatial placement/attachment, and PrimitiveComponent adds geometry/collision. Registration connects render/physics/tick state; unregister reverses that. Tick can remain disabled when the owning Actor explicitly calls the component. Tick groups and prerequisites express ordering around physics. Thus explicit forwarding is a legitimate composition choice, not an incomplete imitation. Boogle's three.js hierarchy remains its view, not an Actor hierarchy or authoritative state store. Sources: Epic [Components](https://dev.epicgames.com/documentation/en-us/unreal-engine/components-in-unreal-engine), [Actor ticking](https://dev.epicgames.com/documentation/en-us/unreal-engine/actor-ticking-in-unreal-engine), accessed November 3 (pages display UE 5.8).

**UE6 direction versus available Verse Scene Graph.** Fresh Epic docs say UEFN Scene Graph is **Beta**, with some Experimental features. Entities contain components/child entities; components supply data and behaviour. Only one component of a class/subclass family can attach to an entity. Verse components have scene/simulation entry and exit callbacks and typed entity-relative queries. A Verse-created entity does not automatically receive the transform that editor-created entities normally have. Sources: [Getting started](https://dev.epicgames.com/documentation/en-us/fortnite/getting-started-in-scene-graph-in-fortnite), [Working with entities and components](https://dev.epicgames.com/documentation/fortnite/working-with-entities-and-components-in-unreal-editor-for-fortnite), [Custom Verse components](https://dev.epicgames.com/documentation/en-us/fortnite/creating-your-own-component-using-verse-in-unreal-editor-for-fortnite), [known issues](https://dev.epicgames.com/documentation/fortnite/scene-graph-known-issues-in-fortnite), accessed November 3.

The subclass restriction above follows the custom-component page. Epic's [working-with page](https://dev.epicgames.com/documentation/fortnite/working-with-entities-and-components-in-unreal-editor-for-fortnite) gives a conflicting example allowing point and rectangular lights together. Treat exact subclass coexistence as unresolved documentation, not a constraint to copy into Boogle; neither interpretation affects the proposed direct-reference convention.

Epic's [June UE6 roadmap](https://www.unrealengine.com/news/the-road-to-ue-6), freshly checked, describes Verse/Scene Graph and targets late-2027 Early Access, not a shipped standalone replacement. It still contains June's Actor/Blueprint coexistence language. [Our Unreal report](unreal-alignment.md#what-exists-and-what-is-only-promised) records November 3 Tokyo slides changing that direction toward removal; this research did **not** independently re-verify those slides or promise conversion tooling. Preserve that qualification instead of treating June's compatibility statement as settled. The useful alignment is small behaviours, explicit ownership and source assets; no TypeScript API here becomes portable Verse, Unreal replication or Chaos physics automatically.

**Godot nodes as composition.** Reusable scenes assemble nodes; parent entry precedes children, readiness runs children before parents, `_process` and `_physics_process` have separate clocks, and freeing a parent frees its children. Its scene-organization guide recommends self-contained scenes and dependency injection, and explicitly calls the tree relationship **aggregation**, not strict component composition. Boogle should borrow explicit lifetime/dependency ownership, not node paths or another scene graph. Sources: [Node](https://docs.godotengine.org/en/stable/classes/class_node.html), [Scene organization](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html).

**A shipped-game lesson, with limits.** Neversoft co-founder Mick West describes Tony Hawk's duplicated functionality and heavyweight inheritance, a two-year conversion while shipping annually, and a first small working component. Later, manager-mediated component access consumed over 5% CPU in that engine; direct references replaced it. He also describes bugs from inconsistent component update order. That is evidence for a bounded proof, direct references and enforced order—not a Boogle speed estimate or an instruction to reproduce his eventual architecture. Primary developer account: [Evolve Your Hierarchy](https://cowboyprogramming.com/2007/01/05/evolve-your-heirachy/) (2007 republication of the 2006 article).

The existing [engine research](engine-architecture.md#what-engine-programmers-look-for) distinguishes component composition from data-oriented ECS and says components earn their wiring cost when one class spans domains or behaviour repeats. Nystrom's [Component chapter](https://gameprogrammingpatterns.com/component.html) likewise shows explicit owner calls and shared state; this run retrieved indexed primary excerpts but the direct page fetch failed. It is supplementary, not the sole support for the recommendation.

## Designs compared against Boogle

| Design                                                    | Benefit                                                                                                                                                           | Cost / fit                                                                                                                                                                                                                                                                    |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Typed owned behaviours; explicit calls (recommend)** | Factory returns a small object; owner keeps `nameLabel`, calls it at the existing method site, disposes it, and includes its description. No scheduler or lookup. | Manual forwarding and teardown remain visible. Component timing is included in the owner's phase row. Fits both current walkers and tiny proofs.                                                                                                                              |
| **B. Runtime component list on every entity**             | `attach(entity, token, component)`, `get(token)`, deferred detach, automatic phase forwarding, component inspection/timing.                                       | Needs mutation semantics, dependency validation, failure isolation and new tests. Entity-major execution cannot put a component on either side of another kind; global scheduling would recreate kinds and complicate registry scanning. Two label sites do not pay for this. |
| **C. Components as separately spawned kinds**             | Existing walkers, timing and literal orders work unchanged; ball/ball-carry already demonstrate this.                                                             | Needs explicit lifetime linkage; extra inspector entities and teardown paths. Use only when a behaviour genuinely requires another global phase slot, not for each reusable helper.                                                                                           |

Boogle's constraints are substantive: browser allocation/GC and hidden tabs; agents reviewing text instead of editor wiring; Local/Owner/Host/Lockstep authority; headless Node runs; literal orders read by `npm run registry`; **one slot per kind per phase**. A component is not a sync kind, and an entity ID is not a network identity. A static table of components must never replace those contracts. No new per-frame arrays, lookup maps, sorting, closures or generic argument bags are needed for A; construction, text changes and requested inspector snapshots can allocate.

## Numbered recommendations for Boogle

1. **Approve a convention before a runtime.** Follow [the plan's Design](../plans/entity-components.md#design): plain typed owned objects and direct calls; leave `src/entity/walker.ts` and `entity.ts` unchanged.
2. **Prove it with name labels in two real entities.** Replace the duplicate blocks in `src/entities/remote-player/index.ts` and `src/fall/index.ts`, preserving blank-name policy, call order and visuals; see [Proof](../plans/entity-components.md#proof-two-conversions-one-behaviour).
3. **Keep ordering where agents can read it.** Retain literal `defineKind` and presence registrations; keep ball/ball-carry separate and preserve `dev/registry/scan.ts` output. No automatic component phase dispatch.
4. **Keep authority and headless boundaries explicit.** Apply [the plan's state table](../plans/entity-components.md#state-headless-and-sync) and `src/world/README.md`; Lockstep rules never import, find or invoke components. Do not make permanent net subscriptions per transient component.
5. **Expose owned state without a new inspector/profiler.** Use the owner's existing `describe().components` and `<kind> <phase>` cost; disclose that there is no independent component CPU row. Extend lint for the shared folder, not suppression allowances.
6. **Defer generic carry, buoyancy, seat and mesh/body components.** Revisit only with two genuinely matching callers or an approved large-entity split. Promote place objects within their own authority plan; retain current batching and existing helpers.
7. **Judge the proof by deleted duplication and unchanged behaviour.** Require the focused label checks and place bot; use entity-core tests within the owner's exception and `npm run sim -- replay` whenever a subsequent component touches player/ball physics. Do not claim Unreal portability or measured performance improvement.

## Limits and disposition

**Owner decision needed for implementation; research complete.** No engine was installed and no conversion was executed. Line counts and call paths were checked, not frame time, heap retention or subjective feel. The preview currently has no label disposal in its entity teardown; the proof would close that ownership gap, but this audit did not measure a leak. Full place promotion, UE6 migration guarantees and device performance remain unverified. The [plan](../plans/entity-components.md) names the bounded implementation steps and stop conditions.

Documentation validation: `npm run check` passed; local file links resolve. No browser/bot/replay run was required or performed for this docs-only change. Those are acceptance work for an approved implementation, not evidence claimed here.
