## Findings

### P2 — Bound and stream capability image reads

**File:** `server/src/reviews.ts:205–214` (especially line 214).

Every image GET allocates the entire image using `fs.readFile`, then hands that Buffer to `res.send`. This route has no rate limiter or concurrency bound; the report limiter only covers POST `/report`. A holder of one card URL can repeatedly request a 4 MiB image without the report token. Concurrent requests and slow readers retain independent full-file buffers; 128 outstanding maximum-size responses alone represent 512 MiB, before the game host or Express overhead. The deployed machine has 512 MiB and runs rooms in the same process (`server/fly.toml:20,41–43`). This exposes room availability and unsaved progress to memory exhaustion from the new media endpoint. Browser caching does not constrain a direct HTTP caller.

**Verification:** Read the complete route registration, global middleware, Express send path and deployment memory configuration. The unbounded full-file allocation is verified in code; a production OOM/slow-client load test was deliberately not attempted. Stream with backpressure and bound request/concurrent read load; a storage byte cap does not bound response memory.

### P2 — Reject non-images with valid magic bytes

**File:** `server/src/reviews.ts:89–96`.

`media()` accepts a file based only on its first 3, 8 or 12 bytes. An authenticated upload containing only the eight-byte PNG signature returns 201, permanently consumes a card slot, and is served as `image/png`, although it has no image data and cannot decode. A truncated capture therefore produces an apparently successful, hash-verified comparison whose evidence cannot be viewed. JPEG and WebP have the same structural problem. There is also no decoded-dimension bound for otherwise compressed images.

**Verification:** Invoked the production upload and image handlers against an isolated temporary directory. Both images were exactly `89 50 4e 47 0d 0a 1a 0a`; upload returned 201 and GET returned those eight bytes. `PNG.sync.read` rejected them. This proves invalid image acceptance, not an XSS exploit: fixed MIME and `nosniff` are present. Validate image structure/decodability and reasonable dimensions before retaining it, while preserving the compressed byte limits.

## Other reviewed behavior

- **Authentication and paths:** POST `/reviews` checks the timing-safe bearer-token comparison before the 12 MiB JSON parser. Missing configured token returns 404; missing/wrong authorization with a configured token returns 401. Authenticated GET `/reviews` is the only listing. UUIDv4 validation and fixed side/file names prevent input paths from escaping storage; a traversal-shaped ID returned 404 in the handler probe. Capability possession intentionally authorizes card reads and submissions. Unknown IDs cannot create cards or receipt directories.
- **Limits and anonymous consumption:** Two images are each capped at 4 MiB after canonical base64 validation. The global creation lock enforces 50 cards; card 51 returned 507. Only token holders can consume card capacity. Each card allows 100 unique receipts, including anonymous capability holders' receipts; receipt 101 returned 507. There is no reserved owner slot or automatic expiry. One capability holder can exhaust that card's feedback capacity, subject to the shared POST `/report` per-IP bucket (default 12/minute). That is a consequence of the explicitly approved capability authority, not an authentication bypass. Recovery requires manual archival/removal. Anonymous callers without an ID cannot practically enumerate UUIDv4 cards.
- **Aggregate disk/memory:** Maximum retained image bytes are 400 MiB, plus metadata and up to 5,000 receipts containing copies of their cards. Receipts do not use the legacy 5 MiB/day report budget. The authenticated listing materializes all receipts before serializing them, and uploads parse/decode before waiting on the creation lock, without a separate upload rate limit. Those trusted-token operations can be expensive. No free-space reserve isolates room saves; reviews share `/data` with snapshots, reports and playdata. Failed/crashed upload temporary directories are outside the 50-card count and need manual cleanup, as documented. Actual volume headroom and maximum-capacity listing memory were not measured.
- **Receipt races/deduplication:** Ten concurrent identical submissions yielded one new receipt, nine duplicates and one timestamp. Reusing its ID with a different verdict returned 409. A matching duplicate still returned 200 after reaching 100 receipts. Validation constructs canonical submission fields before comparison. The per-review lock is shared with the store but uses a namespace that cannot collide with valid room IDs. The deployment assumes one service process; the lock is not cross-process.
- **Acknowledgement durability:** Files are exclusively created and synced, then atomically renamed; directory syncs precede success. A receipt retry after a lost acknowledgement reuses the stored record and repeats directory sync. Exceptions propagate through Express 5's async error handling, so a failed write does not execute the success response. This was verified by code inspection; no power-loss or fsync-failure injection was performed.
- **CORS:** The existing global CORS middleware covers the new routes and permits Authorization preflight. Configured origins control browser response access, not HTTP authorization or blind `text/plain` report submission. Wildcard remains the existing default. Production origin configuration was not queried.
- **XSS/capability leakage:** Card strings and JSON details render using `textContent`; notes use textarea values. Retained image URLs are generated server-side from the UUID and fixed side. CLI reader credentials stay in Authorization headers; the generated link contains no report token. The server override is development-only loopback HTTP. No automatic agent execution or shell evaluation is introduced. A shared review URL intentionally discloses its card, including launcher/context metadata; callers must avoid placing secrets in that metadata.
- **Client correctness:** Submission snapshots and ID checks prevent an older response marking an edited draft received. The legacy sender retains its beacon boolean, payload and deduplication behavior. The legacy verdict-reader path is unchanged unless `--reviews` is supplied. No verified client/script finding was identified.
- **Legacy reports and rooms:** The only legacy dispatch change selects single-object `kind: 'review-v1'`; existing kinds, batch handling, 8 KiB body limit, cleaning, 204 success, daily cap and authenticated log reads remain unchanged. All 11 existing `server/test/server.test.ts` cases passed, including legacy report validation, playtest shape, limits, CORS, snapshots and upgrade handling. The diff makes no room-state/save-format changes. Shared disk and process resources remain the availability coupling described above.

## Deployment

The main push path filter and automerge dispatch both include `server/`, so this diff triggers the existing Fly deployment. `.github/workflows/deploy-server.yml` tests the server, builds from the repository root with `server/Dockerfile`, deploys one machine using `--ha=false`, and checks `/healthz`. It requires the existing `FLY_API_TOKEN`; absent that secret the deploy is skipped. This review performed no deployment or external network access.

`server/Dockerfile` already copies `server/src`, so `reviews.ts` is included. Its `protos/review-types.ts` dependency is an `import type`, stripped by Node 24; it needs no additional runtime COPY. Existing `/data` is mounted from `boogle_data` and made writable for the node user. The service automatically creates `/data/reviews` and receipt subdirectories; no new volume or manually created subdirectory is required. **A configured `REPORT_TOKEN` is required to create cards and retrieve receipts**; deployments that previously left this optional setting unset must now configure it. The site must retain its correct `VITE_BOOGLE_SERVER` and allowed origin. No new environment variable is introduced. Verify free disk space on the existing documented 1 GiB volume before enabling uploads.
