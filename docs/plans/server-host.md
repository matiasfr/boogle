# Plan: the server hosts the main room

> **Status: shelved (2026-10-30).** For rapid iteration peer hosting is enough: `npm run load` shows an 8-player room
> costs the host about 1.7 Mbit/s up and 2% of a main thread, and a server would make every rules change a coupled
> server + client deploy. Pick this plan up when one of these holds:
> - public playtests with strangers (cheating, trust in saves, a host on someone else's phone);
> - world progress while nobody is online (PLAN.md Phase 5, "growth from timestamps");
> - rooms past the 8-player cap;
> - telemetry (`connect` reports) shows failed joins, TURN-only links or host migrations regularly hurting sessions.
>
> Until then, choosing the host on purpose (prefer a visible desktop tab, hand over before hiding) covers most of what
> this plan fixes. Steps 2 (land as JSON) and 3 (sync re-pin and shared-state hashes) help either way and can ship on
> their own. Re-check the code references below before starting: they were read on 2026-10-30.
>
> Steps 1-10 below are separate PRs, each leaving `main` green. Production behavior only changes at step 10 (one Fly
> env var); until then the server answers "this room is peer-hosted" and every tab plays exactly as today.

## Open questions for the user (answer before the step named)

1. **DESIGN.md "PeerJS only" (step 1).** This plan bends it: the main room is hosted by our server over WebSocket,
   PeerJS stays as the fallback and for every other room. Step 1 rewrites that section and the "Clear authority" rows
   (wording below). OK to change the principle?
2. **Fallback signaling when Fly is down (step 9).** Our PeerJS signaling runs in the same Fly process, so when the
   server is unreachable, a peer fallback needs another signaling server. Recommended: PeerJS's public cloud
   (`0.peerjs.com`, already what dev builds use without `VITE_BOOGLE_SERVER`), STUN only (no TURN: `/ice` is on Fly
   too), under a separate room namespace `<room>-fb`. Alternative: no fallback at all, tabs go solo until the server is
   back. Which?
3. **How the server checks planting spots (step 2).** `mush.plant` validate needs `env.canPlantAt`, a render-side check
   (dry land, no rock/tree/wall overhead). Recommended: bake it into a mask in `src/world/home-land.json`, generated by
   the `world-inputs` scenario (`UPDATE_FIXTURE=1`). Cost: moving a POI, rock or tree fails `world-inputs` in CI until
   the author regenerates the file (trees already work this way). Alternative: the server checks only that the cell is
   on the grid and trusts the planting tab's own check (`plantOk` already runs before every `mush.plant` and seed throw).
4. **Old tabs after the flip (step 10).** Node has no WebRTC, so a tab from before step 9 cannot join a server-hosted
   room (it can neither claim nor reach the PeerJS host id) until it reloads (`updates.js` reloads hidden tabs at once
   and shows the reload toast on visible ones). The plan waits at least 24 h between step 9 going live and step 10.
   A WebRTC bridge for old tabs is out of scope. OK?
5. **Deploys disconnect everyone briefly.** Today a server deploy only blocks new joins (P2P links survive). With the
   server as host, each deploy (now also triggered by `src/world/**` and `src/sim/**` changes) freezes the shared world
   and remote avatars for the restart (typically 5-20 s); nothing is lost on a graceful restart. A crash loses at most
   `SERVER_SAVE_MS` (2 s) of world progress, so an item taken in that window can exist twice (ground and hotbar). OK?
6. **`primary_region` (step 10).** `server/fly.toml` says `iad` (Virginia). Where do most players live? A volume is
   region-bound, so moving means a new volume and copying `/data/*.json` (checklist in step 10). Left as a TODO.
7. **Prototype flags on the main room.** Today the host's URL flags (`?proto=...`) set the room's `proto` state. On the
   server host they come from a server env var `PROTO_FLAGS` (default: none, so all on, as for a URL without flags).
   OK?
8. **`?p2p` in a server-hosted room.** `?p2p` (skip the server, peer via our signaling) cannot join a room the server
   hosts (the server holds the host id). Proposed: `?p2p` is for other rooms (`?room=dev&p2p`); in the main room it logs
   a warning and joins the server anyway. OK?

## Risks

- **Hotspots touched:** `src/netplay/net.js` (room picking, lead helper: about 15 lines), `src/world/sync.js` (four
  additive changes, each tested), `src/net/peer-room.js` (imports ids, adds three members), `DESIGN.md`, `PLAN.md`
  (one line), `AGENTS.md` (one line), `package.json` (`test:net`), `.github/workflows/ci.yml` and
  `deploy-server.yml`. `src/world/rules/` is not edited (except its README).
- **AGENTS.md "Don't":** "Save or serve unverified state": the server never uploads or serves a state that failed to
  load (it adopts a handed-off snapshot only after a scratch load with zero `loadErrors` and no `newerSave`), and the
  existing client guards in `sync.js` stay untouched. "Effects in apply": the server installs only rules, never
  adapters, so it runs exactly what `apply` does. "Wall clock in apply": the server's clock enters only through
  `updateWorld(dt)`, as in a tab.
- **Mixed builds** (details in Design, "Mixed builds"): all wire changes are additive (a new WebSocket endpoint and
  protocol, new HTTP routes, new optional room members, no change to any existing message, presence key or state). The
  real new risk is the server running different rules than some tabs; step 3 makes hash checks tolerate states only
  one side has, and `deploy-server.yml` starts deploying on rules changes.
- **Deploy pipeline:** the server image now needs `src/world/`, `src/sim/` and two `src/net/` modules, so the Docker
  build context moves to the repo root (step 7). A wrong `.dockerignore` or path breaks the server deploy; step 7 adds
  a `docker build` to CI so that fails on the PR, not on `main`.
- **Fly shared CPU:** `shared-cpu-1x` has a low sustained CPU baseline. The expected load (10 ticks/s plus about 1,100
  relayed presence packets/s with 8 players) is small, but step 8's load check prints the server's CPU share; if it is
  near the baseline, move to `shared-cpu-2x`.
- **Test time:** `npm run test:net` gains `dev/peer-test/ws-run.mjs` (about 60-90 s), so `check:full` takes longer.
- **Performance (client):** no meshes, lights or tick work are added; `npm run perf` is not needed. Joining costs one
  extra WebSocket round trip before PeerJS in rooms the server does not host.

## Goal

The Fly server becomes the always-on host of the main room (`beach`): it runs the lockstep world headless (stamps
edits, runs the clock, hashes, snapshots, late joins, saves to its own disk) and relays presence and messages over
WebSocket. Browsers stop racing for the PeerJS host id, TURN/NAT failures and host migrations go away for the main
room, and the island keeps ticking with nobody online. PeerJS hosting stays as the fallback and for every other room.

Serves DESIGN.md 8 **"Designed for drop-in, drop-out"** (no host to lose, no migration hiccup, joining never depends
on another player's NAT) and 9 **"Leave something for the next visitor"** (ticks run while everyone is away, which
docs/game-design/multiplayer.md 8.6 lists as unmet). Bends **"PeerJS only"** (open question 1).

## Design

### Pieces and their sync kinds

Nothing changes kind. What changes is who plays the host's part.

| State | Kind | Main room after this plan | Other rooms, `?p2p`, local dev, fallback |
|---|---|---|---|
| Lockstep world (mushrooms, gifts, proto, stubs) | Lockstep | the server's `createSync()` is host; every tab is a client | a browser hosts (unchanged) |
| Avatars, ball, held items, flops, build id | Owner | each tab, relayed by the server | relayed by the host browser (unchanged) |
| The Boogler (`addHostField('g')`) | Host | the **lead** tab, picked by the server (below) | the host browser (lead = host) |
| Honk, ping, any `room.send` | Message | relayed by the server | relayed by the host browser |
| Snapshot on disk | Lockstep save | written by the server to `DATA_DIR` every 2 s and on shutdown | PUT by the host browser (unchanged) |

**Authority.** The server is the world authority for the rooms in its `SERVER_ROOMS` env var (only `beach` in
production). Physics stays Owner: the server never simulates bodies, it only relays presence. Host-kind fields need a
browser (The Boogler walks on the render-side terrain), so the server names one connected tab the **lead**; on
peer-hosted rooms the lead is simply the host.

**Cosmetic:** nothing new. The connection label (`dom.netEl.dataset.state`) keeps its three states.

### The room interface grows three optional members (additive)

`src/net/README.md` gets, for both `peer-room.js` and the new `ws-room.js`:

```js
room.transport          // 'peer' | 'server' | 'fallback' (fallback: peer-hosted on the public signaling server)
room.isLead()           // true when this tab publishes Host-kind fields (addHostField). peer-room: === isHost()
room.onLeadChange(h)    // h(isLead: boolean). returns unsubscribe. peer-room: same events as onHostChange
```

`isHost()` keeps its meaning for `sync.js`: true only when this tab is the lockstep host, so on a server-hosted room
it is always false. `net.js` and `boogler.js` switch their Host-field checks from `isHost()` to a new
`isLead()` helper in `net.js`; nothing else above `net.js` changes.

### Ids (new pure module `src/net/ids.js`)

Moved out of `peer-room.js` so `ws-room.js`, the room picker and the server share them:

```js
export const SELF_ID          // 10 base36 chars, per page load (moved from peer-room.js, same code)
export const SERVER_ID = 'server' // `from` of every message the server host sends; no tab may use it as selfId
export const okId = (s) => typeof s === 'string' && /^[a-z0-9]{1,32}$/.test(s)
export const safeRoom = (s) => ...   // moved from peer-room.js, same code
export const peerHostId = (roomId) => `boogle-${safeRoom(roomId)}-host`
```

No browser globals besides `crypto.getRandomValues` (Node 22 has it), so the server imports it.

### Wire: client <-> server (new, `src/net/ws-wire.js`)

WebSocket at `GET /room/<roomId>?self=<selfId>&b=<build>` with subprotocol `boogle.1` (JSON text frames). The shapes
copy `peer-room.js`'s so both rooms share their handling:

```
client -> server   { t:'p', s, d }        my full presence d, sequence s (latest wins)
                   { t:'m', d }           room.send payload; the server relays it with from = my selfId
                   { t:'hb', at }         heartbeat every HEARTBEAT_MS (1000); the server echoes it (RTT for linkStats)
                   { t:'bye' }            leaving
server -> client   { t:'welcome', v:1, boot, lead, max }   first message: server boot id, the lead's id (or null), cap
                   { t:'list', peers:[{ id, s, d }], last } everyone else, chunked at 12,000 chars, after welcome
                   { t:'p', id, s, d }    a peer's presence
                   { t:'left', id, s }    a peer is gone
                   { t:'m', from, d }     a relayed message; from = SERVER_ID for the server's own lockstep messages
                   { t:'hb', at }         echo
                   { t:'lead', id }       the lead changed (id may be null)
                   { t:'bye', why }       graceful shutdown (why: 'restart'); the socket then closes with 1012
refusals (then close)  { t:'peer' } 4000   this room is not server-hosted: use PeerJS
                       { t:'full', max } 4008  the room has max players (same shape and meaning as peer-room's)
                       { t:'bad' } 4400    bad room id, bad or reserved selfId, wrong protocol
```

`ws-wire.js` exports `WS_PROTOCOL = 'boogle.1'`, `CLOSE = { NOT_HOSTED: 4000, FULL: 4008, REPLACED: 4009, BAD: 4400,
RESTART: 1012 }`, `MAX_MSG = 16000`, `encode(msg)` (JSON.stringify), `decode(data)` (parse; returns an object with a
string `t`, else null), and `roomUrl(base, roomId, selfId, build)` (http->ws, https->wss). Pure, imported by the server.

Server-side message rules: a client's `m` whose `d.t` is `w:edit` or `w:need` goes only to the server's sync (no other
tab needs it); one whose `d.t` is `w:edits`, `w:c`, `w:hash` or `w:snap` is dropped (only the host sends those);
anything else is relayed to every other client and also handed to the sync (which ignores non-`w:` types). The
server's own `w:snap` chunks go only to the client named in `to`. Messages over `MAX_MSG` chars are dropped; per
client, at most 50 messages/s (burst 100) and 40 presence packets/s are accepted, the rest dropped and counted.

### The server host (`server/src/host/`)

| File | Exports | Does |
|---|---|---|
| `land.js` | `loadHomeLand(file?)` -> `{ land: { n, layout }, canPlantAt(i, j) }`, `decodeRuns(runs, size)` | Reads `src/world/home-land.json` (fs, not import), decodes the plant mask |
| `world-host.js` | `createWorldHost({ roomId, store, cfg, log })` | One `createSync({ env: { canPlantAt } })` with `installRules(sync, land)`, attached to a server-side room adapter; drives `updateWorld` every 50 ms from `performance.now()` deltas; `status()`, `validate(snap)`, `adopt(snap)`, `close({ save })` |
| `hosted-room.js` | `createHostedRoom({ roomId, cfg, store, log })` | The clients of one room: join, cap, presence relay, message relay, heartbeats, lead, and the sync adapter |
| `rooms.js` | `createRoomHost(cfg, store)` | The hosted rooms (`cfg.serverRooms`), the held PeerJS ids, `upgrade(req, socket, head)`, `status(id)`, `handoff(id, doc)`, `close(opts)` |
| `upgrade.js` | `routeUpgrades(server, { peerWss, roomHost, cfg })` | One `upgrade` listener: `/peerjs/peerjs` to PeerJS (guarded), `/room/:id` to the room host, anything else 404 |

**The sync on the server.** `world-host.js` calls `sync.attachWorld(adapter, { roomId, serverUrl: '', storage,
now: Date.now, saveMs: cfg.serverSaveMs })` where:

- `adapter = { selfId: SERVER_ID, isHost: () => true, send, onMessage, onConnection, onHostChange }`. `send(msg)`
  encodes `{ t:'m', from: SERVER_ID, d: msg }` once and writes it to every ready client (only to `msg.to` for
  `w:snap`). `onConnection(h)` calls `h(true)` once; `onHostChange` never fires.
- `storage` is synchronous like localStorage: `getItem()` reads `DATA_DIR/<room>.json` with `fs.readFileSync` and
  returns `JSON.stringify(doc.data)` (or null); `setItem(_key, json)` queues an atomic write of
  `{ tick, writerId: SERVER_ID, data, updatedAt }` through the store (the same file and shape `GET /rooms/:id/snapshot`
  already serves). No 250 KB limit: the server's own saves never go through PUT.
- With `serverUrl: ''`, `becomeHost` loads only the disk copy; with `ready` it starts ticking, and the world keeps
  ticking with no clients.
- `env.canPlantAt` comes from `land.js`. A server test (step 7) submits every op's `edits` generator through the world
  host and requires each op to be accepted at least once, so a future validate that needs a new `env` fact fails CI
  until the server provides it (the rules README's env table gains a "Server" column).
- Prototype flags: removed 2026-10-31; `proto` is a stub state the server leaves alone.

**Joining (`hosted-room.js`).** On a `/room/<id>` upgrade: reject with `bad` unless the id is in `SERVER_ROOMS`
(then `peer`), `self` passes `okId` and is not `SERVER_ID`, and the protocol is `boogle.1`; check `Origin` against
`ALLOWED_ORIGINS` (403 unless `*`); at most 20 upgrades per minute per IP (`fly-client-ip` header, else the socket
address). The cap counts ready clients plus ids that left less than `RECONNECT_GRACE_MS` (1500) ago; a known id (a
reconnect) is always admitted, a new one gets `full` once `MAX_PLAYERS` (8, the same as `MAX_PEERS` in
`peer-room.js`; the server is not a player) are in. The same `self` connecting again replaces the old socket (closed
with 4009, no `left`). Then: `welcome`, `list`, and a synthetic `{ t:'w:need' }` from that id into the sync, so a tab
that reconnects after a server restart gets a snapshot at once (`serveSnapshot` rate-limits per id, so a fresh joiner
that also asks gets one).

**Presence relay.** Each client record keeps its latest `{ s, d }`; a `p` with `s` not above the last is dropped.
Relaying goes through `audience(from)` (today: every other ready client) and a per-recipient latest-wins sender keyed
by source id, held back while `ws.bufferedAmount > 64 KB` and spaced 20 ms per key (the same rules as peer-room's
`makeSender`). The packet is encoded once per relay, not once per recipient.

**Leaving.** A closed socket announces `left` after `RECONNECT_GRACE_MS` unless the id is back. A client silent for
`DEAD_MS` (5000) is closed. The housekeeping interval (1 s) sends `hb`, drops the dead and re-checks the lead.

**Lead.** The oldest ready client whose presence has `v === 1` (visible), else the oldest ready client. It changes when
the lead leaves, or when it has had `v === 0` for `LEAD_HIDDEN_MS` (5000) while a visible client exists. Every change
is broadcast as `{ t:'lead', id }` and is in `welcome`.

**Shutdown.** `SIGTERM`/`SIGINT` (already handled in `index.js`, which calls `svc.close()`): `svc.close()` first runs
`roomHost.close({ save: true })`, which sends `bye`, calls `sync.saveNow()`, awaits the store's pending write and closes
the sockets with 1012.

### Who may host: no split brain

- **While the server hosts a room it holds that room's PeerJS host id.** PeerJS signaling runs in the same process.
  `ExpressPeerServer` gets `createWebSocketServer: (o) => (peerWss = new WebSocketServer({ noServer: true, path:
  o.path }))`, and `upgrade.js` routes `/peerjs/peerjs` upgrades itself: if the query `id` is
  `peerHostId(room)` for a hosted room, it completes the upgrade, sends `{"type":"ID-TAKEN","payload":{"msg":"ID is
  taken"}}` and closes. That is what PeerJS sends for a taken id, so a tab trying to claim it becomes a client, and its
  offer to that id expires (`peer-unavailable`). (`noServer` routing is required anyway: a `ws` server attached with
  `server` aborts every upgrade outside its own path with a 400.)
- The guard exists from before `listen()` and hosting is fixed per process (set by env, changed by a restart), so no
  browser can hold the id while the server hosts, and the server never has to evict one.
- A browser that was peer-hosting when the server came up keeps its existing WebRTC links (they do not need
  signaling) but can never re-register the id. New builds move to the server (transition T11); old builds keep a
  separate island until they reload, and **cannot overwrite the server's save**: `PUT /rooms/:id/snapshot` for a hosted
  room answers `409 { error: 'server-hosted', tick }` and writes nothing.
- The public fallback signaling (open question 2) has no guard, but only tabs that cannot reach our server use it, and
  they move back as soon as they can (T9).

### Client: `ws-room.js` and the room picker `room.js`

- `src/net/peer-table.js`: `createPeerTable(selfId)` -> `{ setSelf(presence), upsert(id, presence, seq), drop(id, seq),
  has(id), list(), onChange(h), keepUntil(ids, ms) }`. The peer table and change batching from `peer-room.js`
  (`note`/`flush`/`list`, seq tombstones, 8 ms batches, self first, frozen entries), written fresh. `peer-room.js` is
  **not** refactored onto it in this plan (lower risk); a follow-up may.
- `src/net/ws-room.js`: `createWsRoom({ roomId, server, build, debug, openTimeoutMs = 5000 })` implements the room
  interface plus `transport: 'server'`, `isLead()`, `onLeadChange(h)`, and two members only the picker uses:
  `onRedirect(h)` (h('peer') when the server answers `peer` on a reconnect) and `downMs()` (ms since the link
  dropped, 0 while up). Resolves after `welcome` and the last `list` chunk. Rejects with `err('room_full')` + `max`
  (same as peer-room, so `net.full` works), `err('peer_hosted')`, `err('unreachable')`, or
  `err('browser-incompatible')` (no `WebSocket`). After that it reconnects by itself (250, 500, 1000, 2000, then 3000 ms,
  each +-30% jitter; 500-1500 ms after a `bye`), reports `onConnection(false/true)`, re-pushes its presence with a
  bumped seq, flushes an outbox (200 sends), and drops peers the server has not listed within `GRACE_MS` (9000) of
  reconnecting. Heartbeat 1 s, dead after 5 s. `linkStats()` returns
  `[{ peer: SERVER_ID, relay: false, local: 'ws', remote: 'ws', rttMs }]` from the heartbeat echo.
- `src/net/room.js`: `createRoom({ roomId, server, peerOptions, fallbackSignal, build, debug, timing })`, what
  `net.js` calls. With `server` null it returns `createPeerRoom({ roomId, debug, ...(await peerOptions()) })`
  unchanged. Otherwise it returns a **switching room**: one object with the room interface whose `selfId` never
  changes, wrapping the current transport (`ws`, `peer` = `createPeerRoom` on our signaling, `fallback` =
  `createPeerRoom({ roomId: roomId + '-fb', signal: fallbackSignal })`, no `signal` meaning the public cloud). It keeps
  its own `mine` presence and a `peer-table` fed from the inner room's `onPeers`, forwards messages, connection, host
  and lead events, buffers `send` while switching, and on a switch keeps the old remotes for `GRACE_MS` unless the new
  transport lists them (no avatar pop). `timing` (tests only) overrides `wsGraceMs` (30000), `probeMs` (10000 in
  `fallback`, 30000 in `peer`, each +-30%), `handoffMs` (1500) and `firstWsMs` (6000).
- `reachable()`: `fetch(server + '/healthz', { mode: 'no-cors', cache: 'no-store', signal: timeout 2000 })` resolves
  for any HTTP answer (CORS or not), rejects on a network error. `hostStatus()`: `GET /rooms/<id>/host` (CORS) ->
  `{ mode: 'server' | 'peer', ... }`, or `{ mode: 'peer' }` on a 404 (an older server, or the scenarios' bare PeerServer).

### Transitions (every one)

`ws`, `peer` and `fallback` are the switching room's transports. "Move" means: if this tab is the host of the
transport it leaves, emit `onHostChange(false)` (its sync saves through the handoff route, below), wait `handoffMs`,
then close the old transport and open the new one; a non-host waits `handoffMs` + 0-1000 ms first. `onConnection` is
false while moving.

| # | When | What happens |
|---|---|---|
| T1 | Join, the server hosts the room | `ws`. The sync becomes a client and asks for a snapshot (it also gets the synthetic one). |
| T2 | Join, the server answers `peer` (another room, hosting off, before step 10) | `peer` on our signaling: today's path. |
| T3 | Join, no `welcome` within `firstWsMs`, `reachable()` fails | `fallback`. The first tab there claims `boogle-<room>_2dfb-host`; as a new host without state it loads the newest by tick of its localStorage copy and the server (unreachable, so local). |
| T4 | Join, ws fails but the server is reachable (no `/room` endpoint, or `hostStatus()` says `peer`) | `peer`. If `hostStatus()` says `server`, retry ws until `wsGraceMs`, then `fallback`. |
| T5 | Join, `full` | `createRoom` rejects `room_full`; `net.js` shows solo and retries (as with peer-room's cap). |
| T6 | `ws` drops, server back within `wsGraceMs` (deploy, restart) | Same `ws`, reconnected. Graceful restart: the server saved its last tick, so the world resumes where it stopped. Crash: the server resumes from its last 2 s save; the synthetic `w:need` snapshot rolls every tab back to it. Held edits older than 5 s are dropped (existing rule). |
| T7 | `ws` down longer than `wsGraceMs`, server unreachable | Move to `fallback`. The first tab to claim the host id keeps its live world (`becomeHost` migration path: ready and verified), so play continues from the server's last state; the rest join it and re-pin to it at once (step 3). |
| T8 | `ws` reconnect answered with `peer` (hosting switched off) | Move to `peer` at once; the first claimant keeps its live world (as T7), and its 30 s saves PUT to the server again. |
| T9 | In `fallback`, `hostStatus()` says `server` | Move to `ws`. The fallback host's demotion POSTs its world to `/rooms/<id>/handoff`; the server adopts it if newer (below) and re-serves every connected tab a snapshot. Clients that arrive first get the server's older world, then the adopted one. |
| T10 | In `fallback`, `hostStatus()` says `peer` | Move to `peer`. The handoff POST is stored like a PUT (if newer), so whoever claims the host id there loads it (newest by tick). |
| T11 | In `peer`, `hostStatus()` says `server` (step 10's flip, or hosting switched back on) | Move to `ws` with a handoff, as T9. Meanwhile the peer host's signaling reconnects get `ID-TAKEN`; its P2P links keep working until it moves. |
| T12 | In `peer` or `fallback`, server unreachable | Stay: the P2P links do not need it. Only a peer room that fails (rejects or reports a fatal error) makes the picker try ws, then `fallback`. |
| T13 | The lead leaves or stays hidden 5 s | The server picks a new lead and broadcasts `lead`; `net.js` sends presence at once so the new lead publishes `g` (as on a host change today). |
| T14 | A tab from before step 9 opens a server-hosted room | Its claim gets `ID-TAKEN`, its connect expires: it retries as "connecting" until `updates.js` reloads it (hidden at once, visible on the toast or when hidden). |
| T15 | Old and new tabs in `beach` before step 10 | Every tab ends on `peer` (T2), the same PeerJS room as today. Mixed rooms work as now. |
| T16 | Server returns while some tabs are still reconnecting ws and others are in `fallback` | The first group lands on the server (T6); the fallback group follows within `probeMs` (T9). |
| T17 | One tab cannot reach the server while others can | It ends alone in `fallback` (T3). Its handoffs fail, so it never overwrites anything; it rejoins when it can reach the server. |

**Adopting a handoff (`rooms.js` `handoff(id, doc)`, the newest-by-tick rule).** For a hosted room: validate the body
like PUT (`{ tick, writerId, data }`, up to 1 MB); load `data` into a scratch `createSync()` with the same rules and
land, and require `loadSnapshot` true, `worldStatus().loadErrors === 0`, `!newerSave` and `data.seed` equal to the
hosted seed (else 400); require `data.tick > ` the hosted tick and the hosting process to be younger than
`ADOPT_WINDOW_MS` (600000) (else `409 { adopted: false, tick }`). Then `sync.adoptSnapshot(data)`, a synthetic
`w:need` for every connected client, an immediate disk save, and `200 { adopted: true, tick }`. For a room the server
does not host, handoff is PUT (stored if not older). Same per-IP rate limit as PUT.

### Mixed builds

- **Additive only.** New: the `/room/:id` WebSocket and its protocol `boogle.1`, `GET /rooms/:id/host`,
  `POST /rooms/:id/handoff`, the 409 `server-hosted` answer to PUT (old builds ignore PUT answers), the optional room
  members. Unchanged: every `w:*` message, presence key, state, op and the PUT/GET shapes. The registry check (`npm run
  registry`) does not scan `src/net/`, so the transport types need no entries.
- **Old tab and new tab both in `beach`:** before step 10 they meet on PeerJS (T15). After step 10 old tabs cannot
  join until they reload (T14, open question 4), and an old peer host left running cannot write the save (409).
- **The server is a tab on some build.** After step 7, `deploy-server.yml` also runs on `src/world/**`,
  `src/sim/**`, `src/net/ids.js` and `src/net/ws-wire.js`, so a rules change reaches the server minutes after the
  Pages deploy. In between, and for tabs left open on older builds:
  - an op the server does not know is rejected at stamping (the edit is lost, as with an old host today);
  - a state only one side has used to fail every hash check and loop on resyncs; after step 3 a client compares only
    the state keys both sides hash, minus any it skipped as saved by a newer build;
  - a state whose `version` the server is behind on: the server skips it and stops persisting (`newerSave`), which
    `GET /rooms/:id/host` reports as `noSave: true`. Fix by deploying the server; a rollback deploy needs the same care.

### Land on the server

`src/world/game-world.js` cannot run in Node (`land.layout` is filled from `src/render/props.js`, and `src/island/`
uses `import.meta.glob`). The rules need only `land = { n, layout }` (the README says so), and Node tests already run
them on the layout pinned in `test/fixtures/world-inputs.json`. Step 2 moves `n` and `layout` to
`src/world/home-land.json` and adds `plant`, a run-length mask of `canPlantAt(i, j)` over `g = i * n + j` (runs
alternate, starting with unplantable), all written and checked by `dev/scenarios/world-inputs.mjs` in the running
game. The fixture keeps `states` and `ops`. `test/helpers/land.mjs` (and so the replay test and `npm run registry`)
reads the new file.

### Fly

- One machine (state in memory), `auto_stop_machines = "off"`, `min_machines_running = 1`, kept.
- `[[vm]] memory = "512mb"` (from 256): Node 22 with Express, `peer` and `ws` idles around 70-90 MB RSS; serving
  snapshots builds JSON strings of up to ~1 MB per chunked serve, and eight joiners at once (after a deploy, every tab
  reconnects together) is several of those plus 64 KB socket buffers each. 256 MB leaves too little headroom before the
  OOM killer; 512 MB doubles it for about $1.50 a month. `NODE_OPTIONS = "--max-old-space-size=320"` makes V8 collect
  well before the machine's limit.
- `kill_signal = "SIGTERM"`, `kill_timeout = 10` (the final save takes well under a second).
- `[env] SERVER_ROOMS = "beach"` turns hosting on (step 10); unset or empty everywhere else (local, tests, CI).
- `primary_region = "iad"  # TODO(user): move near the players` (open question 6).
- Deploy from the repo root: `flyctl deploy . --config server/fly.toml --dockerfile server/Dockerfile`.

### Seams left for later (not built)

- **Interest management:** `hosted-room.js` relays presence only through `audience(from)`, which returns every other
  ready client today; filtering by the `p` field of each client's latest presence goes there.
- **Binary / delta presence:** `ws-wire.js` owns `encode`/`decode` and the subprotocol; a `boogle.2` codec is offered
  by new clients and picked by the server's `handleProtocols`, while `boogle.1` keeps working. The server already keeps
  each client's latest full presence, so deltas can be computed per recipient.
- **More rooms on the server:** `SERVER_ROOMS` is a list; each hosted room is its own `createSync()`.
