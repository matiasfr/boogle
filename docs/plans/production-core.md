`initial supply + accepted production = unharvested + loose + carried + station stock + build allocation + embodied/used + cargo + rack`

### Save, restart and mixed-build contract

Recommend **process-crash survival for every published accepted material edit**, as well as graceful restart. Today's two-second asynchronous snapshots cannot prove that promise. Merely calling `saveNow()` in `onApplied` does not close the window, and the persisted snapshot currently does not include the future stamped queue.

Before publishing new production edits, extend server persistence with a versioned, per-room recovery envelope holding a verified checkpoint, its tick/hash/namespace/catalog revision, ordered stamped edits after it (including not-yet-applied edits), and sequence watermark. Serialize writes through one bounded queue; durably complete the recovery write before releasing that batch's accepted stamps/clock to clients. Recovery loads the checkpoint, replays only its tail in stored order, then resumes the clock. Compaction may discard the tail only after its replacement checkpoint is durable. This is a bounded extension to existing storage/sync, not a second railway network or a general event-sourcing service. Do not persist independently sampled railway and carry documents that can tear across one transfer.

The implementation review must settle the exact barrier position in `stamp`/`flush`/tick scheduling and storage failure propagation before coding presentation. No promise of durability from a swallowed write error. On storage failure/backpressure, pause new production mutations and surface a recoverable connection/storage state; retain the last good save. Failed-load/future-version states never overwrite or serve a fresh fallback as a healthy production world. Preserve hash verification and `badSave`/`newerSave` guards. Check both graceful close and forced process death before the old two-second save boundary. Disk loss, corrupted hardware and cross-region replication are not promised; if power-loss durability is claimed later, file/directory flush behavior needs its own proof.

Empty rooms may be unloaded by `rooms.ts`. Store enough funded-job progress and a consumed offline interval marker to finish that one job on wake, through a host-only stamped op such as `rail.resume`. The host computes a bounded elapsed interval; apply receives only integer ticks, clamps to the remaining funded duration and consumes it once. Never read wall time in apply, double-count `bank.wake`, or produce new cargo while away. Server-running empty time uses ordinary ticks; server-down/idle-unloaded time only completes already-started work. Restore ordering is checkpoint → tail → one bounded catch-up → ready snapshot. Test repeated wake/restart at the same completion boundary.

Recommend a clean **development namespace break** when the production protocol is introduced: bump `WORLD_NS` with a dated history entry, preserve append-only rule ordering within it, and keep old tabs in their old world. A room query alone does not protect mixed registry/wire versions. Explain that this isolates/resets development world progress, including classic server saves in the old namespace; it does not delete prototype localStorage. This needs owner approval. Later shape changes use `version`/`migrate` unless another explicit break is chosen. Validate the complete `railway` document into a temporary value, including cross-account/phase invariants, before replacing live state; no partially applied slice restore.

## Presentation, ordering and lifetime

Extract a presentation-only primitive builder from `gifts.ts` when its consumers migrate; rooms must not import gift saving/registration just to build geometry.

Preserve the current causal order explicitly before decomposing further:

1. Accepted edits in server sequence, then deterministic feed/lay/cargo ticks, then read-only adapter updates.
2. Machine/cart/platform kinematic poses and deck deltas before the player controller consumes support; stable platform ids survive state reconstruction. Never clear a ridden platform merely to redraw its mesh.
3. Retain movement's pre-controller order 22, controller order 40 and post-controller order 42 semantics; preserve ring selection at update 11. Do not create one new generic order that changes those relationships.
4. Current place update order is run → cargo → forge → pieces → moments/gifts → folk → chop/crates → town/interiors → tech. Move each complete object's behavior while preserving its producer/consumer edges. Once accepted state replaces a producer, presentation reads that state, not another entity's interpolated mesh.
5. Snapshot replaces state first, rebuilds stock/phase/laid mask and colliders coherently, clears obsolete anticipation, then resumes presentation. Destroy removes bodies, platform handles, listeners, camera constraints, overrides and owned GPU resources. Test mount/unmount/remount with stable counts; hiding a group is not teardown.

Record actual phase slots from `src/loop.ts` during implementation; the list above is a required dependency order, not permission to collide with core registrations. Keep first-seconds content and all rules eager; lazy-load debug mutation and genuinely later interiors only after ownership is established. ## What can keep running, and where to stop

The existing default round, explicit place/classic links, still-used experiments and independent approved visual work remain playable while the isolated production proof grows. They retain their current authority in their own rooms only. Never let a player move inventory between the old and new worlds, or attach both authorities to one room. An old tab may continue its isolated prototype session; explain that its progress is not imported into the new production save. Keep the full-run regression bot usable throughout. Later support a debug tester that invokes real production code; do not retain a second production implementation as a permanent fallback.

Stop conditions:

- **Before code:** owner scope approval and the round-4 playtest gate, except the owner's explicit 4 November authorization to start slice 1 headlessly now. Already-approved independent fixes and non-flow-changing graphics may continue under owner-calls; this plan does not authorize new parallel gameplay.
- **At the authority boundary:** unequal hashes/counts, lost or duplicated material, unsupported source coordinates, nondurable accepted edits, ambiguous receipts, or a corrupt-save fallback stops integration. Fix the contract before adding another station. A nicer animation cannot waive it.
- **At the presentation boundary:** duplicated registrations/bodies, platform discontinuity, new import-cycle/suppression debt or an accepted solo beat lost stops promotion. Keep unresolved visual quality behind the proof flag; three inspection rounds are not permission to ship a conservation failure.
- **At the feel boundary:** if authoritative delay breaks the liked chop/deposit feel, record input→intent, input→acceptance and acceptance→visible-stock separately. Stop after the bounded proof and ask about the observed tradeoff; do not change global tick rate, yields or costs to mask it.
- **At the owner's T1 playtest:** stop and ask **“Did working separately still feel like building the same railway?”** One line on what's new: “Your shared station now survives leaving and returning.” Do not begin line 1 promotion while waiting. Acceptance permits the next agreed slice, not content-scale production.
- **At retirement:** a remaining consumer, pending playtest, unaccepted progression change or missing archive approval keeps that prototype available. The 2 November caution supersedes automatic cleanup. Keep every Boogler line; list suspect lines rather than editing them. None is nominated for removal here.

Material risks: the current mixed-material back differs from classic stacks; source scarcity can expose departed-player hoarding; personal storage can fail; exactly-once receipts and disk barriers add delay; idle eviction differs from “server always ticking”; timetable conversion can regress boarding; and rapidly landing tree/cart/water work can invalidate a source/phase assumption. Treat these as explicit acceptance checks and rebase reviews. This is a production-core proposal, not proof of fun, real-device performance, full-room scale or an eight-hour game.
