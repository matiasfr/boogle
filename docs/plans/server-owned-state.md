## 2. The target

- **Server decides** every shared outcome: it applies each command on arrival, in arrival order, through one command and receipt boundary (below), and replicates changed components. Clients **mirror**, **predict a declared subset** with the same pure rule, and render. No client hashes, no client ticks, no lead tab.
- **Owner-computed by design:** your own body (6 November, "server physics only for what's shared"). The server does not simulate movement. It validates the facts a command carries, as the railway does today (`Actor`: the action's own position `at` and action clock `ms`; reach and cadence judged from them). Added in the follow-ons: the server compares `at` with the session's last relayed presence pose and logs (not refuses) a gap over a generous bound, since exploits do not matter and R0's hard clock bound was removed for tripping bots.
- **What each classic state needs for feel** (designer rules on the predicted rows, D1):

## 3. The order question

Authority (who decides) and storage (closures or components) are separate moves. The railway proved it: it became Server kind at v14 on its old state shape and moved onto E at v17. A classic state becomes Server kind with `registerState(key, handlers, { server: true })` and a hand-written projection (`replication.define({ schema, ids, project, cell })`) over the closure state it has today; `src/sim/<x>.ts` is not edited (one exception: step 3 splits the key list in `src/sim/tune.ts`).

| Path | Files touched twice | Other cost |
| --- | --- | --- |
| **(a) as asked: onto in-house E components now, then the library** | All 18 sim and rules files (1,837 lines) and their 9 unit tests; any E-core growth is discarded if Becsy is chosen | Builds on the foundation the owner leans away from. |
| **(a') authority now on today's storage, storage once on the chosen library** (recommended) | The rules files' projection glue: 9 files, 830 lines; 2 files, 202 lines (tune, roster) if question 1 retires the seven. Sim files (1,007 lines) once | The hand projections are replaced by schema-derived ones later; about 20 to 40 lines per state. |
| **(b) library first, then each state straight onto it** | None | Everything waits for a decision not yet made; client lockstep, hashes and the lead tab stay meanwhile, and new sim work stays frozen (owner call). |
| **(c) per state, storage and authority in one step, tune first** | None | Needs the library chosen. Each step changes storage, authority and transport together, so a trace mismatch cannot be attributed to one of them. |

**Recommendation: (a') now, then (c)'s storage-only half per state once the library is chosen.** Authority is identical under every library and is what the thin client needs; storage is what the library changes. Doing authority first makes the later storage step a pure refactor against a fixed wire, with the trace oracle below.

**The same under every path, can start today:** (1) the trace oracle that pins today's behaviour; (2) the command and receipt boundary for classic ops; (3) durable acceptance; (4) the replica projection and client mirror for tune and roster; (5) removing each state from client hashes as it moves, then the classic transport; (6) the protocol description and schema export (section 6). **Must wait for the library:** rewriting `src/sim/<x>.ts` onto components, schema-derived projections replacing the hand ones, declared system access, the row inspector, the scheduler merge (stage E), and the player on components (stage G).

**Order correction.** The order in the brief (tune, roster and stacks, piles/sites/sources, gifts, bank and opening) is the storage dependency order. For authority it reverses: a lockstep state on a client cannot read a Server state (replication, section 4: "a state switches as a whole"; the server can read lockstep state, never the other way). `stacks` reads `roster` ordinals in apply; `stacks`, `sites` and `sources` read `tune` (`hard`, `cost`, `full`, `yield`, `trickle`) in apply and ticks; `site.stock`, `src.take`, `pile.take`, `pile.drop` and `tune.reset` each write two or more of stacks, piles, sites and sources. So: tune's 16 `rail*` keys and roster can move first only because the Server-kind railway is their one live reader; the 8 haul keys stay lockstep with their readers; stacks, piles, sites and sources move as one cluster; roster's ordinals stay until that cluster has moved.

## 4. Design

- **Sync kind:** Server for every state moved (docs/agents/sync.md). Authority: the server. Cosmetic: predicted effects and correction easing, Local, as on the railway.
- **Command and receipt boundary.** New `src/world/server-ops.ts`: `createServerOps()` with `define(op, { validate(e, ctx), apply(e, tick), durable?: boolean })`, `has(op)`, `run(pid, e, ctx)` returning `{ status: 'accepted' | 'rejected', result }`. `ctx` is today's `{ from, tick, env }` plus the railway's `Actor`. `server/src/host/railway-requests.ts` routes an `r:edit` whose op is not in `RAIL_ACTIONS` to `ops.run`; identity stays the session's `(epoch, request)`; receipts stay `ack`, `rej`, `ok` on the replication packet. A duplicate `(epoch, request)` applies once (the existing `order` and `session` refusals).
- **Durable acceptance.** One rule: the 2 s checkpoint plus the save on close (owner, 6 November). An op defined `durable: true` (`tune.commit`, `who.set`) calls `sync.saveNow(true)` and the session's `ack` does not advance past it until the write resolves; a failed write sends `r:state` `storage`. This replaces the classic recovery tail (`RecoveryEnvelope.tail`, `MAX_RECOVERY_TAIL`, the `recovery-budget` reason) when the last lockstep op goes.
- **Replica projection.** New `src/world/classic-replicate.ts`: schemas via `defineReplicated` and the client mirror. `tuneValue { key: 'str', v: 'int' }`, id = index in `TUNABLES`; `tuneRev { revision: 'int' }`, one row; `player { pid: 'str', name: 'str', color: 'u8' }`, id = roster ordinal. All in `GLOBAL_CELL`. `createClassicMirror()` returns read APIs with today's shapes (`TuneApi.get`, `cost`, `tune.rev`, `tune.revision`; `RosterApi.indexOf`, `nameOf`, `colorOf`), so `src/world/game-world.ts` swaps what `rules.tune` and `rules.roster` are and adapters keep their calls.
- **Client send.** `createRailwayAdapter` (`src/adapters/railway-session.ts`) gains `act(op, fields)` for non-rail ops on the same session, returning the request number, with the outcome through its existing `onAccepted` and `onRefused`. `src/features/identity.ts` and `src/debug/dev/tunables.ts` call it instead of `submitEdit`.
- **Lockstep entries removed, not added:** no new `rules/types.ts` entry, op, state key, `edits` generator, `invariants` or `env` fact. `protoRoom` and `tuneController` move from `ctx.env` to the server op's `ctx` unchanged. **Controls:** none; no action, pad slot, key, touch or guide row changes.
- **Rail route:** no beat's bill, supply or cue changes; tune feeds the railway's timing, so step 3 verifies with `npm run loop -- run`.
