## Design

- **Local controls:** keep `ping` on G/middle click/D-pad left and `place-drop` on right click/R3, with separate touch buttons. Registry inspection confirms their slots do not collide and D-pad up remains available for the update notice. `place.css` currently hides Ping on fresh pages; remove that hiding and position its own button beside Drop, including safe areas and the tablet layout. Existing labels suffice.
- **Interact priority:** an ordinary Interact target, including a blocked one, wins X/Square and E. Only when none exists may that press fall back to the nearest `click` target with empty hands. RT/left click retain their existing direct chop/use behavior. One press runs at most one target. Keep the touch label and visible prompt consistent with the selected action. This is a deliberate small core `hands.ts` change; do not add another X registration or mutate `actionById`. Describe the contextual Chop binding in the control registry so Pause explains it.
- **Local reward presentation:** `got.ts` owns a short anticipation phase before the existing rise and reveal. Start with a roughly 0.45 s hold, then the 0.45 s rise; reveal the item/name and play the existing fanfare at the reveal rather than immediately. A modest camera approach/reframe should frame player and item, using the existing camera constraint pattern and yielding cleanly to reset/dismissal. No new renderer or frame loop. Dismissal becomes eligible only after the reveal has been readable for the existing 0.6 s. Keep the existing capture-phase keyboard/touch guards, fresh press requirement and deliberate tap-versus-drag behavior. Reduced motion keeps timing and explicit dismissal but skips camera travel, item spin/bob, scale travel and decorative bursts.
- **Shared progression stays in its existing prototype sync kind:** `coop.ts`'s elected authority, shared snapshots and current messages remain unchanged. Detect newly accepted false-to-true local unlock transitions for presentation; never grant or spend from the animation callback. First join/reload reconciliation and Start over are quiet baselines, not a replay of every historical reward. Subsequent snapshot reconciliation must not suppress a live unlock merely because it arrives before its one-off message. Deduplicate each unlock within the current run, resetting the local presentation baseline on Start over. No new wire fields, message kinds, ops, saves or lockstep math.
- **Remote reward appearance:** use the recipient's existing `youGot` queue and the same tool/device mesh and existing name already used for local rewards. Cover multi-axe, proper axe, pack, and shared movement devices. A partner receipt does not replay the local device tutorial. Extract tiny existing model/show helpers as necessary rather than duplicating shape definitions. Do not add game prose; record any proposed line here for the owner instead.

## Risks and verification questions

- `hands.ts` is a core input seam: holding a throwable must not let X start a throw; a blocked interaction must not silently chop the tree behind it. Touch's single button and the floating prompt must agree.
- Camera ownership must coexist with `celebrate.ts`, indoor framing and reward queues. Reset and dismissal must release both camera and input; reduced motion must skip travel.
- Snapshot-before-message ordering currently makes the multi-axe silent. Presentation deduplication must cover both paths while keeping initial historical state silent.
- Existing `npm run inflight` lists an older controls documentation branch (`ship/matias-franco-98950cd`); keep changes confined to this checkout and do not reconcile unrelated work. No further network use.
- Evidence questions: are Ping and Drop distinct and reachable together on touch; does Square produce exactly one intended action at a tree/interactable overlap; does anticipation visibly precede the item/name and does the camera frame the item; does the second player visibly receive an unlock once?
- Physical gamepad hardware, real touch dragging on a device, heard sound and real-time smoothness remain owner/device verification. Browser dispatch and sampled frames support narrower claims.
