# Plan: a beautiful corner

> **Draft — needs the owner's approval before implementation. 2 November 2026.** Next phase after the current prototype round, not permission to start it now. All boxes below describe future work. This document changes no game behaviour and approves neither the broader [rail slice](rail-slice.md) nor a whole-game look rollout.

## Goal

Make Station 2's complete gorge crossing in `?proto=place` a small, exceptionally polished, freely playable quality target, then measure how quickly the same craft can make a second arrangement. Serve **DESIGN.md 1, Toys before chores; 7, Telegraph everything; and Small and readable**: shared pride in a chunky machine making a beautiful crossing, with an understandable action and a production method we can repeat.

The owner's brief is “a very polished vertical slice ... just see how polished, how quickly we can get something really polished, even if it's just a small part, like a beautiful corner”. No principle is proposed to bend. This local target can demonstrate craft; **Cooperation is automatic** and **Leave something for the next visitor** require a later approved shared implementation before we call it a co-op production slice.

### The machine's material contract — confirm before building

Use the paintings' **docked feeder, cutter and gripper**, with simple named pivots and a visible route from log to sleeper and from rail rack to placed rail. The current `stepFeed()` empties the frame before departure; `stepLay()` reduces cradle/rack counts by progress. That is not yet an individually staged cutter/gripper handoff.

**Recommendation [H]:** the stationary frame keeps each log until its visible transfer; docked rollers/cutter prepare the load into the mobile cradle, then the gripper lays from that finite visible stock. Track supports → deck → sleepers → rails seat in that order; no rail is simultaneously on the rack and in the gripper. Keep the small machine, standing deck and material path readable from ordinary camera angles. Preserve the accepted quantities and travel speed while comparing.

`look-pass.md` asks for logs remaining in the frame while laying, and the paintings compress the distance between frame and travelling machine. **That literal staging is unresolved:** a frame that stays stocked while feeding a machine 54 m away requires an actual transfer method. Recommend the dock/load/depart interpretation above for this corner; get the owner's answer rather than quietly replacing the requirement, teleporting stock, moving the frame with the machine or inventing a logistics subsystem. Physicality here means supported, visibly continuous construction, not a new Rapier body for every sleeper.

### Work split and review batching

After approval, **Codex can start** bounded TypeScript/TSL effects, kit geometry/export work, explicit surface/shore data and measurement/eval tooling against agreed dimensions and named attachment points. It can inspect source, run headless checks and hand off reproducible candidates. **Codex cannot see the running game in this workflow**, so compilation is not appearance, and its work is not visually accepted or ready to ship by itself.

**Claude is the integrator with eyes:** inspect the first playable change, assemble the outputs, run targeted `look` captures, open them, watch wall-time motion, play collisions and tune composition, palette, machine timing and sound. Batch candidates into three coherent review bundles: **place/light**, **material-to-track action**, **water/life/final integration**. This saves repeated Claude setup and usage while retaining every required inspection; it never justifies weaker verification. Keep kit/TSL/tooling file ownership separate, serialize edits to `layout.ts`, `look.ts`, `index.ts` and shared services, and send one handoff containing commit, owned files, controls, before/after settings, known defects and exact capture actions. A merged diff is not an integrated visual verdict.

### Frame budget and measurements

**Proposed acceptance budget [H], not measured available headroom:** aim for **60 Hz / 16.67 ms frame delivery** on M4 Safari and desktop, with about **20% steady-state headroom** (roughly 13.3 ms work envelope). Compare at a verified **1600×900 scene target, 1.44 MP, existing 4× stored MSAA**, then repeat normal adaptive-resolution play and report the settled dimensions. `dpr=fixed` alone does not select those pixels. No iPad-only aesthetic reduction by assumption; both targets matter, and every cut must have measured cause.

Within that envelope, trial **≤10 ms p95 total GPU work** and **≤2 ms incremental GPU / ≤0.5 ms p95 added main-thread work for water plus the living-effects set**, following the research. These are ceilings, not quantities to spend. The whole-corner baseline must first fit; if it is already over the research's 8 ms pre-effects allocation, measure and narrow optional layers before adding more. Do not add CPU/GPU times, isolated p95 values or render/compute categories and call the sum presented frame latency.

Initial effect caps [H]: 4k–8k visible grass blades in spatial opaque batches, no grass shadows; at most 24 round puffs; two pennants; a few birds and one insect habitat, no new lights. Aim for ≤256 normal live particles and ≤512 short bursts within the existing 720 slots/256-spawn queue. Trial roughly ≤12 extra draws and ≤8 MiB extra effect texture/buffer payload, with no extra fullscreen target/pass. These are combined rejection guides; fewer is fine. Cliff/machine geometry and existing residents are measured separately inside the total ceiling, not declared free or charged against a second invented effects budget.
