**Whole round: `npm run playthrough`** (the production route; `--long` lets the whole of it run, about 13 minutes; `--to <beat>` stops early; --warp underneath, nothing is real time). A bot plays the round and you get time per beat, what never happened, where it stalled, and every line on screen with how long it showed, for cutting text with evidence (Show, don't tell); the full session is in `.look/playthrough/<name>/`. It prints what changed since the last run; `--full` or `report.txt` has everything. Run it after anything that changes pacing. `--name before` keeps a run; `--compare before after` sets two side by side; the bot isn't exact, so read differences under about a minute as noise and rerun before trusting a lone `NEVER`. The bot knows the way, so its times are a floor for a first-timer. The bot is `dev/look/bots/railway.ts` (`dev/look/evals/railway-job.ts` runs it): a new beat goes there, and a track that adds one keeps it playing. Segments, seeds and two players: `docs/agents/test-details/bot-segments.md`. It's built on `dev/look/bot.ts`: `bot.walk` plans over the real colliders as they stand now, so a new bridge or gate needs no route code; `bot.use` walks up and presses what the game offers; `bot.until(fn, ms, what)` records a beat that never came, which fails the run. `--stall` counts only new beats and bot lines, so a loop stops early. `bot.txt` in the run's folder has all it said.

**Start at a shared beat: `npm run look -- --rail-seed q5-done`.** The railway is server state, so a production beat starts from an accepted server seed (`dev/look/rail-seed.ts` names the stages), not a client save. **`--at "path opened"`** (8 s) restores a beat of the last playthrough through the client's own save only: on production that is the pose and personal things, not railway progress (the legacy Place route kept its progress there); `--at list` names the beats. Add `--cam`, `--action`, `--video` as usual. Run a new playthrough when the save's shape changes. A save can't hold what the game doesn't save (a train part way along).

**Owner contact sheet: `npm run sheet`** still plays the legacy `?proto=place` bot and its client saves (not yet moved to production seeds); it plays the bot, captures a short exact-name beat list and the real round-4 first visit, and writes `.look/sheet/<name>/contact-sheet.png` plus `sheet.json` (source/run provenance, timings and capture manifests). `--name review` names the output and new run; `--run review` reuses its checkpoints. `--beats "forge lit,path opened"` captures only those exact beats. Missing beats, bot failures, never-marked beats and longest waits stay visible; all checkpoints outside the curated list print for upkeep. Captures run serially. Exit success is capture health, never a visual pass; inspect every image. Sheets cannot judge feel, sound, real-time motion or first-time understanding.

`--before <ref>` reuses before-after with the same checkpoint and pairs one beat per row only after live readbacks agree: position within 1 m, same room/interior, track metres and town population. Both must also match the checkpoint's saved position, room and progress, so two fresh fallbacks cannot pass. `capture-restore-pair.json` keeps the expected state, both readings and the decision; a mismatch names the measured difference in a NOT COMPARED panel. Changed save-owner code adds a row note, not a veto. No substitute moment. The current broker has no alternate-build route: brokered comparisons remain unavailable; run this mode on the local harness. `before-after --verify-restore` opts into the same check; other callers are unchanged.

`--moments` attempts real hook, glide and train-departure inputs from prior checkpoints (glide needs a fresh run's added mark); reveal and run-end strips are explicitly omitted where checkpoints cannot honestly recreate them. `--coop` was removed: `place-coop.ts` asserts on the retired `placeCoop` message while the game sends `placeCoopCargo1`, and a real-speed town fixture left player 1 in the field while player 2 reached the shop. Neither supplies the intended two-player picture. Opening uses a fresh same-origin iframe with `proto=place&intro=1`, the real Jump in button and wall-time video/samples; it is not frame-exact. No game/save changes or invented moment state.

**Frame-exact stills:** `--filmstrip N --every K` captures N images K drawn 60 Hz frames apart (K defaults to 1), paused between shots; labels show frame and elapsed game time. Use `--curves` to record the same frames. It needs warp and cannot be used with `--real`, `--url`, or `--players`.
Filmstrips show poses, not real-time feel or smoothness; the server and CSS still run on wall time.

**Motion as numbers: `--curves`** adds a plot and CSV of every frame's speed, vertical speed, height, camera distance and frame time, plus readings, while the action plays in real time. Use it for glide, hook, sprint or any camera change: `npm run look -- --at "path opened" --curves --action dev/look/evals/sprint-jump.ts --seconds 6 --frames 2`. `--curves-vs old.csv` draws an earlier run underneath; `--target glide` (or `glide-slow`, `glide-frame`) draws and scores against a reference and says when each value settled; numbers and what's unknown: `docs/research/botw-glide-target.md`, which also gives the transients to compare by hand. Frame the steady part in the last third, and `playMark` the moment the action starts so its line is on the plot.
